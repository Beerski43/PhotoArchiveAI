# PR レビューコメントの起票

## このスキルが目指すもの

レビューの価値は、指摘の数でも鋭さでもなく、**作者が読んだ直後に手を動かせるか**で決まる。
そのために3つを守る。

1. **検証していないことは書かない。** 思いつきの指摘は、作者に「確認する仕事」を
   増やすだけで、間違っていれば信用ごと失う。走らせて再現できたものだけを出す。
2. **重要度を先に示す。** 作者が最初に知りたいのは「マージしていいのか」であって、
   指摘の詳細ではない。表を先頭に置き、詳細は後ろに回す。
3. **判断は作者に返し、作業は引き取る。** 決められないことは選択肢と推奨をつけて渡す。
   決まっていることは新しい Issue に逃がさず、そのPRで片付ける算段まで書く。

この3つを支えているのが、次の前提。

## 前提: 白紙の文脈で始める

**レビューは、その変更に関わっていない第三者として行う。**
実装した本人（＝同じセッション）が続けてレビューすると、レビューとして成立しない。

- 何を意図したかを覚えているので、**コードが意図どおり動くと思い込む。**
  「たぶんこうなる」が「知っている」にすり替わり、検証（§3）を丸ごと省く
- 自分の設計判断を弁護する側に回るので、重要度が甘くなる
- PR 本文を自分で書いていると、その主張を仮説として疑えない

実際、#31 のレビューで最も効いた指摘（「集計行が端末では必ず `0 passed`」）は、
PR 本文の「107 passed」を**鵜呑みにせず自分で走らせた**から見つかった。
書いた本人なら「さっき通ったから大丈夫」で終わっていた。

### 始める前に確かめること

このセッションが、レビュー対象について次のどれかに当てはまるなら、**読み進めない。**

- その変更を実装した / コミットした / PR を作った
- 同じPRを既にレビューして意見を述べた
- ファイルを開く前から、どこが問題かを「知っている」

当てはまる場合は、次のどちらかを**ユーザーに一言で示して止まる。**

1. **`/clear` してから呼び直してもらう（推奨）。** ユーザーが求めているのは
   第三者の目であって、作業の続きではない
2. セッションを残したいと言われたら、**まっさらなサブエージェント**に
   レビューを任せる（`Agent` ツール。`subagent_type` は `general-purpose` などを使い、
   **`fork` は使わない** — fork は今の文脈をそのまま引き継ぐので意味が無い）。
   その場合、サブエージェントには「PR番号」と「このスキルを読むこと」だけを渡し、
   こちらの見立ては伝えない

**「白紙」とはリポジトリを知らないことではない。** §0 で作業ルールや仕様書を読むのは
必須で、むしろ外から来た人ほど文書を読む。避けたいのは
**その変更について既に持っている結論**であって、前提知識ではない。

## 0. 足場を固める

- `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` / `CONTRIBUTING.md` を読む。
  そのリポジトリの作業ルール（ブランチ運用、Issue の粒度、テストの必須手順、
  用語）を知らずに書いた指摘は的を外す。**ルール文書自体がPRに含まれているなら、
  それも査読対象**であることを忘れない。
- 対象PRを確定する。引数に番号があればそれ。無ければ現在のブランチのPR。
- **コメントは PR / リポジトリの言語に合わせる。** 日本語のリポジトリに
  英語のレビューを置かない。

## 1. 集める

```bash
gh api repos/:owner/:repo/pulls/<N> --jq \
  '{number,title,state,base:.base.ref,head:.head.ref,body,additions,deletions,changed_files,mergeable}'
gh api repos/:owner/:repo/pulls/<N>/files --jq '.[].filename'
git fetch -q origin && git diff origin/<base>...origin/<head>
```

`gh pr view` は Projects (classic) の廃止告知で GraphQL エラーになる環境がある。
落ちたら上のように `gh api` を使う。

PR 本文の主張（「〇〇を直した」「回帰テストは N passed」）は**検証対象の仮説**として
読む。鵜呑みにしない。

## 2. 差分を読む

差分だけでは判断できないことが多い。**変更行の周辺ではなく、その関数の呼び出し元と
呼び出し先を開く。** 特に次を追う。

- 追加された分岐が、既存の全経路で成り立つか（早期 return、例外、並列実行、初回 / 2回目）
- 状態を持つもの（グローバル変数、キャッシュ、DBの列、バージョン文字列）の
  書き込み側と読み出し側が対応しているか
- ドキュメント・ヘルプ文字列・設定サンプルが実装と一致しているか
- 新設された仕組み（スクリプト、CI、テンプレート）自体に欠陥がないか。
  **新しい足場は誰も踏んでいないので、いちばん壊れている**

## 3. 検証する — ここが核心

**指摘を書く前に、手を動かして確かめる。** 確かめられなかったものは、
そう明記するか、落とす。

- テスト・回帰スクリプトがあるなら実際に走らせ、出力を控える
- 疑わしい挙動は**最小の再現を自分で作る**。一時ファイルは
  リポジトリの外（`$CLAUDE_JOB_DIR/tmp` など）に置く
- 「たぶんこうなる」で止まったら、定義まで `grep` して裏を取る

**落とした候補も価値がある。** 確かめた結果ちがっていた指摘は、レビュー本文の
「確認して問題なかったもの」に回す。作者はそこを再確認せずに済む。

> 実例: ある版で「`EMBED_VERSION` を上げても再スキャンされない」と書きかけたが、
> `DETECTOR_VERSION = f"mediapipe_fd1/{EMBED_VERSION}"` を読んで成立すると分かり取り下げた。
> 同じ回に、想像ではなく実行で見つかった「集計行が端末では必ず 0 passed になる」は
> 採用された。**出してよい指摘と出してはいけない指摘を分けるのは、検証だけ。**

## 4. 重要度と対応先を決める

重要度は「指摘の賢さ」ではなく、**マージ前に直すべきか**で決める。

| 重要度 | 意味 |
|---|---|
| 🔴 必須 | 壊れている / データが消える / 仕様・ドキュメントと実装が食い違う。マージ前に直す |
| 🟡 推奨 | このPRの中で直せて、放置すると近いうちに人を惑わせる |
| 🟢 任意 | 好みや将来への備え。直さなくてもよい |
| 🔵 判断 | 自分では決められない。ユーザーの決定が要る |

**対応先は原則すべて「このPR」。** 指摘をPRから切り離して新しい Issue にすると、
文脈（なぜそれが問題なのか、どの行なのか）が失われ、直りが遅れる。
Issue を増やさないこと自体が目的ではなく、**直る確率を上げるため**にこのPRへ寄せる。

どうしてもこのPRに収まらないときは、新しい Issue ではなく
**そのリポジトリの計画文書（ROADMAP / プラン）に「要判断」として残す**案を提示し、
Issue 化するかどうかはユーザーに決めてもらう。

## 5. コメントを書く

この順序で書く。詳細を先に置くと、重要度が埋もれる。

````markdown
## レビュー: PR #<番号>

<何を読み、何を実行したかを1〜2行。>

**<全体の判定を1文で。>** <良い設計判断があれば具体名で1〜3行。
お世辞ではなく、作者が「この判断は維持してよい」と分かるように書く。>

そのうえで、**このPRの中で片付けたい点が N 件**あります。新しい Issue は立てず、
ここで決着させる前提で書いています。うち M 件は判断を仰ぎたいので最後にまとめました。

### 指摘一覧

| # | 重要度 | 箇所 | 指摘 | 対応 |
|---|---|---|---|---|
| 1 | 🔴 必須 | `path/to/file.py:70` | <症状を一文で> | このPR |
| 2 | 🟡 推奨 | `docs/plan/ROADMAP.md` | <症状を一文で> | このPR |
| 3 | 🟢 任意 | `.gitignore` | <症状を一文で> | このPR |
| 4 | 🔵 判断 | `data/` | <決めてほしいこと> | 下記 (a) |

---

### 1. 【🔴 必須】<見出し>

**症状。** <何が起きるか。>

**原因。** <なぜそうなるか。該当コードを引用する。>

**再現。** <実際に打ったコマンドと、その出力をそのまま貼る。>

**修正案。** <差分か、具体的な手順。複数あるなら推奨を明示する。>

**テスト。** <足すべきテストと、その名前の案。>

<以降、番号順に同じ形で。任意(🟢)は数行で足りる。>

---

### 確認して問題なかったもの（記録として）

- <検証して問題が無かった点。作者が再確認せずに済むように。>

---

## 判断を仰ぎたいこと

**新しい Issue は立てず、このPRで決着させたい前提で書いています。**
「これは後回し」という判断であれば、そう言ってください。

#### (a) <論点>

<背景を2〜3行。>

1. **<案1>** — <利点と欠点。> **これを推します**
2. **<案2>** — <利点と欠点。>
3. **<案3>** — <利点と欠点。>

---

### まとめ

<どれをこのPRで直してほしいか、どれに返答が要るかを2〜3行で。>
````

書くときの勘どころ。

- **判断待ちは、選択肢と推奨をセットで出す。** 「どうしますか？」だけでは
  設計の仕事を丸投げしたことになる。2〜3案を並べ、自分ならどれを採るかと
  その理由を書く。ユーザーは選ぶだけで済む。
- **再現は貼る。** 「〜になります」ではなく、打ったコマンドと出力を貼る。
  作者が自分で確かめ直す時間をゼロにする。
- **修正案はコードで示す。** 説明だけだと解釈が割れる。
- **「確認して問題なかったもの」を省かない。** ここがあるレビューは、
  指摘そのものの信頼度が上がる。

## 6. 投稿する

```bash
gh pr comment <N> --body-file <一時ファイル>
```

本文はヒアドキュメントで一時ファイルに書いてから渡す。長文を直接引数にしない。

**合図を待たずに投稿する。** 🔴 必須 があっても同じ。レビューは作者に届いて
初めて仕事になる。承認待ちで会話の中に溜めると、**いちばん急いで直してほしい
指摘がいちばん遅く届く。**

**誤った重大指摘を防ぐのは、承認ではなく §3 の検証。** 走らせて再現できたものしか
書いていないなら、投稿して困ることはない。逆に、検証を省いたまま承認をもらっても
間違いは間違いのまま残る。**「確認しますか」と聞きたくなったら、それは検証が
足りていない合図**なので、聞くのではなく確かめに戻る。

投稿したら、**重要度表と「判断を仰ぎたいこと」だけを会話にも出し、コメントのURLを
返す。** ユーザーはそこで中身を見る。間違いに気づいたら本文を直せる（消さずに直す）。

```bash
gh api repos/:owner/:repo/issues/comments/<コメントID> -X PATCH -F body=@<一時ファイル>
```

## やりがちな失敗

- **走らせずに書く。** いちばん多い。テストがあるのに実行しない、
  再現できるのに再現しない。
- **良い点を書かない、または中身のない褒め方をする。** 「よくできています」は
  情報がゼロ。維持してほしい設計判断を名指しする。
- **指摘を Issue に逃がす。** 「これは別 Issue で」は楽だが、文脈が失われて放置される。
- **重要度を盛る。** 全部 🔴 にすると優先順位が消え、表の意味が無くなる。
- **判断待ちを質問だけで済ませる。** 選択肢と推奨を出す。
- **リポジトリの用語を使わない。** そのリポジトリが「手本」と呼ぶものを
  「教師データ」と書くと、指摘の中身以前に噛み合わなくなる。
- **自分が書いたものを、その流れのままレビューする。** いちばん質が落ちる。
  上の「前提」に戻ること。
- **投稿前に合図を待つ。** 待っている間、作者は何も知らない。確信が持てないなら
  §3 に戻って確かめる。確かめたなら出す。

## 長さの目安

指摘1件あたり20〜40行（症状・原因・再現・修正案・テスト）、🟢 任意は5行程度。
全体で200〜300行に収まる。これを大きく超えるなら、🟢 を削るか、
指摘をまとめられないか考える。**読み切れないレビューは読まれない。**
