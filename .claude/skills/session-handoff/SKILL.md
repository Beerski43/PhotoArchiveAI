# セッションの引き継ぎ

## このスキルが目指すもの

**クリアしたあとの自分は、この会話を1行も覚えていない。** 残るのは git と GitHub と
文書だけ。だから引き継ぎの価値は、書いた量ではなく、**次のセッションが
`CLAUDE.md` §1・§2 の読む順どおりに読んだだけで、迷わず次の一手を打てるか**で決まる。

いちばん失われやすいのは**コードではなく、会話の中にしか無いもの**。

| 失われやすいもの | 例 |
|---|---|
| 利用者の決定 | 「PR に入れる」「控えは毎回選ぶ」「版は 1.8 のまま」 |
| 測った数字と、その読み方 | 実データで測った件数・時間・割合（**日付つきで**） |
| 調べて外れた仮説 | 「母の顔を手本にしている」→ 該当 1 件で外れ |
| 着手の許可の有無 | 起票しただけで**着手は指示待ち**、なのか |
| 踏んだ落とし穴 | 同じ穴に次のセッションが落ちないように |

**これらを文書へ移すのがこのスキルの本体。** git の状態を整えるのは前提でしかない。

## 0. 足場を固める

- `CLAUDE.md` を読み直す。とくに §3（進め方）と §5（セッションを切る前に）
- いまのブランチ・作業ツリー・push の状態を見る

```bash
cd ${REPO_DIR} && source .venv/bin/activate
git status -sb && git log --oneline -5
python scripts/check_handoff.py
```

**`develop` / `main` に直接コミット・push しない**（CLAUDE.md §3）。申し送りは
**いま作業しているブランチ**に入れる。開いている PR があれば、その PR に入れれば
マージと一緒に `develop` へ届く。**作業ブランチが無い（`develop` の上にいる）ときは、
どこに入れるかを利用者に聞く。**

## 1. 浮いている作業を片付ける

- **未コミットの変更**: 中身を見て、この作業の一部ならコミットする。何の変更か
  分からないものは**捨てずに利用者に聞く**
- **未 push のコミット**: push する
- **PR の無いブランチ**: `check_handoff.py` が教える。申し送りに書くか、利用者に聞く
- **一時ファイル**: **このセッションで作った**実データの複製（`$CLAUDE_JOB_DIR/tmp/*.db`
  など）は消す。**前からあるものは消さずに、場所と大きさを報告する**（別の作業の
  控えかもしれない）。**実データ本体（`data/photoarchive.db`）とその控え（`*.bak-*`）は
  消さない**
- **使い捨ての測定スクリプトはリポジトリに足さない。** 測り方は details の文書に
  書く（数え直せるように）

## 2. 会話の中にしか無いものを文書へ移す

会話をさかのぼって、次を拾う。**拾ったものは置き場所を決めて書く。**

| 拾うもの | 置き場所 |
|---|---|
| 利用者の決定・指示（**原文を引用**） | WORKLOG のエントリ、PR 本文、Issue のコメント |
| 実データで測った数字・調べた結果 | `docs/history/details/<日付>-<英語のケバブケース>.md`（**日付と数え直す手段を添える**） |
| 次の作業の根拠になる分析 | 上の details ＋ **該当する Issue にコメント**（次に読むのはそこだから） |
| 計画の変更 | ROADMAP を書き換え、WORKLOG に「プラン改版」を1行 |
| 踏んだ落とし穴 | 申し送り。**繰り返し踏みそうなら `CLAUDE.md` §8** |

**Issue は勝手に起票しない**（CLAUDE.md §3.3）。起票が要りそうなものは、
申し送りに「起票の可否を利用者に聞くこと」と書く。

## 3. 申し送りを書く

`docs/history/details/<日付>-<英語のケバブケース>.md`。**このファイルを読めば、
文書だけで再開できる**ことを目標にする。形はこれ。

```markdown
# 申し送り（YYYY-MM-DD）— <一言で>

**このファイルを読めば、文書だけで再開できる状態にしてある。**

## いまどこに居るか
| | 状態 |
|---|---|
| ブランチ | `feature/#N_...`（push 済みか） |
| PR | #N（マージ待ち／マージ済み） |
| Issue | #N（親は #N） |
| 回帰テスト | N passed / M failed（日付） |
| 実データ | 触ったか。触ったなら何をしたか・控えの場所。**件数は日付つき** |

## このセッションで済んだこと
## 利用者が決めたこと（原文）
## 次にやること（**着手の許可があるものと、指示待ちのものを分けて書く**）
## 判断待ち（誰に何を聞くか）
## 踏んだ落とし穴（繰り返さないために）
## 読む順
```

**前の申し送りが役目を終えたら、その冒頭に「役目を終えた。次は <新しいファイル>」と
1行足す**（消さない。経緯を追えなくなる）。

## 4. WORKLOG と ROADMAP

- `docs/history/WORKLOG.md` の**先頭**にエントリを足し、**申し送りへのリンクを張る**
  （リンクの無い申し送りは回帰テストが見つける）
- `python scripts/archive_worklog.py` を流し、その差分も同じコミットに入れる
- `docs/plan/ROADMAP.md` の「現在地」と表が実態どおりか見る。**マージ待ちの PR が
  マージされた前提で書かない**（「マージ待ち」と書き、マージ後の一手を書く）

## 5. 点検して、コミットする

```bash
./scripts/run_regression.sh          # 繋がらない環境では --offline
python scripts/check_handoff.py      # 「気になる点は見つからなかった」まで
```

- **回帰テストが落ちたままにしない。** 落ちているなら直すか、申し送りの先頭に
  **落ちていること・なぜか**を書く
- コミットの先頭は `#<Issue番号> `。push する
- PR があるなら、本文の回帰テストの行を最新にし、「引き継ぎを書いた」とコメントする

## 6. 報告する

利用者に短く返す。**クリアしてよいかどうかを、はっきり言う。**

```
引き継ぎを書きました。クリアしてよい状態です。

- 申し送り: docs/history/details/<ファイル>
- 回帰テスト: N passed / 0 failed
- 残っている判断待ち: なし（または 1行ずつ）

次のセッションでは「実装を再開して」と言えば、申し送りから始められます。
```

**クリアしてよくない状態**（落ちたテスト、未 push、利用者に聞くべきことが残っている）
なら、**そう言って何が残っているかを並べる。** 「たぶん大丈夫」で送り出さない。
