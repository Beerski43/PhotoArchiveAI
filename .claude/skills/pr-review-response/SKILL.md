# PR レビュー指摘への対応

## このスキルが目指すもの

レビュー対応の価値は、直した数ではなく、**レビュアーが返信を読んだだけで
再確認を終えられるか**で決まる。そのために3つを守る。

1. **直す前に再現する。** 指摘は仮説であって事実ではない。再現せずに直すと、
   壊れていないものを変え、本当の原因を残す。再現できなかった指摘は、
   そう書いて落とす。
2. **判断は先にまとめて聞く。** 作業の途中で何度も止めると、レビュアーも
   ユーザーも待たされる。仕分けの直後に一度だけ聞く。
3. **指摘と対応を1対1で返す。** 表で対応させ、直したものは証拠（実行結果）を、
   落としたものは理由を添える。**黙って無視された指摘が1つでもあると、
   レビュアーは全部を見直す羽目になる。**

## 前提: 作者として答える

レビューを書く側（`pr-review-comment`）は白紙の文脈を要求するが、**こちらは逆で、
実装した本人のセッションがそのまま続けてよい。** 何を意図したかを知っているほうが、
指摘が的を射ているかを速く判断できる。

ただし1つだけ、作者だからこその危うさがある。**自分の実装を弁護する側に回ること。**
「そんなはずはない」と思ったら、それは反論を書く合図ではなく、**再現を試す合図**。

## 0. 足場を固める

- `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` / `CONTRIBUTING.md` を読む。
  修正にテストが要るか、コミットメッセージの形、回帰テストの走らせ方、
  PR をマージしてよいかは、そこに書いてある
- **返信の言語は PR に合わせる。** 日本語のレビューに英語で返さない
- 対象のブランチに切り替える。`git fetch` して、`develop`（統合ブランチ）から
  遅れていないかも見ておく

## 1. URL から指摘を取り出す

**URL を貼られただけで動けること。** 渡されるものは次のどれか。

| 渡されるもの | 例 | 取り出し方 |
|---|---|---|
| PR のコメント | `.../pull/36#issuecomment-5746112292` | `gh api repos/:owner/:repo/issues/comments/5746112292` |
| 行コメント | `.../pull/36#discussion_r123456` | `gh api repos/:owner/:repo/pulls/comments/123456` |
| レビュー | `.../pull/36#pullrequestreview-123456` | `gh api repos/:owner/:repo/pulls/36/reviews/123456` |
| PR 本体 | `.../pull/36` / `#36` / 番号だけ | 下の「全部さらう」 |

```bash
# 1件だけ取り出す（本文と投稿者と日時）
gh api repos/:owner/:repo/issues/comments/<ID> --jq '.user.login + " @ " + .created_at + "\n\n" + .body'

# 全部さらう（PR 本体を渡されたとき、または指摘が散らばっているとき）
gh api repos/:owner/:repo/issues/<N>/comments --jq '.[] | "--- \(.user.login) \(.html_url)\n\(.body)"'
gh api repos/:owner/:repo/pulls/<N>/comments  --jq '.[] | "--- \(.path):\(.line) \(.user.login)\n\(.body)"'
gh api repos/:owner/:repo/pulls/<N>/reviews   --jq '.[] | select(.body != "") | "--- \(.user.login) \(.state)\n\(.body)"'
```

`gh pr view` は Projects (classic) の廃止告知で GraphQL エラーになる環境がある。
**`gh api` を使うほうが確実。** `gh pr edit` も同じ理由で落ちるので、本文を書き換える
ときは `gh api -X PATCH repos/:owner/:repo/pulls/<N> -F body=@file.md` にする。

URL に `#` が無い（PR 本体）なら、**そのPRのコメント・行コメント・レビューを全部さらってから**
仕分けに進む。どれが最新の指摘か分からないときは、いちばん新しいものを対象にして、
そう明示する。

## 2. 指摘を仕分ける

レビューが表を持っているならそれを土台にする。無ければ本文から拾って自分で作る。
**拾い漏らしを防ぐため、番号を振って全件を表に載せる。** 最後の返信でこの表を使う。

| 仕分け | 意味 |
|---|---|
| 採用 | 直す。ほとんどの指摘はここ |
| 見送り | 再現しない / 事実誤認 / 別の理由で今は直さない。**理由を必ず書く** |
| 判断待ち | ユーザーが決めること。設計の方向、命名、運用ルール、互換性を壊すか |

**レビュアーが「🔵 判断」と印を付けていなくても、判断待ちは自分で見つける。**
たとえば「この引数を消すべき」は、消すと利用者に影響が出るなら判断待ち。

## 3. 判断が要るものを、一度だけ聞く

判断待ちが1件でもあれば、**作業を始める前にまとめて聞く。**

- 選択肢は具体的に。「どうしますか」ではなく、**取りうる案とそれぞれの結果**を並べる
- **推奨を1つ示す。** 丸投げしない。レビュアーが推奨案を書いているならそれを尊重する
- 聞くのは1回。実装の途中で新しい判断が要ると分かったら、それも**まとめて**聞く

判断待ちが無ければ、この節は飛ばしてよい。

## 4. 直す前に再現する — ここが核心

**採用した指摘は、直す前に症状を自分の手で出す。**

```
症状が出ることを確認 → 直す → 症状が消えることを確認
```

再現の出力（コマンドと結果）は控えておく。返信にそのまま貼る。

**再現できないときは、直さずに落とす。** そして落とした理由を返信に書く。
レビュアーが間違っていることも、環境が違うこともある。

> 実例（PR #36）: レビュアーが「`--thresholds -inf` で止まることをテストせよ」と
> 提案したが、実際に走らせると argparse が `-inf` をオプション名とみなして
> `expected one argument` で落ち、**検証したい経路を通らなかった**。
> `-1` は数値として通る。テストからは `-inf` を外し、負の無限大は
> `math.isfinite` で同じ枝に落ちることをコメントに残し、返信でそう説明した。
> **提案をそのまま入れていたら、通らない経路を試験しているテストが残っていた。**

## 5. 直す

- **修正1件につきテストを1件以上足す**（リポジトリのルールに従う）。
  テストは「直したこと」ではなく**「症状が再発したら落ちること」**を書く
- レビュアーがコード片を提案しているなら、まずそれを試す。
  **変えたほうがよいと判断したら変えてよいが、変えた理由を返信に書く**
- 指摘が文書だけなら、テストは要らない。そう返信に書く
- **指摘の範囲を超えて直さない。** ついでに目についたものは、返信で触れるだけにする

## 6. 回帰テストを流す

リポジトリの回帰テストを走らせ、**最終行を控える。** 落ちた状態で返信しない。
件数が増えたなら、増えたぶんの内訳（どの指摘のぶんか）も控える。

## 7. コミットして push する

- コミットメッセージの先頭は、そのリポジトリの規約に従う（Issue 番号など）
- **1コミットのPRなら `--amend`、複数コミットなら追加コミット**が読みやすい。
  迷ったら追加コミットにする（レビュアーが差分を追いやすい）
- `--amend` や rebase をしたら `git push --force-with-lease`。
  **force-push すると、行に紐づいたレビューコメントが outdated 扱いになることがある。**
  返信でそのことに触れる

**マージはしない。** クローズもしない。判断はユーザーに返す。

## 8. 返信コメントを起票する

```bash
gh pr comment <N> --body-file <file>
```

この順で書く。**表が先。** レビュアーが最初に知りたいのは「全部見たのか」であって、
個々の説明ではない。

````markdown
## レビュー対応（PR #<番号>）

<何に対応し、何を見送ったかを1〜2行。コミットのハッシュも。>

| # | 重要度 | 指摘 | 対応 |
|---|---|---|---|
| 1 | 🟡 | <レビュアーの言葉のまま短く> | **対応** |
| 2 | 🟡 | ... | **見送り**（理由は下） |
| 3 | 🔵 | ... | **<選んだ案>** |

---

### 1. <指摘の見出し>

<何をしたか。>

```
<再現 → 修正後の出力。コマンドごと貼る>
```

<足したテストの名前と、それが何を防ぐか。>

### 2. <見送った指摘>

**再現しませんでした。** <試したことと、その結果。>

---

### 回帰テスト

```
<最終行をそのまま>
```

<増えた件数の内訳。>
````

- **指摘の番号と表の番号を揃える。** レビュアーが照合できる
- 見送りは、**レビュアーを否定せず事実だけ**書く。「間違っています」ではなく
  「この経路では通りませんでした」
- 判断待ちの結果は、**誰が決めたか**が分かるように書く（「案1を採りました」）

## 落とし穴

- **指摘が古いことがある。** 対象PRが更新されていれば、指摘の行番号はずれている。
  行番号ではなく**内容**で当該箇所を探す
- **レビュアーの提案コードをそのまま貼らない。** 動くか確かめる（§4の実例）
- **`develop` が進んでいると衝突する。** 対応の前に rebase しておくと、
  レビュアーが見る差分がきれいになる。WORKLOG のように全員が先頭へ追記する
  ファイルは、ほぼ必ず衝突する
- **「確認して問題なかったもの」を消さない。** レビュアーがその節を書いているなら、
  そこに挙がった項目は再確認しなくてよいという申し送り。ありがたく使う
- **全部直そうとしない。** 🟢 任意は、直さない判断を返信で示せばよい
