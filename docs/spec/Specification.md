# 1. 概要

## 1.1 目的

長期間保存された大量の写真・動画から、AIを利用して家族の思い出となるメディアを
自動で選び出すシステム。

- 過去10年以上の写真・動画から記念動画を作るための素材抽出
- NAS上のフォトフレームで表示する写真セットの作成
- 家族写真アーカイブの整理

## 1.2 担当する範囲

| 範囲 | 状態 |
|---|---|
| 写真・動画ファイルの検索 | 実装済み |
| メディア情報の取得（EXIF・撮影日時・ハッシュ） | 実装済み |
| 顔検出 | 実装済み |
| 家族の人物識別 | 実装済み |
| 写真の品質評価 | 一部実装（§9） |
| 類似写真の判定 | 未実装（§10） |
| 抽出条件による写真選択 | 一部実装（§11） |
| 指定フォルダへのコピー | 実装済み |

担当しない: 動画編集、写真加工、Web表示。

## 1.3 用語

同じものを別の名前で呼ばない。**文書もコードもこの語彙に揃える。**

| 語 | 意味 |
|---|---|
| **メディア** | 写真または動画のファイル1件。`Media` テーブルの1行 |
| **顔** | 写真から検出された顔1つ。`Face` テーブルの1行 |
| **人物** | 利用者が登録した家族の1人。`Person` テーブルの1行 |
| **割り当て** | 顔を人物に結びつけること |
| **手本** | 手動で割り当てた顔。`match` が判断の根拠に使う |
| **未割当** | まだどの人物にも結びついていない顔 |
| **除外** | 「誰でもない顔」として一覧からも自動割り当てからも外すこと |
| **確定** | 自動割り当てを手動割り当てに昇格し、次回の手本にすること |

# 2. 動作環境と設定

## 2.1 環境

- OS: Ubuntu Linux
- 言語: Python 3.10 以上
- データベース: SQLite
- 非公開リポジトリで管理する

**ローカルPC内で完結する。写真・動画データを外部サービスへ送信しない。**
クラウドAIや外部APIは将来のオプション。

## 2.2 設定ファイル（実装済み）

アプリ設定は **YAML**（#27）。`config/app_settings.sample.yml` を写して使う。

| キー | 意味 |
|---|---|
| `database_path` | SQLite データベースの置き場所 |
| `source_roots` | 走査するメディアの根（**配列**・#24）。1つなら文字列でもよい。古い `source_root`（文字列）も1要素として読む。**入れ子は不可**（§6.5） |
| `output_root` | `select` のコピー先 |
| `rule_path` | 抽出ルールファイル |
| `dlib_model_dir` | dlib の学習済みモデルの置き場所（任意） |

### 探索の順序

**次の順で探し、最初に見つかったものを使う。**

1. 環境変数 `PHOTOARCHIVE_CONFIG` が指すファイル
2. カレントディレクトリの `config/app_settings.yml`
3. リポジトリ直下の `config/app_settings.yml`

3 があるのは、リポジトリルート以外から `photoarchive` を起動しても設定が効く
ようにするため。**設定ファイルのパスを変えるためにソースを編集する必要はない。**
3 が候補に出るのは `pip install -e .`（editable install）のときだけで、
通常のインストールでは「リポジトリ直下」にあたるものが無いので使わない。

見つからない場合・壊れている場合は空の設定として扱い、コマンドは CLI 引数だけで
動く。どこを探したかはログ（`--log-level INFO`）に残る。

抽出ルールも YAML で、既定は `config/rule.yml`（`config/rule.sample.yml` がサンプル）。

**JSON は読まない**（#27・利用者の決定）。形式を1つに揃えるため。

- 古い `config/app_settings.json` だけが残っている場合は、**空の設定として扱いつつ
  WARNING で YAML への変換を促す**。DB のパスが無くて止まるときも、そのことを言う
  （「DB のパスが要る」とだけ言うと、形式が変わったことに辿り着けない）
- `.json` のルールファイルを渡されたら、変換を促して止める
- JSON の中身は YAML として読めるので、**空白で字下げしていれば**拡張子を変えるだけでも移れる
  （YAML はタブを字下げに使えない。読めなかったときの WARNING がタブを名指しする）

dlib のモデルの探索順は §7.7 を参照。

## 2.3 Git 管理から外すもの

生成物と、利用者ごとに異なるものは管理しない。

- `.venv/`、`__pycache__/`、`*.pyc`、`build/`、`dist/`、`*.egg-info/`

# 3. 設計の原則

## 3.1 検出・割り当て・抽出を分ける（実装済み）

```
scan          パスの登録 + 顔検出 + 顔画像/特徴量/スコアの保存 + 消えた行の削除
  ↓
photoarchive-gui   人物の登録 + 検出済みの顔を人物へ手動で割り当て
  ↓
match         手動割り当てを手本に、残りの顔を自動で紐づけ
  ↓
select        ルールに従って抽出しコピー
```

**この順序が設計の核心。検出と割り当てを同じ工程にしてはならない。**
人物が1人も登録されていない段階で自動割り当てを行うと、誰とも分からない顔が
誤った人物に結びつく。旧 `analyze` はこれを犯していたため廃止した（Issue #28）。

一度検出した結果は再利用する。

## 3.2 解析結果は永続データ（実装済み）

解析結果は SQLite に保存し、一時データとして扱わない。

### 顔検出の実施状態

`Media.face_count` が3つの状態を表す。**この区別が差分スキャンの土台。**

| 値 | 意味 |
|---|---|
| `NULL` | 未スキャン |
| `0` | スキャン済みで顔が見つからなかった（**読み込めなかった場合を含む**） |
| `N` | 検出した顔の数 |

読めなかったファイルを `NULL` のままにすると毎回読み直すことになるため、
`0` として記録し、理由はログに残す。

### 再検出する条件

1. 新規ファイル
2. ファイルハッシュの変更
3. 検出器のバージョンの変更（`Media.detector_version` の不一致）
4. `scan --force-rescan` による明示的な指示

### ハッシュ計算の省略

ファイルサイズが一致し、**更新時刻の差が 1.0 秒以内**なら、ハッシュを計算しない。
1秒の許容差は NFS とタイムゾーンの丸めを吸収するため。

ハッシュが同じでも、ファイル属性（更新時刻など）は必ず書き戻す。書き戻さないと、
中身が同じなのに毎回「変わったかもしれない」と判断され、恒久的に全体を読み直す
ことになる。このとき `face_count` などの検出状態には触らない。

### 再スキャンは手動の割り当てを破棄する

**ハッシュが変わったメディアは、手動で割り当て済みの顔も含めて顔を作り直す。**
中身が別物になった以上、座標も特徴量も無効なため。削除時は WARNING をログに残す。

GUI での割り当ては人手のかかる作業なので、この挙動は意図的に目立たせている。

```

     |
     v

     |
     v

     |                 match（残りの顔を自動割り当て）
     v <--------------------+

     |
     v

```

# 5. CLI リファレンス（実装済み）

すべてのコマンドは `photoarchive <サブコマンド>`。
`--db` などを省いたときは §2.2 の設定ファイルから補う。

| サブコマンド | 役割 |
|---|---|
| `init-db` | データベースを作る |
| `migrate` | 旧スキーマのデータベースを移行する |
| `convert-heic` | HEIC/HEIF を JPEG へ変換する |
| `scan` | メディアを登録し、顔を検出する |
| `reembed` | 保存済みサムネイルから顔の特徴量だけを作り直す |
| `match` | 未割当の顔を自動で人物へ紐づける |
| `unassign-auto` | 自動割り当てを取り消す（手本と除外は残す） |
| `evaluate` | 手本を使って `match` の取りこぼし率と誤一致率を実測する |
| `select` | ルールに従って抽出しコピーする |

GUI は別の実行ファイル `photoarchive-gui`。

## 5.1 共通

| 引数 | 既定 | 意味 |
|---|---|---|
| `--db` | 設定ファイルの `database_path` | データベースのパス |
| `--log-level` | `WARNING` | `DEBUG` / `INFO` / `WARNING` / `ERROR` / `CRITICAL`（`scan` / `match` / `evaluate`） |

**`convert-heic` はデータベースを使わないので、`--db` も設定ファイルも要らない。**

## 5.2 `scan`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--source` | 設定の `source_roots` → **DB に記録された根**（§6.5） | 走査するディレクトリ。**何度でも書ける**（`--source A --source B`）。書けば設定より優先 |
| `--workers` | `min(4, CPU数 - 1)` | 顔検出のワーカープロセス数 |
| `--no-prune` | off | 実体が無くなったメディアの行を消さない |
| `--force-prune` | off | 安全弁（§6.2）を越えても消す |
| `--force-rescan` | off | 全件の顔を検出し直す |
| `--allow-missing-embeddings` | off | 顔特徴量のモデルが読めなくても続行する。`detector_version` を書かないので、モデル設置後の通常の `scan` が自動でやり直す |

ログは `data/logs/scan_<日時>.log`。

**モデルが読めない状態で走らせない。** 特徴量が全件 `NULL` のまま
「スキャン済み」として記録されてしまう。`scan` は開始時にこれを確かめて中断する。

`--allow-missing-embeddings` を付けて続行した場合、そのメディアには
**`detector_version` を書かない**（`face_count` と `face_scanned_at` だけ記録する）。
版を NULL のまま残すことで、モデルを設置したあとの通常の `scan` が自動で
検出と特徴量生成をやり直す。版を書いてしまうと差分判定が「版が一致する」と
見なして全件スキップし、`--force-rescan` 以外に回収手段が無くなる。
そして `--force-rescan` は**手動割り当てを巻き添えにする**（§3.2）。

## 5.3 `reembed`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--yes` | なし | 確認を省く |
| `--dry-run` | なし | 件数と見積り時間だけを出し、**データベースに書かない** |
| `--limit` | なし | 先頭 N 件だけ作り直す（動作確認用） |

**特徴量モデルを替えたときに使う。** `Face.embedding` と `Face.embed_version`
だけを書き換える。

**なぜ `scan --force-rescan` ではないのか。**

| | `scan --force-rescan` | `reembed` |
|---|---|---|
| 顔の行 | **消して作り直す** | そのまま |
| 手動割り当て・除外・年齢 | **消える** | **残る** |
| 元写真 | 全件読む（実データで 441GB / NFS 24MB/s） | **読まない** |
| 顔画像の出どころ | 元写真 | **`Face.thumbnail`**（実データで 269MB） |
| 実データでの所要 | 10時間 | **約158分**（実測 162ms/件 × 58,606 件） |

- **対象は「版が古い顔」。** `embed_version` が今のモデルと違うものだけを拾うので、
  **途中で止めても続きから再開できる**（塊ごとに確定する）
- **サムネイルの短辺が `EMBED_MIN_FACE_PX`(60px) 未満の顔は作り直さない。**
  小さすぎる顔を 112x112 へ引き伸ばすと中身の無い特徴量ができ、誤った紐づけの
  種になる。実データでは 443 件（0.76%）が該当し、**版が古いまま残るので
  照合の対象からも外れる**
- **並列化していない。** `onnxruntime` が1件の推論で既に全コアを使い、`scan` の
  並列はワーカーが親の SQLite 接続を複製して**実データのDBを壊した**（§6.4）

実行したあとは `match` をやり直す（手本の特徴量も作り直されているため）。

## 5.4 `match`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--threshold` | **`0.45`** | 顔特徴量の距離の上限。小さいほど厳しい |
| `--margin` | **`0.08`** | 2位の人物との距離差の下限 |
| `--no-reset` | off | 既存の自動割り当てを取り消さない |
| （引数なし） | — | **誕生日で候補を絞る**（§8.3）。切る引数は用意していない |
| `--dry-run` | off | 書き込まずに件数と距離の分布だけ出す |

ログは `data/logs/match_<日時>.log`。

**GUI からも流せる**（§5.10。左下の `自動割り当て（match）を実行…`）。既定の閾値と
マージンで、自動割り当てを付け直す（`--no-reset` と `--dry-run` は端末だけ）。
**流す前に控えを取るかを毎回選べる。既定は取る**（`db.backup_to`。WAL も取り込む）。

**進み具合は工程の境目でも知らせる。** 取り消しと手本の読み込みが実データで
約5秒かかり、知らせないと GUI の窓が固まって見える（GNOME は5秒で「応答なし」と
出す）。境目で知らせたあとの最長の空白は約2.6秒（2026-10-09 実測・複製で）。

**流す前に手本の見え方を測る**（§8.3。未計測の手本だけ。初回は手本1万件で約3分、
2回目からは差分だけ）。**付けたばかりの自動割り当ての顔も測る**（`family_score` が
見え方を使うため。§9.2）。実データの複製で、初回は 3分35秒・2回目は 28秒
（2026-10-09）。

`--dry-run` は「いま `match` を実行したらどうなるか」を示す。自動割り当てを
取り消さないので、**取り消し後の状態を再現するために `auto` の顔も候補に含める。**
含めないと2回目以降の dry-run が空振りして、`--threshold` を決める目安にならない。

## 5.5 `unassign-auto`

**自動割り当て（`assign_source='auto'`）だけを取り消す。**
手本（`'manual'`）・除外（`'rejected'`）・年齢（`Face.age`）には触らない。

| 引数 | 既定 | 意味 |
|---|---|---|
| `--person` | （全員） | 人物の名前か id。その人物の自動割り当てだけを消す |
| `--dry-run` | off | 書き込まずに件数だけ出す |

**`match` の結果が信用できないときに、いったん無かったことにするための口。**
`match` は手本と閾値だけで結果が決まるので、**手本を直してから流し直せば付け直せる**
（実データで約6秒）。

- **`family_score` を数え直す。** 取り消しただけだと、もう存在しない自動割り当てから
  計算されたスコアが `AnalysisResult` に残り、`select` の `family_only` が
  その古い値で写真を選ぶ
- **`--person` の名前が見つからない／同じ名前が複数いるときは中断する。**
  絞り込みが黙って無視されると、1人ぶんのつもりで全員ぶんが消える。
  `Person.name` に UNIQUE 制約はまだ無い（§Phase 3 手順7）

## 5.6 `evaluate`

手動割り当ての顔を正解とみなして、`match` の**取りこぼし率**と**誤一致率**を
同じ土俵で測る。**データベースには書かない（読み出しのみ）。**

| 引数 | 既定 | 意味 |
|---|---|---|
| `--thresholds` | `0.3,0.35,0.4,0.45,0.5,0.55,0.6` | 試す閾値をカンマ区切りで指定する |
| `--margin` | **`0.08`** | 2位の人物との距離差の下限。`match` と同じ意味 |
| `--keep-same-media` | off | 同じ写真に写る同一人物の顔も手本に残す |

ログは `data/logs/evaluate_<日時>.log`。測り方は §8.5。

## 5.7 `migrate`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--backup` | `<db>.bak-<日時>` | バックアップの置き場所 |
| `--no-vacuum` | off | 移行後の VACUUM を省く |
| `--yes` | off | 確認を省く |

## 5.8 `select`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--rule` | 設定ファイルの `rule_path` | ルールファイル（YAML） |
| `--output` | 設定ファイルの `output_root` | コピー先 |
| `--source` | 設定の `source_roots` → DB に記録された根 | 出力の相対パスの基準。何度でも書ける。**それを含む根からの相対**でコピーし、根の名前は挟まない（同じ名前は連番で避ける）。どの根にも入らないメディアはファイル名だけ |

**家族写真としての良さで並べる**（§9.2・§12.1）。**その場で、いまの割り当てから
計算する**（保存済みの `family_score` を読まない。GUI で直した結果がすぐ効く）。
見え方が未計測の家族の顔は先に測る。

**古い規則で付いた自動割り当てが残っていれば知らせる**（`Face.assign_rule` が
`matcher.MATCH_RULE` と違うもの）。`select` は `match` の判定をそのまま使うので、
規則を変えたあと `match` を流し直していないと、古い判定で写真を選ぶことになる。

## 5.9 `convert-heic`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--source` | 設定の `source_roots` | 変換するディレクトリ（再帰）。何度でも書ける |

## 5.10 `photoarchive-gui`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--db` | 設定ファイルの `database_path` | データベースのパス |


### 画面は1枚。左の一覧が「いま何を見ているか」

**人物の一覧と表示の切り替えを同じ一覧にまとめる。** 以前は表示が combo、
割り当て済みの確認が**別ウィンドウ**だった。未割当の割り当てと割り当て済みの
見直しは同じ作業の表裏なのに、画面が分かれていて**開き直しの往復**が要った。

| 左で選ぶもの | 右に出るもの | 既定の並び |
|---|---|---|
| `未割当` | まだ誰にも割り当てていない顔 | 撮影日時の新しい順 |
| `自動割当` | `match` が自動で割り当てた顔。**全員ぶん** | **確信度の低い順** |
| `除外済み` | 「誰でもない顔」として外した顔 | 撮影日時の新しい順 |
| **人物** | **その人物に割り当て済みの顔**（旧「割り当て済みを確認」） | 年齢の若い順 |

- 左の一覧には**残っている件数**を出す（`db.face_counts` が**1回の問い合わせ**で
  数える）。手作業の量が精度の上限なので、**減っていくのが見えること自体が
  作業の支えになる**
- **表示の3行はドラッグで動かさない。** 並べ替えは人物の `display_order` だけ
- **表示を切り替えたときだけ、並びをその表示の既定へ戻す。** 同じ表示を見ている
  あいだに戻すと、選んだ並びが勝手に変わる

### 絞り込みは2段に分ける

| 段 | 出すとき | 中身 |
|---|---|---|
| 共通 | **常に** | 並び順 / **撮影年月の範囲** / **撮影日時なしのみ** / 行事 / ページャ |
| 人物向け | **人物を選んでいるときだけ** | 種別 / 年齢の範囲 / 年齢不明も含める |

| 絞り込み | 値 |
|---|---|
| 並び順 | 撮影日時の新しい順・古い順 / 年齢の若い順・高い順 / **自動の確信度が低い順**・高い順 / 画質の高い順・低い順 / **この人物に似た順・似ていない順**（人物のみ） |
| **撮影年月の範囲** | `いつから` 〜 `いつまで`（**両端を含む**・片方だけでもよい）。選択肢は**顔のある写真の月だけ**・新しい順 |
| **撮影日時なしのみ** | **EXIF の無い写真だけ**を見る指示（フォルダ名から推測した撮影時期がある写真も入る）。範囲とは別の問いなので**併用しない**。推測した区間が範囲にまるごと入る写真は、範囲の側にも出る（§8.4.1） |
| 行事 | フォルダ×日（`行事を選ぶ`） |
| 種別（人物のみ） | すべて / 確定済みのみ / 自動のみ / **未割当** / **この人物ではない** |
| 年齢（人物のみ） | 下限と上限。`0` は 0歳、「指定なし」はその1つ下 |

**並びは向きを対にする**（#69。利用者「高い順という選択があるなら低い順もあるべき」）。
**値を持たない顔（撮影日時・年齢・確信度・画質が無い）は、どちらの向きでも最後。**

### 人物に似た順（顔候補の自動推薦・#69）

**人物を選び、種別を `未割当` にすると、未割当の顔がその人物に似た順に並ぶ**
（並びの既定がこの順になる）。本人を目で探さずに済ませるためのもの。

| 項目 | 決めごと |
|---|---|
| 点 | **その人物の手本との最小距離**（尺度は `embedding.ACTIVE`）。閾値では切らない |
| 手本 | いまのモデルの版（`embed_version`）のものだけ。**5点整列ができなかった手本は使わない。** 未計測の手本は**使う前に測って DB に残す**（`matcher.teacher_usable`。GUI で割り当てた手本は `match` まで未計測のため） |
| 候補から外す顔 | **誕生前の写真**（撮影時期が分からない顔は外さない。EXIF が無ければフォルダ名の区間で見て、区間の終わりまでに生まれていないときだけ外す。§8.4.1）・**その人物について「この人物ではない」と記録した顔** |
| 年齢の範囲 | 人物向けの年齢の範囲も効く（その人物がその年齢だった時期の写真に絞られる） |
| 距離を出せない顔 | 特徴量が無い・版が違う顔は、**どちらの向きでも最後** |
| 自分自身 | 確定済み・自動の顔を並べるときは、**自分を手本から外して測る** |
| 手本が0件 | ページの表示に「手本が無いので似た順に並べられない」と出し、id 順 |
| 計算 | 人物ごとに距離を覚え、**ページ送り・絞り込みの変更では計算し直さない**（測っていない顔の分だけ測る）。**手本が増えたら増えた分とだけ比べる**、減ったら全部測り直す（`recommend.PersonSimilarity`） |

- 未割当以外の種別でも選べる。**似ていない順**は、割り当てや手本の誤りを探す並びになる
- 種別 `未割当` の右クリックは `この人物ではない` と `誰でもない顔として除外…`。
  割り当て先は `人物に割り当て`（1〜9）から選ぶ。行事のまとめ処理は無い
- 比べる人物が居ない表示（未割当・自動割当・除外済み）では選べない（理由をツールチップに出す）

**年齢は人物向けだけに出す。** 誕生日が無いと計算できないので、全体の表示では
意味を持たない（`Face.age` は実データで割り当て済み 22,511 件のうち 126 件だけ。
2026-10-07）。

**絞り込みの引数は、一覧（`list_faces`）・件数（`count_faces`）・まとめて処理
（`face_ids`）の3つに同じものを渡す。** 1つだけ受け取れないと、**画面に出ている
顔と処理の対象がずれる**（実際に `face_ids` が撮影年月を受け取れておらず、
年月で絞った状態で行事のまとめ処理を押すと落ちていた。#67 で修正し、
引数の揃いをテストで見張る）。

**撮影年月の範囲は、家族の写っていない時期をまとめて片付けるためのもの。**
結婚式・旅行先の他人などは時期でまとまっているので、その期間だけを開いて
`この顔を除外` でまとめて外せる。

**上下が逆転したら押し戻す。** 黙って0件にすると、絞り込みが壊れているように見える。

**読めない撮影日時を月として扱わない**（`month_expression`）。
`substr(shooting_date, 1, 7)` と書くと「TTTT-TT」という月が一覧に並ぶ。

### `match` を画面から流す

左下の `自動割り当て（match）を実行…`。確認の窓（**既定のボタンは「やめる」**・
**控えを取るかのチェック、既定は取る**）→ 進み具合（件数）→ 結果（割り当てた件数・
人物ごと・控えの場所）。終わったら左の一覧の件数を出し直す。

**別のスレッドに出さない。** このリポジトリの重い処理と同じく `WorkProgress` が
通知のたびにイベントを回す。スレッドに出すと SQLite の接続を2本持つことになり、
その間に画面から書き込めてしまう。

### 控えはファイルを複写しない

**`db.backup_to`（SQLite の backup。`sqlite3 .backup` と同じ）で取る。** この DB は
WAL で動いているので、確定した書き込みがまだ ``-wal`` にだけあることがあり、
**本体のファイルを複写するとその分が控えから黙って抜ける。** 移行の前の控え
（`migration.backup_database`）も `shutil.copy2` だったので同じ作りに直した（#67）。

### 顔への操作は、右クリックのメニューと打鍵に集める

**ボタンは置かない。** 見ている表示によって意味のある操作が変わるので、ボタンで
並べると**表示の数だけ増え、押せないボタンが画面に残る。**

| 見ているもの | 出す操作 |
|---|---|
| 未割当 | 人物に割り当て ▸ / 誰でもない顔として除外 |
| 自動割当 | 手本に確定 / 未割当に戻す / この人物ではない / 誰でもない顔として除外 / 人物に割り当て ▸ |
| 除外済み | 未割当に戻す / 人物に割り当て ▸ |
| 人物 | 手本に確定 / 割り当てを解除 / この人物ではない / 誰でもない顔として除外 / 年齢を設定 / 別の人物に割り当て ▸ |
| 人物（種別＝この人物ではない） | 「この人物ではない」を取り消す |

| 打鍵 | 操作 |
|---|---|
| `1`〜`9` | **左の一覧の並び順で**その人物に割り当て（10人目からは数字を振らない） |
| `C` / `U` / `N` / `X` / `G` / `Z` | 確定 / 未割当に戻す / この人物ではない / 誰でもない顔 / 年齢を設定 / 否定の取り消し |
| `Ctrl+→` / `Ctrl+←` | 次 / 前のページ |

- **打鍵は顔の一覧に焦点があるときだけ効く**（`WidgetWithChildrenShortcut`）。
  年齢の入力欄で数字を打ったときに割り当てが走っては困る
- **メニューと打鍵は同じ `QAction` を使う。** 別々に作ると、押せる条件がずれる
- **右クリックした顔が選ばれていなければ、その顔を選び直す**（選択と違う顔を
  処理しては困る）。すでに選ばれている顔なら選択を崩さない
- **一覧の下に、いま効く打鍵と選択件数を出す。** 右クリックは目に見えないので、
  出さないとボタンを消したぶんが「機能が無くなった」に見える
- **割り当て先はメニューが持つ。** 左の選択は「見るもの」なので、未割当を見ながら
  別の人へ振るたびの往復が要らない。以前は左で選択中の人物へ割り当てており、
  選択が外れていると「先に人物を選択してください」で止まっていた
- **割り当てメニューの人物名には、選んだ顔の撮影時の年齢を添える。** 年齢が揃う
  ときだけ出す（`suggested_age`）。**誕生前の写真が混ざっていたら `⚠誕生前の写真
  あり` と出す**（`match` は誕生日で候補を外すので、この矛盾を作れるのは手作業
  だけ）。**選べなくはしない** — 1件混ざった選択を丸ごと止めると、なぜ割り当て
  られないのかが分からない
- **「誰でもない顔」の確認は、割り当て済みに押すときだけ出す。** 未割当では毎件
  通る操作で、そこに確認を挟むと**作業そのものが遅くなる**（1件あたりの手数が
  総時間）

**年齢の出し方は2通りあり、見た目で区別する。**

| 表示 | 何の値か |
|---|---|
| `7歳` | **`Face.age`**。人が確かめて入れた値 |
| `(7歳)` | **誕生日と撮影日時から計算した値。**括弧つき |
| `(7歳?)` | **EXIF が無く、フォルダ名から起こした撮影時期で計算した値**（§8.4.1） |
| `(誕生前)` | 撮影日が誕生日より前。**誤割り当ての強い手がかり** |
| （何も出ない） | 誕生日が未登録か、撮影時期が分からない（フォルダ名の区間の途中に誕生日がある場合も） |

**`match` は `Face.age` を書かない**ので、自動割り当ての顔は年齢が未設定のまま。
**自動割り当てが正しいかを人が見るとき、撮影時の年齢がいちばん効く手がかり**なので、
未設定なら計算して出す。**計算値を `Face.age` に書き戻さない**（§8.4 と同じ理由で、
人が確かめた値かどうかが区別できなくなる）。

**年齢の絞り込みも、この表示と同じ規則で見る。** `Face.age` が入っていればその値、
無ければ計算した年齢。**`Face.age` だけを見ると絞り込みが働かない** — 実データでは
割り当て済み 22,511 件のうち `Face.age` が入っているのは **126 件だけ**（2026-10-07）で、
`match` は年齢を書かないため。計算のほうは**撮影日の範囲**に読み替えて絞る
（SQL に年齢の計算を持ち込まないため）。EXIF の無い顔は、**フォルダ名から起こした
区間が年齢の範囲にまるごと入り、年齢が1つに決まる**ときだけ当たる（§8.4.1）。

**撮影年月の絞り込みも、EXIF の無い顔はフォルダ名の区間がまるごと範囲に入るときだけ**
当てる（「2012年」までしか分からない顔は、2012年10月だけを見たいときには出さない）。
`撮影日時なしのみ` は **EXIF の無い顔**（推測した区間があっても入る）。

**年齢を出せない顔**（誕生日が未登録、または撮影日時が読めない）は、
範囲を指定すると**既定で外れる**。「7〜9歳」に、年齢の分からない顔は入るとは言えないため。
`年齢不明も含める` で戻せる。

**「選択した顔を確定」は、選択に自動割り当てが1件も無ければ押せない。**
確定は `assign_source` を `'auto'` → `'manual'` へ上げる操作なので、すでに手本の顔に
押しても `assigned_at` が書き換わるだけで意味のある変化が起きない。
押せてしまうと「何かが起きた」と誤解する。

## 5.11 進捗表示

`scan` / `match` / `evaluate` / `convert-heic` / `select` は2行の進捗を出す。1行目が進捗バー、
2行目が**直近のエラー**。エラーが出なかった回で `Error: none` に戻さない
（戻すと、流れていく表示の中でエラーが一瞬しか見えない）。

# 6. メディアの走査（実装済み）

## 6.1 やること

- 指定ディレクトリ以下を再帰的に検索する
- 写真・動画を見つける（`jpg` `jpeg` `png` `heic` `heif` / `mp4` `avi` `mov` `mkv`）
- ファイル情報を取得する（サイズ、更新時刻、EXIF の撮影日時）
- ハッシュを生成する（§3.2 の条件で省略する）
- 顔を検出し、顔画像・顔特徴量・スコアを保存する
- 既に顔検出済みのメディアは再検出しない
- データベースにあるが実体が無くなったメディアの行を削除する
- 走査し終えた根を `ScanRoot` に記録する（§6.5）

**走査は人物への割り当てを一切行わない。**

`Media.type` の値域は `"image"` / `"video"`。

**動画は先頭の1フレームだけを解析する。** 全フレームを見るのは費用に見合わない。

## 6.2 安全弁

未マウントのディレクトリを走査して全件削除する事故を防ぐため、2つの中断条件を持つ。

1. **メディアが1件も見つからない場合**は中断する
2. **実体が無いメディアが、走査ルート配下の登録数の 20% を超える場合**は中断する。
   意図した削除なら `--force-prune` を付ける

母数は**走査ルート配下に限る**。`--source` で年フォルダ1つだけを走査したときに、
他のフォルダの登録件数が母数に混ざらないようにするため。**根が複数あれば根ごとに
判定する**（片方の根が未マウントでも、もう片方のメディアは削除候補にならない）。
1つの根で中断したら、残りの根は走査しない。

## 6.3 HEIC の扱い

- `convert-heic` で JPEG へ変換できる（品質 95、元ファイルは変更しない）
- `scan` は **HEIC を直接読める**（`pillow_heif` のデコーダを登録している）

**未決**: `convert-heic` の後は `photo.heic` と `photo.jpg` が両方登録され、
同じ顔が二重に検出される。ハッシュが違うので重複排除も効かない。
どちらを正とするかは Issue #26 で決める。

## 6.4 並列実行（実装済み）

`--workers` が2以上のとき、顔検出を別プロセスで並列に行う。**DBへの書き込みは
親プロセスだけが行い、ワーカーはファイルを読んで結果を返すだけ。**

### ワーカーは `fork` で起こさない

`scanner.WORKER_START_METHOD = "spawn"`。**これを `fork` に戻してはならない。**

`scan` はDB接続を開いたままプールを作るため、`fork` だと全ワーカーが親の
SQLite 接続と WAL の共有メモリを複製して持つ。ワーカー自身はDBに触らないが、
**子プロセスの終了時に、引き継いだ接続の後始末が親の書き込みと競合する。**
SQLite は接続を `fork()` をまたいで持ち越すことを禁じている。

実データ 64,974 件のスキャンで2回とも
`row N missing from index idx_media_hash` が出て、`scan` が
`database disk image is malformed` で異常終了した（Issue #35）。
`--workers 1`（プールを作らない経路）では起きない。

**数万件規模でしか再現しないので、壊れないことはテストで確かめられない。**
代わりに「`fork` で起こしていないこと」と「子が親のメモリ状態を引き継がない
こと」をテストで固定している。

### 引き継がれないもの

`spawn` の子は白紙のインタプリタとして始まる。親が `sys.modules` へ差し込んだ
ものも、monkeypatch も、モジュール変数の値も引き継がれない。dlib のモデルは
ワーカーごとに読み込まれる（4ワーカーで +800MB 程度）。

**ログの設定も引き継がれない。** 張り直さないと、子が出した警告は `logging` の
lastResort 経由で書式なしの stderr へ漏れ、**ログファイルには1行も残らない。**
`--workers` の既定は2以上なので、放っておくと実運用の経路で
「どのファイルがなぜ読めなかったか」の記録が丸ごと消える。

そこでワーカーの入口（`scanner._start_worker`）で `logging_setup.setup_logging`
を呼び直す。`scan_directory` は `log_file` / `log_level` を受け取り、それを子へ渡す。
**ログ設定の実体を `cli.py` ではなく `logging_setup.py` に置いているのはこのため。**
子から `cli` を import すると、循環参照と CLI 一式の読み込みコストを毎ワーカー抱える。

## 6.5 複数の根と、根の記録（実装済み・2026-10-10・#24）

実データは根が2つある（`${SURNAME}/Photo` と `person2Temp/${PERSON_2}携帯`。2026-10-02 に数えた）。

- **根ごとに順に走査する**（`scanner.scan_directories`）。書いた順
- **入れ子の根は止める。** 共通の親（`${NFS_ROOT}`）で走査すると他家の写真
  （`katayama`）や `temp` まで入る。親を根にすること自体が事故なので、気づけるように止める
- 根は実体のパスにそろえる（`Media.path` と同じく symlink を解く）
- **どの根も走査する前に、すべての根があるかを確かめる。** 無い根があれば何も走査せずに
  止める（後ろの根の指定ミスに、前の根を走査し終えてから気づかないように）。中身の無い
  マウントポイントは §6.2 の「1件も無い」で止まる

### 根を DB に記録する（v7）

**設定ファイルは git 管理外で、2026-10-02 に失ったとき DB から根を戻せなかった。**
`Media.path` の共通接頭辞で推定すると上の親になり、そのまま走査すると事故になる。

- `scan` が**根を1つ走査し終えるたびに** `ScanRoot` に書く。中断したら書かない
- **既存の根の内側は書かない**（年フォルダだけの `--source` は根の一部のやり直し）
- **記録済みの根を内側に含む根（親）は、走査する前に止める**（利用者の決定）。根を思い出せず
  共通の親を1つだけ渡したときに起きる。入れ子の検査（同じ指定の中の親と子）では止められない
  ので、記録と突き合わせる。以前は親を走査すると記録が親だけに置き換わり、正しい根で走査し
  直しても戻らなかった。**記録は消さない**
- **設定にも `--source` にも根が無ければ、記録された根を使う**（`scan` と `select`）。
  何を使うかを表示する。GUI のフォルダ表示も、設定に根が無ければ記録を使う
- **移行では埋めない**（推定しないため）。次の `scan` が書く

## 7.1 Media

## 7.3 Face

写真から検出された顔。**GUI で登録する「手本の顔」も、この中の
`assign_source = 'manual'` の行として表す。手本専用の行は作らない。**

| 列 | 型 | 制約 |
|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT |
| `media_id` | INTEGER | NOT NULL、`Media(id)` へ FK、`ON DELETE CASCADE` |
| `bbox_top` / `bbox_right` / `bbox_bottom` / `bbox_left` | INTEGER | NOT NULL。**検出器が返した生の矩形**（§7.7） |
| `detection_score` | REAL | 検出器の確信度 |
| `embedding` | BLOB | float32 × 次元数（ArcFace は512。`embedding.ACTIVE.dimensions`）。作れなかった場合は NULL（§7.7） |
| `embed_version` | TEXT | NOT NULL。特徴量の生成規約 |
| `thumbnail` | BLOB | 一覧表示用の小さな顔画像（JPEG） |
| `smile_score` / `quality_score` | REAL | この顔のスコア（§9） |
| `person_id` | INTEGER | `Person(id)` へ FK、`ON DELETE SET NULL`。NULL=未割当 |
| `assign_source` | TEXT | NULL=未割当 / `'manual'` / `'auto'` / `'rejected'` |
| `assign_score` | REAL | 自動割り当て時の類似度 0-100（§8.3） |
| `assigned_at` | TEXT | 割り当てた時刻 |
| `age` | INTEGER | 撮影時の年齢（任意）。**未設定（NULL）と0歳は別の状態** |
| `created_at` | TEXT | NOT NULL |
| `aligned` | INTEGER | **5点整列ができたか**（1/0）。NULL=未計測（v5。§8.3） |
| `yaw` | REAL | 横向きの度合い（鼻のずれ ÷ 両目の間隔。正面で 0）。整列できなければ NULL（v5） |
| `sharpness` | REAL | 鮮明さ（112px にそろえたラプラシアン分散。小さいほどボケ）。NULL=未計測（v5） |
| `assign_rule` | TEXT | **自動割り当てを付けた規則の版**（`matcher.MATCH_RULE`）。`'auto'` の行だけが持つ（v5。§5.8） |

**`aligned` / `yaw` / `sharpness`（見え方）は保存済みサムネイルから測る**
（`appearance.py`。元写真は読まない）。測るのは**割り当てのある顔だけ**で、
`match` と `select` が使う前に未計測の分を埋める。**目印の検出器が無い環境では
書かない**（「測れない」と「整列できなかった」を混ぜない。混ぜると全部の手本が
根拠から外れ、しかも二度と測り直されない）。

### `assign_source` を区別する理由

- **自動割り当ての手本に使ってよいのは `'manual'` だけ。** `'auto'` を手本に
  混ぜると、誤った割り当てが次の判定の根拠になって増幅する
- `'auto'` だけをまとめて取り消せるので、`match` を何度実行しても同じ結果になる
- `'rejected'` を持てるので、誰でもない顔が未割当一覧に残り続けない

## 7.4 AnalysisResult

メディア単位のスコア。顔の数は `Media.face_count` が持つ。

| 列 | 型 | 制約 |
|---|---|---|
| `media_id` | INTEGER | **PRIMARY KEY**、`Media(id)` へ FK、`ON DELETE CASCADE` |
| `family_score` | REAL | `match` が書く。**家族写真としての良さ**（§9.2） |
| `smile_score` | REAL | `scan` が書く |
| `quality_score` | REAL | `scan` が書く |

**`scan` がスコアを書くときに `family_score` を潰してはならない。逆に `match` は
smile / quality を触らない。** `media_id` が主キーなので、どちらも UPSERT
（`ON CONFLICT(media_id) DO UPDATE SET` で自分の列だけ）で書く。

`match` は `family_score` を全行 0.0 に戻してから付け直すため、人物が1人も
登録されていなくても NULL ではなく 0.0 になる。また、GUI で割り当てを解除しても
`AnalysisResult` は更新されないので、**次に `match` を実行するまで `family_score`
は古いまま**である。

**そのため `select` はこの列を読まない**（2026-10-09）。同じ式（§9.2）で、いまの
割り当てからその場で計算する。この列は `match` の結果の記録として残している。

## 7.5 FaceRejection

**「この顔はこの人物ではない」という否定の記録**（2026-10-08 追加）。

| 列 | 型 | 制約 |
|---|---|---|
| `face_id` | INTEGER | `Face(id)` へ FK、`ON DELETE CASCADE` |
| `person_id` | INTEGER | `Person(id)` へ FK、`ON DELETE CASCADE` |
| `created_at` | TEXT | NOT NULL |

**主キーは `(face_id, person_id)`。** 1つの顔が複数の人物を否定できる。
同じ組を2度記録しても増えない（`ON CONFLICT DO NOTHING`）。

**`Face.assign_source='rejected'` とは別物**（§8.3 の表）。あちらは「誰でもない顔」で
`match` の候補から顔ごと外れるが、こちらは**その人物だけ**を候補から外す。
**兄弟の赤ん坊の顔は互いによく似ており**、未割当へ戻すだけでは `match` を流すたびに
同じ誤りが戻る。

**この表は新規なので、既存DBへの移行は要らない。** `create_tables` の
`CREATE TABLE IF NOT EXISTS` が開いた時点で作る（`idx_media_event` と同じ扱い）。
**`PRAGMA user_version` は変わらない**（列を足していないので `missing_columns` も
反応しない。§7.8）。

## 7.6 インデックス

| 名前 | 対象 |
|---|---|
| `idx_media_hash` | `Media(file_hash)` |
| `idx_media_type` | `Media(type)` |
| `idx_media_unscanned` | `Media(id) WHERE face_count IS NULL` |
| `idx_face_media` | `Face(media_id)` |
| `idx_face_person` | `Face(person_id)` |
| `idx_face_manual` | `Face(person_id) WHERE assign_source = 'manual'` |
| `idx_face_unassigned` | `Face(quality_score DESC, id) WHERE assign_source IS NULL` |
| `idx_media_shooting` | `Media(<読める撮影日時> DESC, id)` — **式インデックス** |
| `idx_media_event` | `Media(<フォルダ>, <読める撮影日時の日付>)` — **式インデックス** |

`idx_face_unassigned` が §10.4 の「品質スコア降順のページング」を成立させている。
部分インデックスが参照する列は SQLite では `DROP COLUMN` できないため、
移行はテーブル再構築方式をとる（§7.8）。

`idx_media_shooting` は §10.4 の「撮影日時の新しい順」を成立させている。
**式インデックス**で、`db.SHOOTING_DATE_SORT_KEY`（日付として読める
`shooting_date` だけを返し、読めなければ NULL）に対して張る。

- **`ORDER BY` に同じ式を書かないと索引が使われない。** 定数を1つ持ち、
  索引の定義と問い合わせの両方でそれを使う
- 問い合わせは `Media m CROSS JOIN Face f` の順にする。**`CROSS JOIN` は結合の
  順序を固定するためのもの**で、直積を作るわけではない。外すと SQLite が
  `Face` を外側に選び、ページを送るたびに未割当の顔を全件並べ直す

| 実データ（未割当 58,547 件）での1ページの読み出し | 索引なし | 式インデックス＋`CROSS JOIN` |
|---|---|---|
| 1ページ目 | 219ms | **0.7ms** |
| 100ページ目 | 361ms | **68ms** |
| 最終ページ付近 | 436ms | **197ms** |

**`ANALYZE` を実行しないこと。** 統計があるとブルームフィルタを挟む計画に
変わり、1ページ目が 0.7ms → 47ms に落ちた（2026-09-20 実測）。

`idx_media_event` は §10.4.1 の「行事（フォルダ×日）で絞る」を成立させている。
こちらも**式インデックス**で、`db.folder_expression()` と `db.day_expression()`
に対して張る。無いと、ページを送るたびに `Media` を全件走査する。

- **フォルダだけの索引は別に張らない。** 複合索引の先頭列がフォルダなので、
  フォルダだけの絞り込みもこれで足りる
- **移行は要らない。** `CREATE INDEX IF NOT EXISTS` なので、既存のデータベースを
  開いた時点で張られる（`PRAGMA user_version` は変わらない）
- 行事で絞ったときは `ORDER BY` が索引から外れる（`USE TEMP B-TREE FOR ORDER BY`）。
  1行事に絞ったあとの並べ替えなので、それでも1ページ 0.014 秒で収まる

## 7.7 特徴量の生成規約

**2026-10-02 に dlib ResNet から ArcFace へ替えた。** 実データの手本126件で
1位正解率 **69.8% → 95.2%**、行事をまたぐ分離 **+0.033 → +0.418**。
測定は [../history/details/2026-10-02-embedding-model-comparison.md](../history/details/2026-10-02-embedding-model-comparison.md)。

### モデルの記述は1か所に持つ

次元数・距離尺度・閾値・版の文字列は `photoarchive_ai/embedding.py` の
`EmbeddingModel` が持ち、`db` / `matcher` / `scoring` / `face` はそこを見る。
**定数を書き写さない**（以前は4つのモジュールに散っていて、モデルを替えると
どれか1つが古いまま残る形だった）。

| | dlib ResNet（2026-10-02 まで） | **ArcFace（いま）** |
|---|---|---|
| `version` | `dlib_resnet_v1/sp5/pad0.25/full` | `arcface_w600k_r50/5pt/112` |
| 次元数 | 128 | **512** |
| 距離尺度 | ユークリッド | **L2 正規化後のコサイン** |
| `match` の閾値 / マージン | 0.4 / 0.05 | **0.45 / 0.08** |
| 類似度の基準距離 | 0.6 | **1.0** |
| 1位正解率（実データ） | 69.8% | **95.2%** |

**閾値の選び方はモデルを替えても同じ。** 「行事をまたぐ別人のペアを 1% 程度しか
誤らない」点を採る（誤った紐づけは手作業でのやり直しが高くつくため、
取りこぼす側に倒す）。既定どうしを比べると、**`evaluate` の正解が 26.9% → 78.6%、
他人誤認率が 0.5〜1.0% → 1.06%**（§8.3 に表がある）。
マージン 0.08 は1位と2位の差の下位10%に当たる。
**どちらも手本126件での暫定値で、手本が増えたら `evaluate` で確定する。**

### 定数

| 定数 | 値 | 意味 |
|---|---|---|
| `EMBED_VERSION` | `embedding.ACTIVE.version` | 特徴量の生成規約。**照合の絞り込みにも使う** |
| `DETECTOR_VERSION` | `mediapipe_fd1` | 検出器のバージョン。**特徴量の版を内包しない** |
| `EMBED_PADDING` | `0.25` | 顔矩形のパディング率（元写真から作るときだけ） |
| `EMBED_MIN_FACE_PX` | `60` | 特徴量を作る最小の辺の長さ |
| `FACE_DETECTION_MAX_SIZE` | `1280` | 検出時に縮小する長辺 |
| `THUMBNAIL_MAX_SIZE` / `THUMBNAIL_QUALITY` | `160` / `85` | 保存するサムネイル |
| `ARCFACE_INPUT_SIZE` | `112` | ArcFace の入力（整列後） |

### 5点整列（ArcFace の前処理）

ArcFace は 112x112 のテンプレートに5点（両目・鼻・両口角）を合わせる前提で
学習されている。**整列を省くと 95.2% → 78.6% に落ちる**（現行 dlib を
サムネイルから作り直した 82.5% にも負ける）。

- 5点は **MediaPipe FaceMesh** から取る（`scoring` と同じものを使うので
  **依存は増えていない**）。目は目尻と目頭の中点
- 変換は Umeyama の閉じた式（`face.similarity_transform`）。**RANSAC を使わない**
  （乱数で揺れると、同じ写真から同じ特徴量が出なくなる）。**鏡像は許さない**
- **目の左右が逆なら口角も一緒に入れ替える**（`face.order_five_points`）。
  MediaPipe の添字の左右と画面の左右は一致する保証がない
- **5点が取れない顔は縮小で通し、件数を数える**（実データの手本126件では14件）。
  捨てると、整列できる顔だけで精度を語ることになる

### `scan` と `reembed` で入力の作り方が違う（2026-10-03 に測って許した）

**同じ版の文字列に、2つの入力規約が同居している。**

| 経路 | 特徴量の入力 |
|---|---|
| `scan` | 元写真から `face_rect`（**25%パディング・元解像度**） |
| `photoarchive reembed`（§5.3） | **サムネイル**（パディング無し・最大160px） |

**5点整列がパディングの違いを吸収する**ので、作り替えていない。実データの
手本126件で、同じ顔を両経路で作って比べた結果。

| 測ったもの | 値 |
|---|---|
| 同じ顔の両経路の距離 | 中央 **0.090** / p90 0.270 / 最大 0.893 |
| **閾値 0.45 を超える顔** | **10 / 126 件（8%）** |
| 1位正解率（手本は reembed 経路） | reembed 問い合わせ **95.2%** / scan 問い合わせ **95.2%** |

**精度は落ちていない。** 一方、**同じ顔なのに距離が閾値を超えてずれる顔が 8%** ある。
**閾値 0.45 と他人誤認率 1.06% は reembed 経路だけで測った数字**なので、
新しく `scan` した顔はこのぶんだけずれる余地がある。

**経路ごとに別の版にはしない。** 照合は版の完全一致で絞るので（下記）、
分けると**新しく scan した顔と reembed した顔が互いに見えなくなる。**

### 照合は同じ版の特徴量だけを見る

**別の埋め込み空間の特徴量を混ぜて距離を取るのは常に誤り。** 次元が違えば
`np.vstack` が落ち、**次元が同じモデル同士なら黙って無意味な距離が出る。**

`db.load_manual_embeddings` と `db.iter_unassigned_embeddings` は
`embed_version` で絞る。`reembed` の途中は必ず混在するので、ここで絞るのが要る。

### 検出器の版と特徴量の版を分ける

以前は `DETECTOR_VERSION = f"mediapipe_fd1/{EMBED_VERSION}"` と連結しており、
**特徴量の規約を変えるだけで `Media.detector_version` が不一致になって再検出が
走った。** サムネイルから作り直せるようになった（§5.3）ので、その必要がない。
**検出結果（矩形・サムネイル）は作り直さない。**

**実データの `Media.detector_version` は 70,297 件すべてが連結された古い形**
（`mediapipe_fd1/dlib_resnet_v1/sp5/pad0.25/full`）。素朴に文字列を変えると
全件が不一致になり、**441GB を NFS（実測 24MB/s）から読み直す。**
比較の側を `face.detector_version_of` で正規化して、古い値と揃えている。

### 矩形の正規化（元写真から作るとき）

検出器が返した矩形を、**正方形にしたうえで長辺を 1.5 倍**（`1 + 0.25 × 2`）に
広げ、画像内へ収める。この処理は1か所（`face.face_rect`）に集約する。

**パディングを安易に変えてはならない。** 実データ950件の顔で
0 / 0.1 / 0.25 / 0.4 / 0.6 を比べたところ、0〜0.25 はほぼ同等で、
0.4 以上は急激に悪化した（0.6 では別人同士の誤一致率が 47〜59%）。
変える場合は **`EMBED_VERSION` を必ず上げる。** 上げないと古い特徴量と混ざって
照合が壊れる。

> **2026-10-02 の測定では、密着側のほうが良かった。** 同じ dlib でも、原寸に
> 0.25 のパディングを付けたもの（69.8%）より、サムネイル（検出矩形の生クロップ）
> から作り直したもの（82.5%）のほうが高い。**ただし解像度と切り出し方を同時に
> 動かした比較なので、`EMBED_PADDING` を下げる根拠にはまだ足りない。**

`Face.bbox_*` に保存するのは**正規化前の生の矩形**。GUI の拡大プレビューと
サムネイルはこちらを使う。

### サムネイルから作り直せる理由

| 測ったもの（実データ 58,606 件） | 値 |
|---|---|
| サムネイルの短辺（中央） | **160px**（ArcFace の入力は 112x112） |
| 112px 未満 | 6.20% |
| 60px 未満（作り直さない） | 0.76%（443件） |
| サムネイルの合計 | **269MB**（元写真は 441GB） |

### `embedding` が NULL になる条件

1. 正規化後の矩形の短辺が `EMBED_MIN_FACE_PX`（60px）未満
2. モデルを読み込めなかった
3. 推論が例外になった

**2 は `scan` と `reembed` が開始時に確かめて中断する**（§5.2 / §5.3）。
`match` は `embedding IS NOT NULL` かつ**版が一致する**顔しか見ない。

### モデルの探索順

**dlib**（`convert-heic` 以外では使わなくなったが、記述は残してある）。

1. 環境変数 `PHOTOARCHIVE_DLIB_MODEL_DIR`
2. 設定ファイルの `dlib_model_dir`
3. `face_recognition_models` パッケージ内の `models/`
4. リポジトリ直下の `models/`

**ArcFace**（`w600k_r50.onnx`）。

1. 環境変数 `PHOTOARCHIVE_ONNX_MODEL_DIR`
2. 環境変数 `PHOTOARCHIVE_DLIB_MODEL_DIR`（同じ置き場にまとめる運用）
3. リポジトリ直下の `models/`

`python scripts/fetch_models.py` で取得する（**sha256 を検証して置く**）。
**アプリからは呼ばない**（`scan` が黙って外部へ通信するのは挙動が読みにくい）。
**`insightface` パッケージは入れない**（モデル動物園と GPU 版 onnxruntime を
引き込むため）。

**`face_recognition` パッケージは import しない。** `face_recognition_models` の
`__init__.py` が `pkg_resources` に依存しており、setuptools 81 以降では
`ModuleNotFoundError` になる（Issue #10 の原因）。モデルのパスは
`importlib.util.find_spec` で取り出す（モジュールを実行しないので踏まない）。

## 7.8 スキーマのバージョンと移行

**現在のスキーマ版は 7。** `PRAGMA user_version` で管理する。

`photoarchive migrate` が旧スキーマから移行する。**版ごとにやることが違う。**
一括りに「移行」と呼ばない。

| 移行 | 中身 | 失われるもの |
|---|---|---|
| **v1 → v2** | テーブル再構築 | `Face` と `AnalysisResult`（下記） |
| **v2 → v3** | `ALTER TABLE Person ADD COLUMN birth_date TEXT` | **なし** |
| **v3 → v4** | `ALTER TABLE Person ADD COLUMN display_order INTEGER` | **なし** |
| **v4 → v5** | `Face` に `aligned` / `yaw` / `sharpness` / `assign_rule` を足す | **なし**（既存の行は未計測） |
| **v5 → v6** | `Media` に `folder_date_from` / `folder_date_to` を足し、**パスから埋める**（NFS は読まない。実データの複製で数秒） | **なし** |
| **v6 → v7** | `ScanRoot` テーブルを足す（**中身は推定しない**。次の `scan` が書く・§6.5） | **なし** |

**足りないテーブルと索引は `db.SCHEMA` を丸ごと流して作る**（`IF NOT EXISTS` なので
足りないものだけができる）。作るものを移行コードに書き足さない。

**足す列を移行コードに書き足していかない。** 何を足すかは
`db.missing_columns`（実際の形との差）と `db.ADDABLE_COLUMNS`（列と型の一覧）から
決まる。版を上げるたびに `if "..." not in columns` を書き足す作りだと、
**書き忘れが「版だけ進んで列が無い」状態を生む**（下記）。

**v1 の再構築経路も、最後に同じ処理を通す。** 再構築は自前の DDL で
テーブルを作り直すが、その DDL は現行スキーマとは別に書かれているので、
列を足すたびに片方だけ古くなる（実際にそうなった）。

`VACUUM` するのは **v1 からの移行だけ**（テーブルを組み直すため）。列を足す
だけの移行は組み直さないので `--no-vacuum` を見ない。**そのことは移行前の
案内に出す**（黙って効かない引数を作らない）。

どちらも移行前に**自動でバックアップ**を取り、`PRAGMA integrity_check` を通す。
**冪等**で、移行済みのデータベースに実行しても何も起きない。

### 移行したかどうかは、版の数字だけで決めない

**`PRAGMA user_version` は「移行済み」の印であって、中身の保証ではない。**
版だけが進み、列が足りていないデータベースがありうる。そうなると `migrate` が
「すでに最新です」と答え、**欠けた列は二度と足されない。**

そのため次の2つを守る。

- **既にテーブルのあるデータベースに、アプリケーションが版を刻まない。**
  版が古ければ移行を促して中断する（`db.create_tables`）
- **移行が要るかどうかは、版と実際の列の両方で判断する**（`db.missing_columns`）。
  版だけ進んでしまったデータベースも、`migrate` が列を足して直せる

列の一覧は `SCHEMA` から実際に作って読み取る。別に書き写すと、スキーマを
変えたときに片方だけ古くなる。

### v1 → v2（顔を作り直す）

- **温存するもの**: `Media` と `Person`（id ごと）。`file_hash` も残すので
  再スキャンでハッシュを計算し直さずに済む
- **破棄するもの**: `Face`（旧 `FaceEmbedding`）と `AnalysisResult`。
  旧特徴量は FaceMesh の x 座標を128個並べただけで個人識別能力が無く、
  現在の特徴量と互換性がないため。**破棄は互換性の問題によるもので、
  移行という操作の性質ではない**
- 移行後、全 `Media` は `face_count IS NULL`（未スキャン）になる
- 最後に VACUUM する（`--no-vacuum` で省ける）

実績: 773MB / `Media` 70,297件 / `Person` 5件 のデータベースが 29MB に縮み、
17秒で完了した（2026-09-19）。

### v2 以降（列を足すだけ）

**何も破棄しない。** 列を1本足すだけなので、顔も解析結果も検出済みの状態も残る。

**この違いを取り違えると、実データが消える。** v2 のデータベースを v1 の
再構築経路へ流すと、使えるはずの顔と、数時間かけたスキャンの結果が失われる。
移行処理は**元の版で分岐**し、テストで「v2 から移行して顔が1件も減らないこと」
を固定している。

実績: 359MB / `Media` 70,297件 / `Face` 58,606件 のデータベースが
**2.5秒・無損失**で完了した（2026-09-20）。

スキーマ版が古いまま他のコマンドを実行すると、移行を促すエラーで止まる。
スキーマ版が新しすぎる場合も拒否する。

# 8. 家族の顔認識

## 8.1 人物の登録（実装済み）

利用者が家族を登録する（父・母・長男・長女 など）。
1人につき複数の顔を割り当てる。正面顔、年齢差のある写真、明るい写真が望ましい。

## 8.2 割り当ての流れ（実装済み）

```
[ scan ]   写真 → 顔検出 → 顔特徴量 → 未割当の顔として保存
                                        ← ここでは人物と比較しない
[ GUI ]    人物を登録し、顔を手動で割り当て（assign_source = 'manual'）

[ match ]  手動割り当ての顔とだけ比較
           → 閾値とマージンを満たせば人物判定（assign_source = 'auto'）
           → 満たさなければ未割当のまま
```

## 8.3 自動割り当て（実装済み）

### 手本

- `assign_source = 'manual'` かつ `embedding` を持つ顔だけ
- **自動割り当ての結果は手本に含めない**

### 判定

- **「この人物ではない」と記録された人物を、候補から外す**（下記）
- **その写真の時点で生まれていない人物を、候補から外す**（下記）
- 残った中から、**特徴量の距離**が最小の人物を候補とする。**尺度はモデルが決める**
  （ArcFace は L2 正規化後のコサイン。§7.7）
- 距離が閾値（既定 **0.45**）以下であること
- かつ、次に近い**別人物**との距離差がマージン（既定 **0.08**）以上であること
- 勝った人物の、**5点整列ができた**手本の**どれか1件**までの距離が、
  **その手本の年齢で決まる上限**以下であること（下記。2026-10-09・#66）
- どれかを満たさない顔は未割当のまま残す
- **同じ版の特徴量だけを見る**（`embed_version`）。別の埋め込み空間の距離を
  比べるのは常に誤り

### 手本の選別と、年齢による上限（実装済み・2026-10-09・#66）

**勝者とマージンは全手本で決め、受け入れだけを絞る。** 2つある。

| | 規則 | 理由 |
|---|---|---|
| **手本の選別** | **5点整列ができなかった手本**（`Face.aligned = 0`）を受け入れの根拠にしない | 目印が取れないと ArcFace は整列を飛ばして縮小で通す（§7.7）。その特徴量は整列されておらず、**他人を引き寄せる「磁石」になっていた** |
| **年齢の上限** | 手本ごとに、**8歳以下なら 0.35、年齢不明なら 0.40** を上限にする（閾値より緩めない）。**どれか1件が自分の上限以内なら受け入れる** | **赤ちゃんの顔は誰でも互いに近い。** ${PERSON_4}の誤りの 83% が 0〜5歳の手本に引き寄せられていた |

手本の年齢は、確定値（`Face.age`）を優先し、無ければ誕生日と撮影日時から計算する。
値は `embedding.ACTIVE.age_limits` / `unknown_age_limit` に1か所で持つ。

**どちらも勝者とマージンには効かせない。** 効かせると勝つ人物が入れ替わる。

- **手本を消すと誤りが増える。** 整列できない手本を丸ごと外すと、その人物が
  **2位の対抗馬として他人を止めていた役目**まで消え、実データで誤りが **+418 件**
  増えた。**根拠にしないだけで、対抗馬としては残す**
- **年齢の差を距離に足し引きすると、勝つ人物が入れ替わる。** 大人の手本を締めると
  誤りが **+258 件**増えた（マージンで止まっていた他人が、別の人物へ流れる）

**「最も近い1件の上限」で判定しない**（2026-10-10・PR #70 のレビュー指摘2）。
同じ人物に2歳の手本（距離 0.36・上限 0.35）と10歳の手本（0.40・上限 0.45）が
あるとき、最も近い1件で決めると落ち、**手本を足して割り当てが減る**形になる。
「年上の手本を割り当てれば年上の顔が付く」が成り立たない。

`assign_score` は**受け入れを決めた手本までの距離**（上限以内の手本のうち最も近いもの）
から出す（受け入れと同じ根拠にそろえる）。

**自動割り当てには規則の版を記録する**（`Face.assign_rule` ← `matcher.MATCH_RULE`。
いまは `aligned-age/3`）。規則を変えたら版を上げる。`select` が古い判定の残りに気づける。

#### 実測（2026-10-09・実データの複製・撮影日で半分に分けて片方で選び、もう片方で確かめた）

| 検証側（較正に使っていない半分） | 正解 | 誤り |
|---|---|---|
| 0.45 一律（以前） | 4,865 | 215 |
| 整列できない手本を根拠にしない | 4,853 | 159（−26%） |
| ＋ 8歳以下 0.35・年齢不明 0.40（最も近い1件で判定） | 4,816 | 97（−55%） |
| **同じ上限・どれか1件で判定**（いまの規則） | **4,824** | **106（−51%）** |

誤りは「この人物ではない」「誰でもない顔」として人が否定した顔と、手本と同じ写真に
写る別の顔に、`match` と同じ判定を通して数えた。正解は手本の1件抜き（同じ写真・
同じ撮影日の同一人物の手本は外す）。

**本番の `match` では、自動割り当てが 13,426 → 9,671 件に減った**（同じ手本で。
「どれか1件」に変えたあとは **9,966 件**。増えた 295 件は年上の${PERSON_4}・${PERSON_5}・${PERSON_3}
らしい顔が多かった）。
手本の選別で外れた 665 件は、目で見てほぼ全部が外すべきもの（顔でないもの・他人・
ボケ・横顔）だった。**年齢の上限で外れた約 3,100 件には、年上の${PERSON_3}らしい顔が
多く含まれる**（${PERSON_3}の手本は 98.7% が0〜3歳で、年上の${PERSON_3}が赤ちゃんの手本に
0.35〜0.45 で付いていた）。**利用者が精度を優先して入れると決めた**（2026-10-09）。
年上の手本が増えれば、その年頃の顔は年上の手本（上限 0.45）で受け入れられる。

**この測定の限界**: 正解の側は手本どうしで測っているので、**年上の子の手本が少ない
ところの取りこぼしは測れていない**（上の${PERSON_3}がそれ）。誤りの側の「否定した顔」は
${PERSON_4}の見直しで見つかったものに偏っている。詳細は
[../history/details/2026-10-09-age-threshold-measured.md](../history/details/2026-10-09-age-threshold-measured.md)。

### 「この人物ではない」による候補の絞り込み（実装済み）

**除外は2種類ある。混ぜない。**

| | `FaceRejection`（この人物ではない） | `Face.assign_source='rejected'`（誰でもない顔） |
|---|---|---|
| 意味 | **その人物ではない** | **家族の誰でもない** |
| ほかの人物への自動割り当て | **ありうる** | 無い |
| `match` の候補 | 残る（**その人物だけ**外れる） | 外れる |
| 持ち方 | `FaceRejection(face_id, person_id)` | `Face` の列 |

**「割り当てを解除」だけでは足りない。** `match` は手本と閾値だけで結果が決まるので、
未割当へ戻した判断はどこにも残らず、**流すたびに同じ誤りが戻る**。
実データでは、${PERSON_4}の自動割り当てを見直して解除した **1,785 件**がこれに当たった
（2026-10-08）。**兄弟の赤ん坊の顔は互いによく似ている。**

- 記録すると、その人物への割り当ては外れる（記録が矛盾しないように）
- **ほかの人物に割り当たっている顔は巻き込まない**
- GUI の種別「この人物ではない」から見直して**取り消せる**
- **その一覧には「誰でもない顔」にした顔を出さない。** `rejected` は `match` の
  候補から顔ごと外れるので、**「この人物ではない」の記録はもう何の仕事もしていない**。
  出すと、`誰でもない顔` を押したのにサムネイルが消えない
- **記録そのものは消さない。** 消すと、除外を取り消した瞬間に `match` がまた
  その人物へ付ける。除外を取り消せば一覧にも戻る

### 誕生日による候補の絞り込み（実装済み）

**「その人が生まれる前の写真には写れない」は動かせない事実**なので、
`Person.birth_date` と `Media.shooting_date` から候補を外す。

| | 扱い |
|---|---|
| 撮影日が誕生日より前 | **候補から外す** |
| EXIF が無く、フォルダ名から起こした区間の**終わり**が誕生日より前 | **候補から外す**（§8.4.1） |
| EXIF が無く、区間の途中で生まれた | **絞らない**（分からないものを弾かない） |
| 撮影時期が分からない（EXIF もフォルダ名も読めない） | **絞らない** |
| 誕生日が未登録 | **絞らない**（誕生日は任意の項目） |
| 候補が1人も残らない | 未割当のまま。距離の分布にも入れない |

**年齢の上限では弾かない。** 「老けすぎ」は判断が要る。誕生前だけが事実。

**外すのは距離を比べる前。** マージンは「次に近い別人物」との差なので、
**あとから捨てると、ありえない人物が2位に居座って判断を保留させる。**

> 実測（2026-10-07・手本6,140件）: 誕生前への割り当て **351 件が消え**、
> それとは別に **未割当だった 457 件が正しく割り当たった**（ありえない候補が
> マージンを潰していたため）。合計は 15,487 → **15,734 件**。
> **誤りが減るだけでなく、割り当ては増える。**

**読める撮影日時かどうかの判断は `dates.parse_date` の1か所に持つ**
（CLAUDE.md §8。`0000-00-00` と `TTTT-TT-TTTTT:TT:TT` で2度壊れている）。

**`evaluate` も同じ規則で測る。** 揃えないと実測値が嘘になる（§8.5）。

### 閾値の根拠

方針は「**誤って紐づけるより、取りこぼす側に倒す**」。誤った紐づけは手作業での
やり直しが高くつくため。

**選び方は「他人誤認率」で決める。** 同じ写真に写る2つの顔を「別人」とみなして
測った誤認率で、**dlib の 0.4 を選んだときと同じ数え方**。本番の `match` が解くのは
「未割当（**大半が他人**）を手本と照合する」問題なので、ここがいちばん実害に近い。

#### ArcFace の 0.45（2026-10-03・実データ全件で実測）

同じ写真のペア **37,933 組**で測った他人誤認率と、`evaluate`（手本126件の
1件抜き交差検証、マージン 0.08）の判定を並べる。

| 閾値 | **他人誤認率** | `evaluate` 正解 | 取りこぼし | `evaluate` の誤り |
|---|---|---|---|---|
| 0.40 | 0.61% | 68.3% | 31.7% | 0.0% |
| **0.45（既定）** | **1.06%** | **78.6%** | **21.4%** | **0.0%** |
| 0.50 | 1.92% | 84.1% | 14.3% | 1.6% |
| 0.60 | 5.64% | 88.9% | 9.5% | 1.6% |

#### dlib の 0.4（2026-09-19 実測・参考）

| 閾値 | 2005年（顔幅の中央値128px） | 2026年（同233px） |
|---|---|---|
| 0.40 | 1.0% | 0.5% |
| 0.45 | 2.8% | 5.7% |
| 0.50 | 9.0% | 22.7% |
| 0.60（dlib 標準） | 40.4% | 63.4% |

**尺度が違うので閾値の数字そのものは比べられない**（dlib はユークリッド、
ArcFace はコサイン）。比べるのは**それぞれの既定での成績**。

| | dlib 0.4 | **ArcFace 0.45** |
|---|---|---|
| `evaluate` 正解 | 26.9% | **78.6%** |
| `evaluate` の誤り | 2.6% | **0.0%** |
| 他人誤認率 | 0.5〜1.0% | **1.06%** |

**ArcFace 0.45 は、どの指標でも dlib 0.4 を上回る。**

#### ⚠️ はじめ 0.60 を既定にしていた。それは緩すぎた

**手本どうしのペアだけで閾値を選んでいたのが誤り。** あの測定は
「行事をまたぐ別人のペアの誤りが1%以下」で 0.60 を選んだが、
**手本は家族5人しかいないので、数えていたのは家族内の取り違えだけ。**
他人が紛れ込む誤りは1件も入っていなかった。

実際に測ると 0.60 の他人誤認率は **5.64%** で、**dlib の既定より6〜11倍甘い。**
`evaluate` の誤りが 1.6% と低く見えるのも同じ理由（家族5人の中だけを数えている）。

**教訓: 閾値は「本番で解く問題」と同じ母集団で測る。**

#### ペアの率は、顔1件あたりの率ではない

`match` は1件の顔を手本すべてと比べていちばん近いものを採るので、
**手本のうち誰か1人に似ていれば割り当てられる。** 他人誤認率を
「他人の1.06%しか間違わない」と読むと**過小評価になる**（距離は相関するので
単純な累乗ではないが、向きは悪いほう）。逆にマージン（2位との差）が
安全弁として効くぶんもある。

**顔1件あたりの実際の判定を知るには `evaluate`**（§8.5）。上の表に並べてある。

#### この測定の限界

- **「同じ写真なら別人」は仮定**で、鏡・ポスター・壁の写真立て・顔でないものの
  誤検出で外れる。外れたぶんは誤りに数えられるので、**他人誤認率は実際より
  高めに出る**（ただし両方が手本で同じ人物のペアは除いてある）
- `evaluate` の正解は**実運用より甘く出る。** 連写のように似た手本が別のファイルに
  あると当てやすい（`evaluate` 自身が出力で警告する）
- **手本126件・人物5名。** 誤差は小さくない。**手本が増えたら測り直して確定する**
  （ROADMAP の Phase 3 手順5）

マージン **0.08** は、1位と2位の距離差の**下位10%**（実測 0.091）に当たる。
いちばん迷っている1割を未割当のまま残す。**閾値に対する比率で決めていない**
（距離差は埋め込み空間の性質で、閾値を動かしても変わらない）。

### 冪等性

実行のたびに `assign_source = 'auto'` の割り当てを一旦取り消してから付け直す。
結果は「手本の集合」と「閾値・マージン」だけで決まる。

### `assign_score`

```
assign_score = (1 - 距離 / 基準距離) × 100     （0-100 に丸める）
                （基準距離 = embedding.ACTIVE.similarity_reference。ArcFace は 1.0）
```

**閾値で切るため、自動割り当ての `assign_score` には下限がある**（ArcFace の既定 0.45 と基準距離 1.0 では **55.0**。dlib の 0.4 では 33.3 だった）。
0 にはならないので、「数値が低い顔から確認する」運用の際はこの下限を念頭に置く。
手動割り当ての顔は確信度 100 とみなす。

`family_score` は、メディアに写る顔の `assign_score` の最大値として算出し直す。

## 8.4 年齢の扱い（一部実装）

子どもの成長を考慮し、同一人物について複数年代の顔を保持できる。年代の異なる顔を
手動で割り当てておくと `match` の手本が厚くなる。

年齢は `Face.age` に持つ。**未設定（NULL）と0歳は別の状態**として扱い、
一度入れた年齢を「未設定」へ戻せる。

### 撮影時の年齢の計算（実装済み）

`Person.birth_date`（§7.2）と `Media.shooting_date` の差から、その写真での年齢を
出す。誕生日を迎える前なら1引く。

**これは入力の補助であって、保存される値ではない。** `Face.age` に何を入れるかは
利用者が決める。計算値は判断材料として画面に出すだけで、確定するまで保存しない。

出せない場合がある。**どちらか一方でも欠けていれば計算しない。**

| 欠けているもの | 実データでの割合 |
|---|---|
| `Media.shooting_date`（EXIF 無し） | 15.8%（11,090件） |
| `Person.birth_date`（未登録） | 登録するまで全員 |

撮影日が誕生日より前になる場合は **「誕生前」と出す。** 行を消すのではなく
そう示すことで、**人物の選び間違いや日付の誤りに気づける。**

EXIF が無い写真は、**フォルダ名から起こした撮影時期**で計算する（§8.4.1）。

## 8.4.1 フォルダ名から撮影時期を起こす（実装済み・2026-10-10・#65）

**EXIF の撮影日時が無い写真（実データで 11,090 件。壊れた値 67 件を含む）の
撮影時期を、フォルダ名から起こす。** 写真は `2012/1210/` や
`2026/20260100いろいろ/` のように、年のフォルダの下の日付入りのフォルダに
置かれている。

### 読み方

**最初に出てくる4桁の年のフォルダ**が起点で、その下のフォルダ名の先頭の数字を読む。
**ファイル名は読まない**（`2010/2010.jpg` を `YYMM` と読むと 2020年10月になる）。

| 形 | 例 | 読み |
|---|---|---|
| `YYYYMMDD` | `20260407${EVENT}` | 2026年4月。**DD=00** は日なし、**MM=00** は年だけ |
| `YYMMDD` / `YYYYMM` | `130816-18${EVENT}` / `202101-03${EVENT}` | 2013年8月 / 2021年1〜3月（`-MM` は月の範囲） |
| `YYMM`（年が合わなければ `MMDD`） | `1210` | 2012年10月。**`MMDD` ではない**（照合で 400 件中 400 件） |
| `MM` | `02` | その年の2月 |
| 読めない名前 | `式前` `temp` `2021046-07` | **年だけ受け継ぐ** |

- **親フォルダの区間に収まる読み方だけを残す。** `090920-22${EVENT}/0920${EVENT}`
  の `0920` は、親が 2009年9月なので `MMDD`。読み方が2つ以上残れば読まない
- 区間は**必ず1つの暦年の中**に収まる（年齢の絞り込みの SQL がこれを前提にする）
- 読み方は `dates.folder_date_range` の**1か所だけ**。`Media.folder_date_*` はその出力で、
  `scan`（`save_media` と、終わりの `db.refresh_folder_dates`）と `migrate` が書く

### 月までしか主張しない（利用者が決定）

EXIF が読める 59,061 件を正解として突き合わせた（`scripts/measure_folder_dates.py`）。

| 主張する精度 | 不一致 |
|---|---|
| 日まで | 2,394 |
| 日まで＋7日の幅 | 1,188 |
| 月まで | 469 |
| **月まで＋読めないサブフォルダは年だけ受け継ぐ（採用）** | **277（0.47%）** |
| 年まで | 172 |

- **日付入りのフォルダ名は行事の初日で、撮影日ではない**（出産の入院で +1〜5日、
  `061231USJ` は元日に撮影）
- 日付の無いサブフォルダ（`071222Wedding/式前/衣装合わせ`・`前撮り`）には**行事より前**の写真が入っている
- 残る 277 件は規則では消せない（EXIF の誤り・年月の境目をまたいだもの・別時期の写真の混入）。
  分類は `docs/history/details/2026-10-10-folder-dates-measured.md`
- 行事（フォルダ×日）の束ねは**日が要る**ので、推測した撮影時期では決まらない（§10.4.1 のまま）

### 年齢は、区間の両端で同じときだけ決まる

区間の途中に誕生日があれば**年齢を出さない**（推測で埋めない）。区間の終わりまでに
生まれていなければ「誕生前」で決まる（`dates.age_at`）。**画面・絞り込み・`match`・
`evaluate` で同じ規則を使う。**

### 効かせる範囲（利用者が決定）

| 使い道 | 推測した撮影時期を使うか |
|---|---|
| GUI の年齢表示・プレビュー | **使う。** `(7歳?)`・`撮影時期: 2012年10月（フォルダ名から推測）` と、EXIF 由来と見分けられる形で出す |
| GUI の年齢・誕生前・撮影年月の絞り込み、年齢順 | **使う** |
| `match` / `evaluate` の誕生前の除外（§8.3） | **使う**（規則 `aligned-age/3`。実データの複製で自動割り当て +2 件） |
| `match` の**手本の年齢**（閾値の上限。§8.3） | **使わない。** 使うと日付の無かった手本 661 件に年齢が付き、8歳以下と分かった手本の上限が締まって、**正しい自動割り当てが 125 件外れた**（付いたのは 54 件。2026-10-10・複製で目で見た） |
| `select` の `date` と `count_per_year` | **使う。** EXIF → フォルダ名 → ファイル日時（撮影日時が空のときだけ）の順。区間は**まるごと範囲に入る**ときだけ通す |

## 8.5 精度の実測（実装済み）

閾値は**取りこぼし率と誤一致率の釣り合い**で決まる。片方だけでは決められない
（§8.3 の表は誤一致率しか測っていない）。`evaluate` が両方を同時に出す。

### 測り方: 1件抜き交差検証

手動割り当ての顔は、**正解が分かっている唯一の集合**。ここから顔を1件抜き、
残りを手本にして §8.3 と同じ判定へ通し、抜いた顔が元の人物へ戻るかを見る。

| 結果 | 意味 | 直し方 |
|---|---|---|
| 正解 | 元の人物に割り当てられた | — |
| **取りこぼし** | 閾値かマージンを満たさず未割当のまま残った | 閾値を緩める |
| **誤り**（誤一致） | 別の人物に割り当てられた | **まず手本を疑う**（下記）。手本が正しければ閾値を締める |

判定は `matcher` の関数をそのまま呼ぶ。**測るものと実際に動くものがずれたら、
実測値そのものが嘘になる。** 手本の選別と年齢の上限（§8.3）も同じに効かせる。
未計測の手本はその場で測るが、**DB には書かない。**

### 誤りは、閾値より先に手本を疑う

**「誤り＝閾値を締める」ではない。** 締めれば誤りは取りこぼしに変わるだけで、
その顔が正しい人物へ行くようにはならない。

見分けるのは **「自分の最短」**（その顔から、自分の人物の手本までの最短距離）。

| 自分の最短 | 何が起きているか | 直し方 |
|---|---|---|
| 閾値の近く | 正しい人物も近いが、別人がわずかに近い | **閾値かマージン**を締める |
| **閾値よりずっと大きい** | その顔に似た手本が**1枚も無い** | **手本を増やす**。ラベルが間違っていることもある |

`evaluate` は、試したどれかの閾値で誤った顔を**パスつきで名指しする**
（顔 id・正解・誤った相手・その距離・自分の最短・誤った最小の閾値）。
**既定の閾値で誤りが 0 件でも出す。** 少し緩めただけで誤る顔は「もろい手本」で、
そこが手本を直す手がかりになる。

> 実測（2026-10-06・手本126件）: 既定 0.45 は誤り 0 件で、0.46 から2件誤る。
> **その2件はどちらも手本の問題だった** — 1件は赤ん坊の顔に大人のラベルが
> 付いており、もう1件は顔の半分しか写っていない極端な横顔。自分の最短は
> どちらも 0.676 で、**どの閾値へ動かしても正しい人物には届かない。**
> この2件を手本から外すと、0.60 まで誤り 0% になる。

### 数字を甘くしないための決まり

- **同じ写真に写る同一人物の顔は、既定で手本から外す。** 抜いた顔とほぼ同じ
  手本が残っていれば必ず当たる。実運用で紐づけたいのは別の写真に写った顔。
  `--keep-same-media` で残せるが、その数字は上振れする
- **自分の人物の手本が1つも残らない顔は評価から外す。** 手本が1件だけの人物が
  これに当たり、構造上かならず取りこぼす。取りこぼしに数えると率が実態より
  悪く出るため、件数だけ別に報告する

### 残る限界

**連写のように似た手本が別のファイルにある場合は、正解が実運用より甘く出る。**
同じ写真かどうかでしか近さを判定していないため。撮影日時での除外は未実装。

**手本そのものが「人が判別できた顔」に偏っている。** 小さい顔・横向き・ぶれた顔は
GUI で人物を選べないので手本にならないが、`match` の候補にはそれが含まれる。
**この測定は難しい側の顔を母集団から外している**ので、実運用の取りこぼし率は
ここで出る数字より悪くなる。**方向は必ずこちら側**なので、取りこぼしが少なく
見えても閾値を締める根拠にはならない。

# 9. 画質・表情のスコア（一部実装）

## 9.1 実装済み

いずれも顔ごとに算出し、**0-100** に収める。

**`smile_score`** — 口のランドマーク（FaceMesh の 61 / 291 / 78 / 308）の
外接矩形の縦横比から推定する。

```
smile_score = clamp(0, 100, (幅 / 高さ - 1.4) × 70)
```

**`quality_score`** — 顔領域の明るさと、画面に占める顔の大きさから、
素材としての扱いやすさを表す。

```
brightness = 顔領域の平均輝度 / 255
size_ratio = min(1, 顔の面積 / (画像の面積 × 0.12))
quality_score = min(100, brightness × 60 + size_ratio × 40)
```

**メディア単位のスコアは、写っている顔の最大値**を採用する。顔が0件なら 0。
**他人の顔も含む**ので、`select` の並びの主役には使わない（§9.2 が主役）。

`AnalysisResult` のスコアは `Media` 単位、`Face` のスコアは顔単位で、
**同じ名前だが粒度が違う。**

## 9.2 家族写真としての良さ（実装済み・2026-10-09）

**`select` の並びを決める点**（`family_score`）。**家族の顔だけから作る。**
利用者の要望「せっかく本人が映ってる写真を select で選んでくれてても、ぼやけてたら
意味ない」「家族の写真としてスコアの高いものを選んでほしい」。

**家族の顔1つの良さ**（0〜100。`scoring.family_face_score`）。重く見るものは利用者が
選んだ（ボケていない・正面・笑顔）。

```
鮮明さ  = 対数目盛りで  sharpness ≤ 30 → 0、≥ 150 → 1
正面    = yaw ≤ 0.1 → 1、≥ 0.6 → 0（間は直線）。整列できない顔は 0
笑顔    = smile_score / 100
良さ    = 100 × (0.40 × 鮮明さ + 0.35 × 正面 + 0.25 × 笑顔)
```

見え方が未計測の要素は 0.5 とみなす（良いとも悪いとも言わない）。

**写真の点**（`scoring.family_photo_score`）= いちばん良い家族の顔の良さ ＋
**はっきり写った家族**が2人目から1人につき **10**。はっきり写った家族とは、
整列できて鮮明さが 0.4（sharpness 約 57）以上の顔。**ボケた家族は人数に数えない。**

目盛りは実データの手本 10,701 件を、鮮明さ・向きの帯ごとに並べて目で見て決めた。
**30 以下ははっきりボケ、110 以上はくっきり。** 赤ちゃんの肌はなめらかで、
ピントが合っていても低めに出る（75〜110 はピントの合った赤ちゃんが多い）。
向きは 0.2 以下が正面、0.45 以上はほぼ横顔。

**笑顔の重みはいちばん軽い。** `smile_score` は家族の顔で 73% が 100、19% が 0 に
張り付いていて、見分ける力が弱い（式の見直しは下の 9.3）。

実データの複製で `select` の上位は「家族5人がくっきり正面で写った写真」（点 140）、
下位はボケ・横顔・見切れだった（2026-10-09）。

## 9.3 未実装（将来）

仕様として掲げていたが実装していない評価項目。ROADMAP の Phase 6。

- ピント・ブレ — **家族の顔については §9.2 の鮮明さで見ている**（顔の外は見ていない）
- 白飛び
- 目閉じ
- 笑顔の式の見直し（張り付いている。§9.2）

これらの係数（`1.4` / `70` / `60` / `40` / `0.12`）は実データでの調整を経ていない。
Phase 3 の精度確立と合わせて見直す。

# 10. 顔登録GUI（実装済み）

## 10.1 位置づけ

`photoarchive-gui` は解析エンジンから独立した補助ツール。人物の登録と顔の
割り当てだけを担当し、**写真の解析や抽出は行わない。**

PySide6(Qt) で実装する。

## 10.2 機能

- 人物の一覧表示・追加・編集・削除（削除しても顔は消さず、未割当に戻す）
- 人物一覧の**並べ替え**（ドラッグ。順序は `Person.display_order` に残る。
  **打鍵の 1〜9 もこの順**）
- 人物の誕生日の登録（任意。撮影時の年齢の計算に使う）
- **1枚の画面で、未割当・自動割当（全員）・除外済み・人物ごとを切り替える**
  （§5.10。左の一覧が「見るもの」。別ウィンドウは無い）
- 未割当の顔の一覧表示と、人物への割り当て
- 割り当ての解除 / 自動割り当ての確定 / 年齢の設定
- 誰でもない顔の除外と、**その取り消し**（未割当へ戻す）
- **「この人物ではない」の記録と取り消し**（§7.5）
- **顔への操作を右クリックのメニューと打鍵に集める**（§5.10）
- **残っている件数の表示**（左の一覧。1回の問い合わせで数える）
- **`match`（自動割り当て）を画面から流す**（進み具合つき・控えを取るかを選べる）
- **行事（フォルダ×日）での絞り込み**と、行事単位のまとめ除外・まとめ取り消し
- **行事の中で顔を束ね、束ごとにまとめて割り当て・除外**（§10.4.1）

## 10.3 顔の割り当て

GUI は **`scan` が検出して貯めた顔**を人物へ割り当てる。
利用者が画像ファイルを選んで顔を切り出す操作は行わない。
検出と特徴量生成の規約を `scan` と GUI で一致させるためである。

推奨は1人あたり 20〜50枚。正面・左右・笑顔・真顔・明るい写真・年齢の異なる写真を
混ぜるとよい。割り当てた顔は `assign_source = 'manual'` になる。

### 撮影日時とフォルダを出す

**割り当てのときに年齢（`Face.age`）を入力するには、その写真がいつ撮られたか
が要る。** プレビューの下に次を出す。

```
撮影日時: 2017-12-16 18:46:32
フォルダ: 2017/171216${EVENT}
ファイル: 20171216184632.JPG
${PERSON_2}: 6歳                                   ← 人物を選んでいるとき
```

**人物を選んでいないとき（未割当などの表示）は、登録した全員の年齢を1行で出す。**

```
撮影時の年齢: ${PERSON_3} 10歳 / ${PERSON_2} 6歳 / ${PERSON_2} 40歳
```

未割当の作業は「この顔は誰か」を決めることなので、**全員の年齢が並んでいるほうが
効く。** まだ生まれていない人は出さない（`persons_alive_on`）。

- 撮影日時は `Media.shooting_date`（EXIF）。**実データでは 15.8% が欠けている**
- 欠けているときは `不明（EXIFなし）` と明示し、フォルダ名から撮影時期を起こせれば
  `撮影時期: 2012年10月（フォルダ名から推測）` と**推測と分かる名前で**出す（§8.4.1）。
  年齢も `${PERSON_2}: 6歳?` と `?` を付ける。そのうえで `Media.created_time` を
  **「ファイル日時」という別の名前で**出す。コピーで変わる値なので、
  撮影日時として扱わせない
- フォルダは**それを含む根**からの相対。日付を含むフォルダ名が多く、EXIF が
  無いときの手がかりになる。**根が2つ以上なら根の名前を前に付ける**（`Photo/2011/…`・
  `${PERSON_2}携帯/2021/…`。どちらにも `2021/` がある）。1つなら付けない。どの根の外も絶対パスのまま出す
- **元写真が開けないときも出す。** 出どころはDBなので画像と無関係に読める

### 押したことが分かるようにする

**メディアは NFS 上にあり、顔を1つ選ぶたびに元写真を読み直して 220ms かかる**
（実測）。その間まったく無反応なので、押したのかどうかが分からない。

- **時間のかかる操作は砂時計にする**（割り当て・除外・確定・解除・年齢の設定、
  プレビューの読み出し）。**例外が出ても必ず戻す**（戻し忘れると以後ずっと砂時計）
- **件数の分かる作業は、進み具合を件数で出す**（`N / M 件`）。
  ただし**短い作業では窓を出さない**。一瞬だけ出て消える窓は、出さないより煩わしい
- **進み具合のために `executemany` を分けても、戻り値は全件を返す。**
  `cursor.rowcount` は最後の塊のぶんしか持たないので、塊ごとに足す
- **取り消しボタンは置かない。** 書き込みの途中で止めると、半分だけ適用された
  状態が残る

### 一覧を作り直すあいだ、信号を止める

`QListWidget.clear()` は項目を1つずつ外すので、そのたびに
`itemSelectionChanged` が出る。プレビューがこれに繋がっているため、
**200件を選んで割り当てると元写真を NFS から100回読み直し、1回の操作に
17秒かかっていた**（実測。止めると 92ms）。

作り直したあとは何も選ばれていないので、**プレビューを描き直す理由がそもそも
無い。**

### 登録が済んだ顔は、そうと分かるようにする

割り当てても除外しても、**顔は一覧から消えるのにプレビューだけが残る。**
そのままだと「まだ選んでいる」ように見え、**同じ顔をもう一度登録しようとする。**

- **顔写真に重ねて中央に「完了」を出す。** 画像の外に置くと、見ているところ
  （顔）から目を離さないと気づけない
- **顔写真そのものを薄くする**（不透明度は `gui.DONE_PREVIEW_OPACITY`）。
  文字だけだと、次の顔を選ぶまで前の顔がそのままの濃さで残る
- **次の顔を選んだら消す。** 残ると、いま選んだ顔が済んでいるように見える
- 薄くするのは複製で、**元の画像は書き換えない**

### 選択中の人物の年齢を出す

最後の行に、**選択中の人物がこの写真で何歳か**を出す（§8.4）。人物を選び直すと
この行だけ書き直す（元写真は読み直さない）。**人物を追加・編集した直後も、
その人物を選んだ状態にして書き直す** — 選択が外れると、誕生日を登録した本人に
機能が効いていないように見える。人物の選択が外れたときは、この行も消す。

- 人物が未選択・`Person.birth_date` が未設定・撮影日時が無い、のいずれかなら
  **行そのものを出さない。** 誤解を招く「不明」を並べるより、無いほうがよい
- 撮影日が誕生日より前なら **「誕生前」**。行を消さずにそう示すことで、
  **人物の選び間違いや日付の誤りに気づける**

### 年齢の入力に初期値を入れる

年齢を入力するダイアログは、**計算した年齢を初期値として開く。**
ただし**自動保存はしない。** 利用者が確定して初めて `Face.age` に入る。

**選択中の顔すべてが同じ年齢に落ちるときだけ**入れる。1回の入力は選択中の
全件に入るので、年をまたいで選んでいるときに片方の年齢を初期値にすると、
黙って間違いが入る。初期値を入れたときは、計算値であることをダイアログに書く。

**「分からない」を「反対しない」として扱わないこと。** 撮影日時の無い顔・
読めない顔が**1件でも混ざっていれば出さない**。読める顔だけを見て決めると、
10件のうち9件が EXIF 無しでも残る1件の年齢が全件の初期値になり、
**年齢の分からない顔に別の写真の年齢が保存される**（実データでは
`Media.shooting_date` が 15.8% 欠けている）。

そのため `db.taken_for_faces` は**顔1件につき1件**返す（EXIF が無ければ
フォルダ名から起こした区間。区間の途中に誕生日があれば年齢は「分からない」）。
`DISTINCT` で潰したり、日時の無い顔を落としたりすると、この判断ができない。

ダイアログの知らせには、**撮影日時の分からない顔の件数**と、**フォルダ名から
推測した撮影時期の顔の件数**も出す。
初期値が入らない理由がそれなので、黙っていると「なぜ空欄か」が分からない。
範囲を作るときは読めない値を外す（§10.3 の表示と同じ判断）。

### 誕生日の入力

人物ダイアログの「誕生日」は、**年・月・日をそれぞれ別の欄**で受け取る。

```
誕生日  [2011]年 [5]月 [3]日
```

1つの欄に `YYYY-MM-DD` と打たせると、**区切りの書き方を間違えただけで弾かれる。**
分ければ書式を間違えようがない。

- 3つとも未入力なら未設定。`QDateEdit` は未設定を表せないので使わない
- **年月日まで揃っていないものは受け取らない**（§7.2）。一部だけの入力と、
  暦に無い日（2月30日など）とで、警告の文面を分ける
- 警告を出したときは、その登録・編集を行わない

## 10.3.1 起動時の移行（実装済み）

**移行が必要なデータベースを開こうとしたら、その場で実行できる。**

```
┌──────────────────────────────────┐
│ データベースの移行が必要です              │
│   Media 70,297 件 / Person 5 件 は保持 │
│   顔データ 58,606 件はそのまま残ります    │
│ 実行する前に、自動でバックアップを取ります  │
│           [ 移行を実行 ]  [ 終了 ]  │
└──────────────────────────────────┘
```

この製品の主な作業（人物の登録と顔の割り当て）は GUI で行う。**移行のためだけに
端末へ出させない。**

- 何が残って何が消えるかの文面は、**CLI と同じものを使う**（§7.8）。2か所に
  書くと、片方だけ「破棄します」のまま残る
- **既定のボタンは「終了」。** Enter の連打で、内容を読まないまま走り出さない
- **移行に失敗したらウィンドウを開かない。** 開くと、次に落ちるのは保存のとき。
  どこまで進んだか（バックアップを取ったかどうか）も画面に出す
- 対象は設定の `database_path`（または `--db`）。**ファイルを選ぶ画面は持たない**

### 人物一覧は並べ替えられる

**ドラッグで入れ替える。** よく割り当てる人物を上に置けないと、人数が増えるほど
毎回探すことになる。

- **落とした時点で確定する。** 保存ボタンは置かない（押し忘れたぶんが黙って消える）
- 一覧に出ている**全員**の `display_order` を書き直す。一部だけ書くと、
  書かなかった人物の順序が古いままになって並びが混ざる
- **追加した人物は末尾**に置く。先頭に割り込ませると、並べ替えた結果を崩す
- 並べ替えたことのない人物（移行してきた行）は `display_order` が NULL で、
  **名前順のままそのあとに続く**。新しく追加した人物は必ず値を持つので、
  **登録順**に並ぶ
- **NULL の行が残っているうちに人物を足すときは、先にいまの並びを書き戻す。**
  書き戻さずに `MAX(display_order) + 1` を振ると、`MAX` が NULL のときに 0 に
  なり、**その人物だけが全員より前に出る**（`migrate` 直後がこの状態）

## 10.4 一覧のページング

**顔は数万件になりうる。一覧は必ずページ単位で読み出す。**
サムネイルの BLOB を全件読むと数百MBになり、画面が固まる。

```
[顔][顔][顔][顔][顔][顔]
[顔][顔][顔][顔][顔][顔]

 < 前    3 / 310 ページ（全 61,842 件）    次 >
```

- 1ページあたり 200 件
- **見るものは左の一覧で選ぶ**（未割当 / 自動割当 / 除外済み / 人物。§5.10）
- **「未割当に戻す」で、除外と自動割当を取り消せる。** 除外した顔は
  `person_id` を持たないので §10.5 の画面には出てこない。ここに置かないと、
  **いったん除外した顔は誰かに割り当てる以外に戻す手段が無くなる**
  （「決めきれないので保留に戻す」ができない）。未割当を表示しているときは
  戻す先が無いので**隠さずに押せなくする**（隠すと操作自体が無いと思われる）
- 顔を選ぶと、元写真から切り出し直して拡大表示する
- **割り当て済みの一覧にもページャがある。** 無いと201件目以降に手が届かない

### 枠はサムネイルの寸法に任せない

**`setUniformItemSizes(True)` は、先頭の項目から枠の寸法を決める。** 保存して
あるサムネイルは大きさがまちまちで（短辺の中央 160px・**112px 未満が 7.3%**）、
**先頭にたまたま小さい顔が来たページでは、枠がその顔に合わせて縮み、残りの
サムネイルが切り詰められて下の文字も枠の外に出る**（2026-10-09 に利用者が報告。
実データの未割当1ページ目は先頭 101px・残り 160px だった）。

**枠は `ITEM_WIDTH` / `ITEM_HEIGHT` で固定し、項目1件ずつにも同じ大きさを持たせる。**
高さはサムネイルと**文字2行**ぶん（`13391 (自動 55) ${PERSON_4} (0歳)` のように長い）。
一覧を作る場所は `make_face_list` に1つだけ（メイン画面と束ねる画面で同じ見た目）。

### 並び順は画面の目的で決める

| 表示 | 既定の並び | なぜ |
|---|---|---|
| 未割当 | **撮影日時の新しい順** | 同じ行事の写真が固まるので、まとめて選んで一度に割り当てられる。撮影年をまたがないので、年齢の初期値（§10.3）も1つに定まる |
| 人物（割り当て済み） | **年齢の若い順** | 成長の順に並ぶので、年齢の入れ間違いや別人の混入に気づきやすい |
| 自動割当（全員） | **確信度の低い順**（`assign_score`） | 低いほど「似ていないのに割り当てた」顔。**誤りに早く当たる** |
| それ以外（`match` / `evaluate`） | 品質スコアの高い順 | 既定。変えない |

**並びは画面で選べる**（上の4つ）。**既定は表示ごとに決まっている**ので、
表示を切り替えれば向いた順に戻る。

**並べ替えは条件に当たる全件に効かせ、そのあとでページに分ける。**

**年齢の若い順は、画面に出ている年齢で並べる**（`db._ids_in_age_order`）。
`Face.age` があればそれ、無ければ誕生日と撮影日時から計算した年齢、どちらも
出せなければ最後。**以前は `Face.age` だけで並べていた**ため、実データでは
${PERSON_4}の 9,502 件のうち確定値の 199 件だけが並び、**残り 9,303 件は id 順のまま
2ページ目以降に散っていた**（2026-10-09 に利用者が報告）。

**SQL に年齢の計算を持ち込まない**（§8.4・日付の判断は `dates` に1つだけ）。
条件に当たる顔を**サムネイル抜きで**全件読んで Python で並べ、1ページ分だけ
サムネイルを読む。誕生日は、人物を選んでいればその人物、全員ぶんの表示では
**顔ごとに付いている人物**のもの。

**表示ごとに意味を持たない並びは押せなくする**（`ORDER_UNUSABLE`）。未割当と
除外済みでは年齢と確信度を出せない（実データの未割当 31,275 件で、年齢 2 件・
確信度 0 件）。選べると id 順のまま何も変わらず、壊れているように見える。

**読めない値は最後に置く。** 撮影日時の無い顔（実データの 15.8%）と、年齢が
未設定の顔がこれにあたる。先頭に来ると、順に見ていく邪魔になる。

- 年齢は SQLite の NULL が最小なので、`age IS NULL` を先に見て最後へ送る
- 撮影日時は**日付として読めないものも「無し」として扱う。** カメラが
  `TTTT-TT-TTTTT:TT:TT` を書くことがあり（実データで Media 67件・顔123件）、
  文字の大小で並べると `T` は数字より大きいので、**新しい順の1ページ目を
  まるごと占領する**。判断は §7.5 の `SHOOTING_DATE_SORT_KEY` に持たせ、
  画面の表示（§10.3）と同じ意味にそろえる

## 10.4.1 行事（フォルダ×日）で絞って束ねる（実装済み）

**判断の単位を「顔」から「束」へ移す。** **日付の読める未割当は 51,860 件**あり、
1件ずつ人物を選ぶ作業は終わらない。同じ行事の中で同じ人物の顔を束ねると、人間の決定は
**19,678 回**まで落ちる（実測。詳細は
[../history/details/2026-10-04-event-clustering-measured.md](../history/details/2026-10-04-event-clustering-measured.md)）。

### 行事とは

**フォルダ × 撮影日の1日。** 同じフォルダでも日をまたぐと同一人物の距離が開く
（ArcFace で 0.295 → 0.533）ので、フォルダだけでは粗い。

- 判断は `db.folder_expression()` と `db.day_expression()`（SQL 側）、
  `db.folder_of()`（Python 側）に持つ。**「読める撮影日時か」は §7.5 と同じ**
- **撮影日時が読めない顔は行事を決められない**（実データで顔 6,190 件。うち
  特徴量を持ち束ねられるのは 5,910 件）。フォルダだけが同じ集まりとして
  「（撮影日時不明）」で見せ、**フォルダ単位で束ねる。** これは日をまたぐ単位
  なので条件が違い、**別に測ってある**（同じ上限 0.45 で他人誤認率 0.88% /
  決定 5,910 → 3,139 回。日付つきの 62.1% に対し減り方は 46.9%）
- 絞り込みで「日を指定しない」と「日が読めない顔だけ」は**別の指示**として
  区別する（`day=None` と `db.UNDATED`）

### 束ね方

- **平均連結（average linkage）。** 単連結は1つの誤った近さで鎖のように繋がり、
  完全連結は同じ人物の中の角度差で割れる
- **連結の上限はモデルの属性**（`embedding.ACTIVE.cluster_threshold`。ArcFace は
  0.45）。照合の閾値（§8.3）とは役割が違い、**別に測って選んでいる**
- 選び方は §8.3 と同じ「他人誤認率」。同じ写真に写る顔のペアを同じ束へ入れた
  割合で、0.45 なら 0.66%（0.50 は 1.22% で照合の 1.06% を越えるので採らない）
- **DBに書かない。** 束はその場で計算して捨てる（手本が増えれば束は変わる）
- **同じ入力から必ず同じ束が出る**（乱数を使わない）

### 画面でできること

| 操作 | 効く範囲 |
|---|---|
| この束をまとめて割り当て | **その束の未判断（`assign_source IS NULL`）の顔だけ** |
| この束をまとめて除外 | 同上 |
| この束を割る | 連結の上限を 0.05 下げて、その束だけ割り直す |

- **束は提案で、確定ではない。** 押すのは人。自動では1件も割り当てない
- **手本と除外を巻き込まない。** 束に手本が混ざっていても触らず、
  「手本: ${PERSON_2}」として**誰の束かの手がかりに使う**
- **その日に生まれていない人物は、割り当て先に出さない。** まとめて押すときは
  画面に出るのが人物名だけなので、選べると気づけない
- **大きい束を割れるようにする。** 実データでいちばん大きい行事（1,357 件）は
  380 件の束を作る。割れないと、別人が混ざっていると分かってもまとめて押せない
- サムネイルは**選んだ束の1ページ分だけ**読む（§10.4 と同じ理由）
- 一度に束ねられる顔は `clustering.MAX_FACES` 件まで。超えたら
  **黙って先頭だけ束ねずに断る**（出ていない顔が未割当のまま残るのを防ぐ）

## 10.5 割り当て済みの確認（人物の表示）

**左の一覧でその人物を選ぶ。** 以前は「割り当て済みを確認」で別ウィンドウが
開いたが、#67 でメイン画面に畳んだ。**機能は落としていない** — 種別の絞り込み、
年齢の範囲、年齢不明の扱い、確定の活性制御、「この人物ではない」の一覧と取り消し、
年齢の設定、ページャはそのまま。

**畳んだことで増えたもの。** 共通の絞り込み（撮影年月・行事・並び順）が人物の
表示にも効く。「2018年の${PERSON_4}だけ見直す」ができる。

できる操作は §5.10 の表のとおり（右クリックのメニュー）。

**「この人物ではない」の一覧も、ふつうの絞り込みと同じ経路で読む**
（`db._face_filter` の `rejected_for_person`）。以前は専用の読み出しだったため、
**撮影年月・行事・年齢の絞り込みとページャが効かなかった。**
**「誰でもない顔」にした顔はこの一覧から外す** — あちらは `match` の候補から
顔ごと外れるので、否定の記録はもう何の仕事もしていない。**記録そのものは消さない**
（消すと、除外を取り消した瞬間に `match` がまたその人物へ付ける）。

年齢で絞り込んだとき、**年齢を出せない顔は既定で外れる**（`年齢不明も含める`
で戻せる。§5.10）。

# 12. 抽出（一部実装）

## 12.1 ルール

抽出は YAML のルールで制御する（JSON は読まない・§2.2）。

```yaml
date:
  start: 2014-01-01
  end: 2023-12-31
family_only: true
count_per_year: 40
include_video: true
remove_duplicate: true
```

| キー | 既定 | 意味 | 状態 |
|---|---|---|---|
| `date.start` / `date.end` | 制限なし | 撮影日時（無ければフォルダ名から起こした撮影時期。それも無く撮影日時が空なら作成日時）の範囲。フォルダ名の区間は**まるごと入る**ときだけ通す。**日付だけの `end` はその日の終わりまで含む**。YAML の引用符の無い日付も読む。日付が読めないメディアは範囲外（§8.4.1） | 実装済み |
| `include_video` | `true` | 動画を含めるか | 実装済み |
| `family_only` | `false` | 家族の顔（手本か自動割り当て）が写っているメディアだけにする | 実装済み |
| `remove_duplicate` | `false` | ハッシュが同じメディアを1件にまとめる（§11） | 実装済み |
| `count_per_year` | 制限なし | 1年あたりの上限件数 | 実装済み |
| `purpose` | — | 用途プリセット（§13） | **未実装** |

並び順は **家族写真としての良さ**（§9.2）→ `quality_score` → `smile_score` → `face_count` の降順。
家族写真としての良さは**その場でいまの割り当てから計算する**（§5.8）。
`count_per_year` はこの順で各年の上位から採る。年ごとの件数を揃える処理は
入っていないので、元の件数が少ない年はそのままになる。

**`family_only` は「家族の顔（手本か自動割り当て）が写っているか」だけを見る。**
写り方の良し悪しは並びで効かせる（ボケた家族の写真も残るが、後ろへ回る）。
**点（§9.2）で絞らない。** 点は鮮明さ・正面・笑顔がすべて 0 なら 0 になるので、
「点 > 0」で絞るとボケて横を向いた家族の写真が落ちる（実データの複製で 20,828 枚中
433 枚。PR #70 のレビュー指摘1）。以前は確信度が閾値で下限を持ち、
「点 > 0」が「割り当てが1つでもある」と同義だった。

## 12.2 出力

- **入力データは変更しない。** 出力先へコピーする
- 出力先での配置は、**それを含む根**からの**相対パスをそのまま再現**する（根の名前は挟まない・#24）
- 名前が衝突する場合は `photo_1.jpg`、`photo_2.jpg` のように空いている連番を付ける

## 15.1 想定する規模

## 15.2 処理時間の実測

| 項目 | 実測 | 全件換算 |
|---|---|---|
| NFS 読み出し | 24 MB/s | 画像 2.5h / 動画 2.6h |
| JPEG フルデコード | 0.094〜0.205 s/枚 | 1.7〜4.0h |
| MediaPipe 顔検出 | 0.020〜0.030 s/枚 | 0.4〜0.6h |
| dlib 特徴量 | 0.130 s/顔 | 2.2h |
| SHA-256 | 0.012 s/枚 | 0.2h |

**IO が律速。** 1回読み + 差分判定 + `--workers 4` で全件 2.5〜3.5時間の見込み。
2回目以降のスキャンは数十秒。

デコードを速くする最適化（`Image.draft()` による DCT スケーリング）は、
検出結果は一致するものの**同じ顔の特徴量の距離が平均 0.13・最大 0.38 動いた**ため
採らなかった。閾値 0.4 に対して無視できず、IO が律速である以上デコード時間は
並列化で吸収できる。

顔1件あたりのデータベース増分は約5KB（サムネイルの実測平均が 3.3KB）。

## 15.3 中断と再開

顔検出が終わったメディアは逐次コミットされるので、`scan` を中断しても
再実行すれば続きから再開する。

## 15.4 ログ

`scan` と `match` は `data/logs/<コマンド>_<日時>.log` に出力する。
既定のログレベルは `WARNING`。ログの世代管理は行っていない。
