# 1. 概要

## 1.1 目的

長期間保存された大量の写真・動画から、AIを利用して家族の思い出となるメディアを
自動で選び出すシステム。

- 過去10年以上の写真・動画から記念動画を作るための素材抽出
- NAS上のフォトフレームで表示する写真セットの作成
- 家族写真アーカイブの整理

## 1.2 担当する範囲

| 範囲 | 状態 |
|---|---|
| 写真・動画ファイルの検索 | 実装済み |
| メディア情報の取得（EXIF・撮影日時・ハッシュ） | 実装済み |
| 顔検出 | 実装済み |
| 家族の人物識別 | 実装済み |
| 写真の品質評価 | 一部実装（§9） |
| 類似写真の判定 | 未実装（§10） |
| 抽出条件による写真選択 | 一部実装（§11） |
| 指定フォルダへのコピー | 実装済み |

担当しない: 動画編集、写真加工、Web表示。

## 1.3 用語

同じものを別の名前で呼ばない。**文書もコードもこの語彙に揃える。**

| 語 | 意味 |
|---|---|
| **メディア** | 写真または動画のファイル1件。`Media` テーブルの1行 |
| **顔** | 写真から検出された顔1つ。`Face` テーブルの1行 |
| **人物** | 利用者が登録した家族の1人。`Person` テーブルの1行 |
| **割り当て** | 顔を人物に結びつけること |
| **手本** | 手動で割り当てた顔。`match` が判断の根拠に使う |
| **未割当** | まだどの人物にも結びついていない顔 |
| **除外** | 「誰でもない顔」として一覧からも自動割り当てからも外すこと |
| **確定** | 自動割り当てを手動割り当てに昇格し、次回の手本にすること |

# 2. 動作環境と設定

## 2.1 環境

- OS: Ubuntu Linux
- 言語: Python 3.10 以上
- データベース: SQLite
- 非公開リポジトリで管理する

**ローカルPC内で完結する。写真・動画データを外部サービスへ送信しない。**
クラウドAIや外部APIは将来のオプション。

## 2.2 設定ファイル（実装済み）

アプリ設定は JSON。`config/app_settings.sample.json` を写して使う。

| キー | 意味 |
|---|---|
| `database_path` | SQLite データベースの置き場所 |
| `source_root` | 走査するメディアのルート |
| `output_root` | `select` のコピー先 |
| `rule_path` | 抽出ルールファイル |
| `dlib_model_dir` | dlib の学習済みモデルの置き場所（任意） |

### 探索の順序

**次の順で探し、最初に見つかったものを使う。**

1. 環境変数 `PHOTOARCHIVE_CONFIG` が指すファイル
2. カレントディレクトリの `config/app_settings.json`
3. リポジトリ直下の `config/app_settings.json`

3 があるのは、リポジトリルート以外から `photoarchive` を起動しても設定が効く
ようにするため。**設定ファイルのパスを変えるためにソースを編集する必要はない。**
3 が候補に出るのは `pip install -e .`（editable install）のときだけで、
通常のインストールでは「リポジトリ直下」にあたるものが無いので使わない。

見つからない場合・壊れている場合は空の設定として扱い、コマンドは CLI 引数だけで
動く。どこを探したかはログ（`--log-level INFO`）に残る。

抽出ルールは `config/rule.json`。**拡張子が `.yml` / `.yaml` なら YAML として
読む**（`config/rule.sample.json` がサンプル）。

dlib のモデルの探索順は §7.6 を参照。

## 2.3 Git 管理から外すもの

生成物と、利用者ごとに異なるものは管理しない。

- `.venv/`、`__pycache__/`、`*.pyc`、`build/`、`dist/`、`*.egg-info/`
- `data/`（SQLite データベース、ログ、バックアップ）
- `output/`、`models/`
- `mediaFiles/`（実データへの symlink 置き場）
- `config/app_settings.json`、`config/rule.json`（`*.sample.json` だけ管理する）
- `.pytest_cache/`

ファイルの置き場所の決まりは [../../CLAUDE.md](../../CLAUDE.md) にある。

# 3. 設計の原則

## 3.1 検出・割り当て・抽出を分ける（実装済み）

```
scan          パスの登録 + 顔検出 + 顔画像/特徴量/スコアの保存 + 消えた行の削除
  ↓
photoarchive-gui   人物の登録 + 検出済みの顔を人物へ手動で割り当て
  ↓
match         手動割り当てを手本に、残りの顔を自動で紐づけ
  ↓
select        ルールに従って抽出しコピー
```

**この順序が設計の核心。検出と割り当てを同じ工程にしてはならない。**
人物が1人も登録されていない段階で自動割り当てを行うと、誰とも分からない顔が
誤った人物に結びつく。旧 `analyze` はこれを犯していたため廃止した（Issue #28）。

一度検出した結果は再利用する。

## 3.2 解析結果は永続データ（実装済み）

解析結果は SQLite に保存し、一時データとして扱わない。

### 顔検出の実施状態

`Media.face_count` が3つの状態を表す。**この区別が差分スキャンの土台。**

| 値 | 意味 |
|---|---|
| `NULL` | 未スキャン |
| `0` | スキャン済みで顔が見つからなかった（**読み込めなかった場合を含む**） |
| `N` | 検出した顔の数 |

読めなかったファイルを `NULL` のままにすると毎回読み直すことになるため、
`0` として記録し、理由はログに残す。

### 再検出する条件

1. 新規ファイル
2. ファイルハッシュの変更
3. 検出器のバージョンの変更（`Media.detector_version` の不一致）
4. `scan --force-rescan` による明示的な指示

### ハッシュ計算の省略

ファイルサイズが一致し、**更新時刻の差が 1.0 秒以内**なら、ハッシュを計算しない。
1秒の許容差は NFS とタイムゾーンの丸めを吸収するため。

ハッシュが同じでも、ファイル属性（更新時刻など）は必ず書き戻す。書き戻さないと、
中身が同じなのに毎回「変わったかもしれない」と判断され、恒久的に全体を読み直す
ことになる。このとき `face_count` などの検出状態には触らない。

### 再スキャンは手動の割り当てを破棄する

**ハッシュが変わったメディアは、手動で割り当て済みの顔も含めて顔を作り直す。**
中身が別物になった以上、座標も特徴量も無効なため。削除時は WARNING をログに残す。

GUI での割り当ては人手のかかる作業なので、この挙動は意図的に目立たせている。

```
写真 / 動画
     |
     v
scan（登録 + 顔検出 + 特徴量 + スコア）
     |
     v

     |                 match（残りの顔を自動割り当て）
     v <--------------------+

     |
     v

```

# 5. CLI リファレンス（実装済み）

すべてのコマンドは `photoarchive <サブコマンド>`。
`--db` などを省いたときは §2.2 の設定ファイルから補う。

| サブコマンド | 役割 |
|---|---|
| `init-db` | データベースを作る |
| `migrate` | 旧スキーマのデータベースを移行する |
| `convert-heic` | HEIC/HEIF を JPEG へ変換する |
| `scan` | メディアを登録し、顔を検出する |
| `match` | 未割当の顔を自動で人物へ紐づける |
| `evaluate` | 手本を使って `match` の取りこぼし率と誤一致率を実測する |
| `select` | ルールに従って抽出しコピーする |

GUI は別の実行ファイル `photoarchive-gui`。

## 5.1 共通

| 引数 | 既定 | 意味 |
|---|---|---|
| `--db` | 設定ファイルの `database_path` | データベースのパス |
| `--log-level` | `WARNING` | `DEBUG` / `INFO` / `WARNING` / `ERROR` / `CRITICAL`（`scan` / `match` / `evaluate`） |

**`convert-heic` はデータベースを使わないので、`--db` も設定ファイルも要らない。**

## 5.2 `scan`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--source` | 設定ファイルの `source_root` | 走査するディレクトリ |
| `--workers` | `min(4, CPU数 - 1)` | 顔検出のワーカープロセス数 |
| `--no-prune` | off | 実体が無くなったメディアの行を消さない |
| `--force-prune` | off | 安全弁（§6.2）を越えても消す |
| `--force-rescan` | off | 全件の顔を検出し直す |
| `--allow-missing-embeddings` | off | 顔特徴量のモデルが読めなくても続行する。`detector_version` を書かないので、モデル設置後の通常の `scan` が自動でやり直す |

ログは `data/logs/scan_<日時>.log`。

**モデルが読めない状態で走らせない。** 特徴量が全件 `NULL` のまま
「スキャン済み」として記録されてしまう。`scan` は開始時にこれを確かめて中断する。

`--allow-missing-embeddings` を付けて続行した場合、そのメディアには
**`detector_version` を書かない**（`face_count` と `face_scanned_at` だけ記録する）。
版を NULL のまま残すことで、モデルを設置したあとの通常の `scan` が自動で
検出と特徴量生成をやり直す。版を書いてしまうと差分判定が「版が一致する」と
見なして全件スキップし、`--force-rescan` 以外に回収手段が無くなる。
そして `--force-rescan` は**手動割り当てを巻き添えにする**（§3.2）。

## 5.3 `match`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--threshold` | `0.4` | 顔特徴量の距離の上限。小さいほど厳しい |
| `--margin` | `0.05` | 2位の人物との距離差の下限 |
| `--no-reset` | off | 既存の自動割り当てを取り消さない |
| `--dry-run` | off | 書き込まずに件数と距離の分布だけ出す |

ログは `data/logs/match_<日時>.log`。

`--dry-run` は「いま `match` を実行したらどうなるか」を示す。自動割り当てを
取り消さないので、**取り消し後の状態を再現するために `auto` の顔も候補に含める。**
含めないと2回目以降の dry-run が空振りして、`--threshold` を決める目安にならない。

## 5.4 `evaluate`

手動割り当ての顔を正解とみなして、`match` の**取りこぼし率**と**誤一致率**を
同じ土俵で測る。**データベースには書かない（読み出しのみ）。**

| 引数 | 既定 | 意味 |
|---|---|---|
| `--thresholds` | `0.3,0.35,0.4,0.45,0.5,0.55,0.6` | 試す閾値をカンマ区切りで指定する |
| `--margin` | `0.05` | 2位の人物との距離差の下限。`match` と同じ意味 |
| `--keep-same-media` | off | 同じ写真に写る同一人物の顔も手本に残す |

ログは `data/logs/evaluate_<日時>.log`。測り方は §8.5。

## 5.5 `migrate`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--backup` | `<db>.bak-<日時>` | バックアップの置き場所 |
| `--no-vacuum` | off | 移行後の VACUUM を省く |
| `--yes` | off | 確認を省く |

## 5.6 `select`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--rule` | 設定ファイルの `rule_path` | ルールファイル（JSON / YAML） |
| `--output` | 設定ファイルの `output_root` | コピー先 |
| `--source` | 設定ファイルの `source_root` | 出力の相対パスの基準 |

## 5.7 `convert-heic`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--source` | 設定ファイルの `source_root` | 変換するディレクトリ（再帰） |

## 5.8 `photoarchive-gui`

| 引数 | 既定 | 意味 |
|---|---|---|
| `--db` | 設定ファイルの `database_path` | データベースのパス |

## 5.9 進捗表示

`scan` / `match` / `evaluate` / `convert-heic` / `select` は2行の進捗を出す。1行目が進捗バー、
2行目が**直近のエラー**。エラーが出なかった回で `Error: none` に戻さない
（戻すと、流れていく表示の中でエラーが一瞬しか見えない）。

# 6. メディアの走査（実装済み）

## 6.1 やること

- 指定ディレクトリ以下を再帰的に検索する
- 写真・動画を見つける（`jpg` `jpeg` `png` `heic` `heif` / `mp4` `avi` `mov` `mkv`）
- ファイル情報を取得する（サイズ、更新時刻、EXIF の撮影日時）
- ハッシュを生成する（§3.2 の条件で省略する）
- 顔を検出し、顔画像・顔特徴量・スコアを保存する
- 既に顔検出済みのメディアは再検出しない
- データベースにあるが実体が無くなったメディアの行を削除する

**走査は人物への割り当てを一切行わない。**

`Media.type` の値域は `"image"` / `"video"`。

**動画は先頭の1フレームだけを解析する。** 全フレームを見るのは費用に見合わない。

## 6.2 安全弁

未マウントのディレクトリを走査して全件削除する事故を防ぐため、2つの中断条件を持つ。

1. **メディアが1件も見つからない場合**は中断する
2. **実体が無いメディアが、走査ルート配下の登録数の 20% を超える場合**は中断する。
   意図した削除なら `--force-prune` を付ける

母数は**走査ルート配下に限る**。`--source` で年フォルダ1つだけを走査したときに、
他のフォルダの登録件数が母数に混ざらないようにするため。

## 6.3 HEIC の扱い

- `convert-heic` で JPEG へ変換できる（品質 95、元ファイルは変更しない）
- `scan` は **HEIC を直接読める**（`pillow_heif` のデコーダを登録している）

**未決**: `convert-heic` の後は `photo.heic` と `photo.jpg` が両方登録され、
同じ顔が二重に検出される。ハッシュが違うので重複排除も効かない。
どちらを正とするかは Issue #26 で決める。

# 7. データベース設計（実装済み）

外部キーは有効（`PRAGMA foreign_keys = ON`）。GUI と CLI を同時に使うため
`journal_mode = WAL` / `synchronous = NORMAL`。

## 7.1 Media

| 列 | 型 | 制約 |
|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT |
| `path` | TEXT | UNIQUE NOT NULL |
| `filename` | TEXT | NOT NULL |
| `type` | TEXT | NOT NULL（`"image"` / `"video"`） |
| `file_hash` | TEXT | NOT NULL |
| `file_size` | INTEGER | NOT NULL |
| `created_time` | TEXT | NOT NULL（ファイルの更新時刻） |
| `shooting_date` | TEXT | EXIF の撮影日時 |
| `face_count` | INTEGER | **NULL=未スキャン / 0=顔なし / N=検出数**（§3.2） |
| `face_scanned_at` | TEXT | 顔検出を行った時刻 |
| `detector_version` | TEXT | 検出器のバージョン（§7.6） |

## 7.2 Person

| 列 | 型 | 制約 |
|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT |
| `name` | TEXT | NOT NULL |
| `relation` | TEXT | 続柄（任意） |
| `memo` | TEXT | 任意 |

**`name` に UNIQUE 制約は無い。**同名の人物を作れてしまうが、制約を足すには
既存データベースの移行が必要になるため保留している（ROADMAP の Phase 3）。

## 7.3 Face

写真から検出された顔。**GUI で登録する「手本の顔」も、この中の
`assign_source = 'manual'` の行として表す。手本専用の行は作らない。**

| 列 | 型 | 制約 |
|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT |
| `media_id` | INTEGER | NOT NULL、`Media(id)` へ FK、`ON DELETE CASCADE` |
| `bbox_top` / `bbox_right` / `bbox_bottom` / `bbox_left` | INTEGER | NOT NULL。**検出器が返した生の矩形**（§7.6） |
| `detection_score` | REAL | 検出器の確信度 |
| `embedding` | BLOB | float32 × 128。作れなかった場合は NULL（§7.6） |
| `embed_version` | TEXT | NOT NULL。特徴量の生成規約 |
| `thumbnail` | BLOB | 一覧表示用の小さな顔画像（JPEG） |
| `smile_score` / `quality_score` | REAL | この顔のスコア（§9） |
| `person_id` | INTEGER | `Person(id)` へ FK、`ON DELETE SET NULL`。NULL=未割当 |
| `assign_source` | TEXT | NULL=未割当 / `'manual'` / `'auto'` / `'rejected'` |
| `assign_score` | REAL | 自動割り当て時の類似度 0-100（§8.3） |
| `assigned_at` | TEXT | 割り当てた時刻 |
| `age` | INTEGER | 撮影時の年齢（任意）。**未設定（NULL）と0歳は別の状態** |
| `created_at` | TEXT | NOT NULL |

### `assign_source` を区別する理由

- **自動割り当ての手本に使ってよいのは `'manual'` だけ。** `'auto'` を手本に
  混ぜると、誤った割り当てが次の判定の根拠になって増幅する
- `'auto'` だけをまとめて取り消せるので、`match` を何度実行しても同じ結果になる
- `'rejected'` を持てるので、誰でもない顔が未割当一覧に残り続けない

## 7.4 AnalysisResult

メディア単位のスコア。顔の数は `Media.face_count` が持つ。

| 列 | 型 | 制約 |
|---|---|---|
| `media_id` | INTEGER | **PRIMARY KEY**、`Media(id)` へ FK、`ON DELETE CASCADE` |
| `family_score` | REAL | `match` が書く |
| `smile_score` | REAL | `scan` が書く |
| `quality_score` | REAL | `scan` が書く |

**`scan` がスコアを書くときに `family_score` を潰してはならない。逆に `match` は
smile / quality を触らない。** `media_id` が主キーなので、どちらも UPSERT
（`ON CONFLICT(media_id) DO UPDATE SET` で自分の列だけ）で書く。

`match` は `family_score` を全行 0.0 に戻してから付け直すため、人物が1人も
登録されていなくても NULL ではなく 0.0 になる。また、GUI で割り当てを解除しても
`AnalysisResult` は更新されないので、**次に `match` を実行するまで `family_score`
は古いまま**である。

## 7.5 インデックス

| 名前 | 対象 |
|---|---|
| `idx_media_hash` | `Media(file_hash)` |
| `idx_media_type` | `Media(type)` |
| `idx_media_unscanned` | `Media(id) WHERE face_count IS NULL` |
| `idx_face_media` | `Face(media_id)` |
| `idx_face_person` | `Face(person_id)` |
| `idx_face_manual` | `Face(person_id) WHERE assign_source = 'manual'` |
| `idx_face_unassigned` | `Face(quality_score DESC, id) WHERE assign_source IS NULL` |

`idx_face_unassigned` が §10.4 の「品質スコア降順のページング」を成立させている。
部分インデックスが参照する列は SQLite では `DROP COLUMN` できないため、
移行はテーブル再構築方式をとる（§7.7）。

## 7.6 特徴量の生成規約

| 定数 | 値 | 意味 |
|---|---|---|
| `EMBED_VERSION` | `dlib_resnet_v1/sp5/pad0.25/full` | 特徴量の生成規約 |
| `DETECTOR_VERSION` | `mediapipe_fd1/<EMBED_VERSION>` | 検出器のバージョン |
| `EMBED_PADDING` | `0.25` | 顔矩形のパディング率 |
| `EMBED_MIN_FACE_PX` | `60` | 特徴量を作る最小の辺の長さ |
| `FACE_DETECTION_MAX_SIZE` | `1280` | 検出時に縮小する長辺 |
| `THUMBNAIL_MAX_SIZE` / `THUMBNAIL_QUALITY` | `160` / `85` | 保存するサムネイル |

### 矩形の正規化

検出器が返した矩形を、**正方形にしたうえで長辺を 1.5 倍**（`1 + 0.25 × 2`）に
広げ、画像内へ収めたものを dlib に渡す。この処理は1か所（`face.face_rect`）に
集約する。

**パディングを安易に変えてはならない。** 実データ950件の顔で
0 / 0.1 / 0.25 / 0.4 / 0.6 を比べたところ、0〜0.25 はほぼ同等で、
0.4 以上は急激に悪化した（0.6 では別人同士の誤一致率が 47〜59%）。
変える場合は **`EMBED_VERSION` を必ず上げる。** 上げないと古い特徴量と混ざって
照合が壊れる。

`Face.bbox_*` に保存するのは**正規化前の生の矩形**。GUI の拡大プレビューと
サムネイルはこちらを使うので、dlib が見た領域より狭い。

`DETECTOR_VERSION` が `EMBED_VERSION` を内包しているため、特徴量の規約を変えれば
`Media.detector_version` の不一致として再検出の対象になる。
`Face.embed_version` は記録のためだけにあり、再検出の判定には使わない。

### `embedding` が NULL になる条件

1. 正規化後の矩形の短辺が `EMBED_MIN_FACE_PX`（60px）未満（生の矩形でおよそ40px）
2. dlib のモデルを読み込めなかった
3. dlib の処理が例外になった

**2 は `scan` が開始時に確かめて中断する**（§5.2）。`match` は
`embedding IS NOT NULL` の顔しか見ないので、特徴量の無い顔は割り当ての対象外。

### モデルの探索順

1. 環境変数 `PHOTOARCHIVE_DLIB_MODEL_DIR`
2. 設定ファイルの `dlib_model_dir`
3. `face_recognition_models` パッケージ内の `models/`
4. リポジトリ直下の `models/`

**`face_recognition` パッケージは import しない。** `face_recognition_models` の
`__init__.py` が `pkg_resources` に依存しており、setuptools 81 以降では
`ModuleNotFoundError` になる（Issue #10 の原因）。モデルのパスは
`importlib.util.find_spec` で取り出す（モジュールを実行しないので踏まない）。

## 7.7 スキーマのバージョンと移行

**現在のスキーマ版は 2。** `PRAGMA user_version` で管理する。

`photoarchive migrate` が旧スキーマから移行する。

- 移行前に**自動でバックアップ**を取り、`PRAGMA integrity_check` を通す
- **温存するもの**: `Media` と `Person`（id ごと）。`file_hash` も残すので
  再スキャンでハッシュを計算し直さずに済む
- **破棄するもの**: `Face`（旧 `FaceEmbedding`）と `AnalysisResult`。
  旧特徴量は FaceMesh の x 座標を128個並べただけで個人識別能力が無く、
  現在の特徴量と互換性がないため
- 移行後、全 `Media` は `face_count IS NULL`（未スキャン）になる
- 最後に VACUUM する（`--no-vacuum` で省ける）
- **冪等**。移行済みのデータベースに実行しても何も起きない

実績: 773MB / `Media` 70,297件 / `Person` 5件 のデータベースが 29MB に縮み、
17秒で完了した（2026-09-19）。

スキーマ版が古いまま他のコマンドを実行すると、移行を促すエラーで止まる。
スキーマ版が新しすぎる場合も拒否する。

# 8. 家族の顔認識

## 8.1 人物の登録（実装済み）

利用者が家族を登録する（父・母・長男・長女 など）。
1人につき複数の顔を割り当てる。正面顔、年齢差のある写真、明るい写真が望ましい。

## 8.2 割り当ての流れ（実装済み）

```
[ scan ]   写真 → 顔検出 → 顔特徴量 → 未割当の顔として保存
                                        ← ここでは人物と比較しない
[ GUI ]    人物を登録し、顔を手動で割り当て（assign_source = 'manual'）

[ match ]  手動割り当ての顔とだけ比較
           → 閾値とマージンを満たせば人物判定（assign_source = 'auto'）
           → 満たさなければ未割当のまま
```

## 8.3 自動割り当て（実装済み）

### 手本

- `assign_source = 'manual'` かつ `embedding` を持つ顔だけ
- **自動割り当ての結果は手本に含めない**

### 判定

- 顔特徴量のユークリッド距離が最小の人物を候補とする
- 距離が閾値（既定 0.4）以下であること
- かつ、次に近い**別人物**との距離差がマージン（既定 0.05）以上であること
- どちらかを満たさない顔は未割当のまま残す

### 閾値 0.4 の根拠

実データで、同一写真に写る2つの顔を「別人」とみなして誤一致率を測った。

| 閾値 | 2005年（顔幅の中央値128px） | 2026年（同233px） |
|---|---|---|
| 0.40 | 1.0% | 0.5% |
| 0.45 | 2.8% | 5.7% |
| 0.50 | 9.0% | 22.7% |
| 0.60（dlib 標準） | 40.4% | 63.4% |

dlib 標準の 0.6 はこのデータでは論外。当初の既定 0.5 も緩すぎたため 0.4 にした。

**ここで測ったのは誤一致率だけで、本来割り当てるべき顔を取りこぼす率は未計測。**
取りこぼした顔は未割当のまま残るだけなので、誤って割り当てるより害が小さい。
取りこぼしが多すぎるようなら 0.45 へ緩める（ROADMAP の Phase 3）。
**取りこぼし率は `evaluate` で測る**（§8.5）。手本が入り次第、両方の率を
並べて閾値を決め直す。

**マージン 0.05 には実測の根拠がない。** 閾値に対する相対比で決めた値。

### 冪等性

実行のたびに `assign_source = 'auto'` の割り当てを一旦取り消してから付け直す。
結果は「手本の集合」と「閾値・マージン」だけで決まる。

### `assign_score`

```
assign_score = (1 - 距離 / 0.6) × 100     （0-100 に丸める）
```

**閾値 0.4 で切るため、自動割り当ての `assign_score` は最低でも 33.3 になる。**
0 にはならないので、「数値が低い顔から確認する」運用の際はこの下限を念頭に置く。
手動割り当ての顔は確信度 100 とみなす。

`family_score` は、メディアに写る顔の `assign_score` の最大値として算出し直す。

## 8.4 年齢の扱い（一部実装）

子どもの成長を考慮し、同一人物について複数年代の顔を保持できる。年代の異なる顔を
手動で割り当てておくと `match` の手本が厚くなる。

年齢は `Face.age` に持つ。**未設定（NULL）と0歳は別の状態**として扱い、
一度入れた年齢を「未設定」へ戻せる。

**未実装**: EXIF の撮影日時からの年齢の自動入力。`Person` に生年月日の列が無く、
現状では原理的に算出できない。実装するなら `Person.birth_date` の追加が前提となり、
スキーマ版を上げる必要がある。

## 8.5 精度の実測（実装済み）

閾値は**取りこぼし率と誤一致率の釣り合い**で決まる。片方だけでは決められない
（§8.3 の表は誤一致率しか測っていない）。`evaluate` が両方を同時に出す。

### 測り方: 1件抜き交差検証

手動割り当ての顔は、**正解が分かっている唯一の集合**。ここから顔を1件抜き、
残りを手本にして §8.3 と同じ判定へ通し、抜いた顔が元の人物へ戻るかを見る。

| 結果 | 意味 | 直し方 |
|---|---|---|
| 正解 | 元の人物に割り当てられた | — |
| **取りこぼし** | 閾値かマージンを満たさず未割当のまま残った | 閾値を緩める |
| **誤り**（誤一致） | 別の人物に割り当てられた | 閾値を締める |

判定は `matcher` の関数をそのまま呼ぶ。**測るものと実際に動くものがずれたら、
実測値そのものが嘘になる。**

### 数字を甘くしないための決まり

- **同じ写真に写る同一人物の顔は、既定で手本から外す。** 抜いた顔とほぼ同じ
  手本が残っていれば必ず当たる。実運用で紐づけたいのは別の写真に写った顔。
  `--keep-same-media` で残せるが、その数字は上振れする
- **自分の人物の手本が1つも残らない顔は評価から外す。** 手本が1件だけの人物が
  これに当たり、構造上かならず取りこぼす。取りこぼしに数えると率が実態より
  悪く出るため、件数だけ別に報告する

### 残る限界

**連写のように似た手本が別のファイルにある場合は、正解が実運用より甘く出る。**
同じ写真かどうかでしか近さを判定していないため。撮影日時での除外は未実装。

**手本そのものが「人が判別できた顔」に偏っている。** 小さい顔・横向き・ぶれた顔は
GUI で人物を選べないので手本にならないが、`match` の候補にはそれが含まれる。
**この測定は難しい側の顔を母集団から外している**ので、実運用の取りこぼし率は
ここで出る数字より悪くなる。**方向は必ずこちら側**なので、取りこぼしが少なく
見えても閾値を締める根拠にはならない。

# 9. 画質・表情のスコア（一部実装）

## 9.1 実装済み

いずれも顔ごとに算出し、**0-100** に収める。

**`smile_score`** — 口のランドマーク（FaceMesh の 61 / 291 / 78 / 308）の
外接矩形の縦横比から推定する。

```
smile_score = clamp(0, 100, (幅 / 高さ - 1.4) × 70)
```

**`quality_score`** — 顔領域の明るさと、画面に占める顔の大きさから、
素材としての扱いやすさを表す。

```
brightness = 顔領域の平均輝度 / 255
size_ratio = min(1, 顔の面積 / (画像の面積 × 0.12))
quality_score = min(100, brightness × 60 + size_ratio × 40)
```

**メディア単位のスコアは、写っている顔の最大値**を採用する。顔が0件なら 0。

`AnalysisResult` のスコアは `Media` 単位、`Face` のスコアは顔単位で、
**同じ名前だが粒度が違う。**

## 9.2 未実装（将来）

仕様として掲げていたが実装していない評価項目。ROADMAP の Phase 6。

- ピント
- ブレ
- 白飛び
- 目閉じ

これらの係数（`1.4` / `70` / `60` / `40` / `0.12`）は実データでの調整を経ていない。
Phase 3 の精度確立と合わせて見直す。

# 10. 顔登録GUI（実装済み）

## 10.1 位置づけ

`photoarchive-gui` は解析エンジンから独立した補助ツール。人物の登録と顔の
割り当てだけを担当し、**写真の解析や抽出は行わない。**

PySide6(Qt) で実装する。

## 10.2 機能

- 人物の一覧表示・追加・編集・削除（削除しても顔は消さず、未割当に戻す）
- 未割当の顔の一覧表示と、人物への割り当て
- 割り当ての解除
- 誰でもない顔の除外
- 割り当て済みの顔の一覧表示と、自動割り当ての確定
- 年齢の設定

## 10.3 顔の割り当て

GUI は **`scan` が検出して貯めた顔**を人物へ割り当てる。
利用者が画像ファイルを選んで顔を切り出す操作は行わない。
検出と特徴量生成の規約を `scan` と GUI で一致させるためである。

推奨は1人あたり 20〜50枚。正面・左右・笑顔・真顔・明るい写真・年齢の異なる写真を
混ぜるとよい。割り当てた顔は `assign_source = 'manual'` になる。

## 10.4 一覧のページング

**顔は数万件になりうる。一覧は必ずページ単位で読み出す。**
サムネイルの BLOB を全件読むと数百MBになり、画面が固まる。

```
[顔][顔][顔][顔][顔][顔]
[顔][顔][顔][顔][顔][顔]

 < 前    3 / 310 ページ（全 61,842 件）    次 >
```

- 1ページあたり 200 件
- 並び順は**品質スコアの高い順**。大きく明るい顔から出るので割り当てが進めやすい
- 表示の切り替えで「未割当」「自動割当」「除外済み」を選べる
- 顔を選ぶと、元写真から切り出し直して拡大表示する
- **割り当て済みの一覧にもページャがある。** 無いと201件目以降に手が届かない

## 10.5 割り当て済みの確認

人物を選んで「割り当て済みを確認」を開くと、サムネイル一覧を表示する。
顔を選ぶと次の操作ができる。

- **確定**（`'auto'` を `'manual'` に昇格し、次回の `match` の手本にする）
- 割り当ての解除（未割当に戻す）
- 年齢の設定（未設定へ戻すこともできる）

年齢で絞り込めるが、**年齢が未設定の顔は絞り込んでも常に表示する。**
消えてしまうと、そもそも年齢を入れられなくなるため。

## 10.6 GUI が更新するテーブル

- `Person`
- `Face` の `person_id` / `assign_source` / `assign_score` / `assigned_at` / `age`

**`Media` と `AnalysisResult` は更新しない。** 顔の検出結果そのもの
（座標・特徴量・サムネイル）も GUI からは書き換えない。

その結果、GUI で割り当てを解除しても `family_score` は次に `match` を実行するまで
古いままになる（§7.4）。

## 10.7 将来の拡張

顔候補の自動推薦、「この人は○○ですか？」の確認画面、類似人物の統合、
家族関係ツリーの表示、人物検索、人物ごとの写真枚数表示。

# 12. 抽出（一部実装）

## 12.1 ルール

抽出は JSON（または YAML）のルールで制御する。

```json
{
  "date": { "start": "2014-01-01", "end": "2023-12-31" },
  "family_only": true,
  "count_per_year": 40,
  "include_video": true,
  "remove_duplicate": true
}
```

| キー | 既定 | 意味 | 状態 |
|---|---|---|---|
| `date.start` / `date.end` | 制限なし | 撮影日時（無ければ作成日時）の範囲。日付が読めないメディアは範囲外 | 実装済み |
| `include_video` | `true` | 動画を含めるか | 実装済み |
| `family_only` | `false` | `family_score > 0` のメディアだけにする | 実装済み |
| `remove_duplicate` | `false` | ハッシュが同じメディアを1件にまとめる（§11） | 実装済み |
| `count_per_year` | 制限なし | 1年あたりの上限件数 | 実装済み |
| `purpose` | — | 用途プリセット（§13） | **未実装** |

並び順は `family_score` → `quality_score` → `smile_score` → `face_count` の降順。
`count_per_year` はこの順で各年の上位から採る。年ごとの件数を揃える処理は
入っていないので、元の件数が少ない年はそのままになる。

**`family_only` は現状ほぼ機能しない。** 閾値 0.4 で切ると `assign_score` の下限が
33.3 になるため、`family_score > 0.0` が「割り当てが1つでもあれば通る」と同義に
なっている。判定の見直しは ROADMAP の Phase 3。

## 12.2 出力

- **入力データは変更しない。** 出力先へコピーする
- 出力先での配置は、`source_root` からの**相対パスをそのまま再現**する
- 名前が衝突する場合は `photo_1.jpg`、`photo_2.jpg` のように空いている連番を付ける

**未実装（将来）**: 用途別・年別のディレクトリ構成（`Output/Movie/2016/`）と、
コピーの代わりにシンボリックリンクを張る出力。ROADMAP の Phase 6。

# 15. 非機能要件

## 15.1 想定する規模

実データ（2026-09-19 時点の実測）。

| 項目 | 値 |
|---|---|
| メディア件数 | 70,297 |
| 総容量 | 441GB（画像 219GB / 動画 222GB） |
| 顔の件数 | 約 62,000 |
| メディアの置き場所 | NFS |

## 15.2 処理時間の実測

| 項目 | 実測 | 全件換算 |
|---|---|---|
| NFS 読み出し | 24 MB/s | 画像 2.5h / 動画 2.6h |
| JPEG フルデコード | 0.094〜0.205 s/枚 | 1.7〜4.0h |
| MediaPipe 顔検出 | 0.020〜0.030 s/枚 | 0.4〜0.6h |
| dlib 特徴量 | 0.130 s/顔 | 2.2h |
| SHA-256 | 0.012 s/枚 | 0.2h |

**IO が律速。** 1回読み + 差分判定 + `--workers 4` で全件 2.5〜3.5時間の見込み。
2回目以降のスキャンは数十秒。

デコードを速くする最適化（`Image.draft()` による DCT スケーリング）は、
検出結果は一致するものの**同じ顔の特徴量の距離が平均 0.13・最大 0.38 動いた**ため
採らなかった。閾値 0.4 に対して無視できず、IO が律速である以上デコード時間は
並列化で吸収できる。

顔1件あたりのデータベース増分は約5KB（サムネイルの実測平均が 3.3KB）。

## 15.3 中断と再開

顔検出が終わったメディアは逐次コミットされるので、`scan` を中断しても
再実行すれば続きから再開する。

## 15.4 ログ

`scan` と `match` は `data/logs/<コマンド>_<日時>.log` に出力する。
既定のログレベルは `WARNING`。ログの世代管理は行っていない。
