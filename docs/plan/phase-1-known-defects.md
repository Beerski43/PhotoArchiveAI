# Phase 1 — 既知の欠陥修正（Issue #30 で実施）

状態: **実施中**

Phase 0 の調査で、場所まで特定できた欠陥。**実データでの全件スキャン（Phase 3）に
進む前に潰す必要がある。**特に A1 は、441GB を NFS 24MB/s で読む環境では
毎回のスキャンを全読みに戻してしまう。

修正1件につきテストを1件以上足す。**テストの無い修正は入れない。**

## 欠陥の一覧

### A1 — mtime だけ変わったファイルが毎回フルリードされる

`db.py` の `save_media` は `file_hash` が変わったときだけ行を更新する。
ファイルを touch しただけだと、

1. サイズと更新時刻の一致判定（`scanner.py` の `MTIME_TOLERANCE_SECONDS`）を外れて
   「変わったかもしれない」と判断され
2. SHA-256 のために全体を読み
3. ハッシュが同じなので `created_time` が DB に書き戻されず
4. 次回もまた 1 に戻る

**恒久的に毎回フルリードになる。** 影響: `README` の「2回目以降は短時間で終わります」
という前提が崩れる。

### A2 — `convert-heic` が DB パスを要求して落ちる

`cli.py` が全サブコマンド共通で DB パスを解決し、空なら `SystemExit` する。
`convert-heic` は DB を一切触らないのに、`config/app_settings.json` が無い環境では
`Database path is required` で落ちる。README は「scan の前に convert-heic」と
案内しているので、**手順どおりに実行すると失敗しうる。**

### A3 — dlib モデルが読めないと、顔が無言で全損する

`face.py` はモデルを読めなかったとき特徴量に `None` を返す。一方で
`scanner.py` の再検出判定は `Media.detector_version` しか見ない。よって

- 全顔が `embedding = NULL` のまま保存され
- `Media.face_count` は N（スキャン済み）として記録され
- `match` は `embedding IS NOT NULL` の顔しか見ないので、全件が未割当のまま
- `--force-rescan` を手で付けない限り、二度と回収されない

**エラーも警告も出ない。** `scan` の開始時にモデルの有無を確かめて中断する。

### A4 — GUI だけ設定ファイルを読まない

CLI は `--db` → `config/app_settings.json` の順に解決するが、GUI は `--db` が必須で
設定ファイルを見ない。仕様書 §2.3 の「アプリケーション内に DB パスをハードコード
しない」の趣旨から外れる。

### A5 — 設定ファイルの探索がカレントディレクトリ依存

`config.py` の `DEFAULT_CONFIG_PATH` が相対パス1つだけ。リポジトリルート以外から
`photoarchive` を起動すると、**例外にならず空の設定が返る**。
仕様書 §2.3 は「パスを変更するには `config.py` を編集する」と書いており、
同じ節の「ハードコードしない」と矛盾していた。

探索順を決める: 環境変数 `PHOTOARCHIVE_CONFIG` → カレントディレクトリ →
リポジトリルート。

### A6 — `match --dry-run` が2回目以降ほぼ空振り

`matcher.py` は dry-run のとき自動割り当てを取り消さない。一方で候補は
「未割当の顔」だけ。よって一度 `match` した後に `--dry-run` すると、
既に auto が付いた顔が候補から外れ、件数も距離の分布も過小になる。
README は「`--dry-run` は距離の分布を表示するので `--threshold` を決める目安になる」
と案内しているので、用途と食い違う。

### A7 — `detection_score` が全行 NULL

`face.py` の `detect_faces` が MediaPipe の `detection.score` を捨てている。
仕様書 §6.3 は `detection_score` を保存項目として挙げているので、実装が仕様を
満たしていない。

### A8 — `Error: none` が全コマンドで出る（Issue #25）

`cli.py` の進捗表示が、エラーが無いときに毎回 `Error: none` で2行目を塗り潰す。
直近のエラーを保持して上書きしない。
なお、エラー文字列は `cli.py` で120文字に切られるが、`face.py` が先に80文字へ
切っているので120の方は効いていない。

### A9 — 割り当て済み一覧にページャが無い

`gui.py` の `RegisteredFacesDialog` は `limit` だけで `offset` を持たない。
**201件目以降の割り当て済みの顔に到達できない。** 仕様書 §8.5 の
「顔は数万件になりうるため、一覧は必ずページ単位で読み出す」の趣旨からも外れる。

### A10 — 年齢を「未設定」へ戻せない

`db.py` の `assign_faces` は `age is None` のとき age 列を UPDATE 文から外すため、
一度入れた年齢を「未設定」に戻せない。同じ GUI でも `set_face_age` を通る経路なら
戻せるので、**同じ画面で操作によって挙動が違う。**
仕様書 §8.7 の「未設定と0歳は別の状態として扱う」に照らすと、未設定へ戻す操作が
欠けている。

## あわせて片付ける小物

- `matcher.py` の進捗の分母が `embedding IS NULL` の顔を含むため 100% に届かない
- チャンクサイズ 5000 が `matcher.py` と `db.py` に二重定義されている
- `selection.py` の出力先の衝突回避が「コピー済み総数」を連番に使っていて、
  一意性が保証されない命名になっている
- コードだけ「教師データ」、文書は「手本」。**「手本」に統一する**

## やらないこと

- **`Person.name` の UNIQUE 制約。** 既存DBに同名人物がいると移行が必要になり、
  スキーマ版を上げる話になる。Phase 3 で判断する
- スキーマの変更全般。この Phase の修正はすべてスキーマ非破壊
