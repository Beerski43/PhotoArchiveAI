## 決めたこと

- **長い処理の実行中も、顔の割り当てなどの操作は続けられる**（利用者の決定・2026-11-03）。代わりに書き込みが重なったときの作りが要る:
  - 裏の `scan` は **1件ごとに commit する**（`scanner.scan_directory(commit_interval=1)`。CLI は今までどおり 50 件ごと）。書き込みロックを握るのを1件ぶんにする
  - 画面の接続は、ほかの書き込みを最大 30 秒待つ（`busy_timeout`）
  - **待ちきれなければ、書きかけを rollback して知らせる**（`gui.report_unhandled_error`・`sys.excepthook` で受ける）。以前は画面の書き込みが例外を受け止めず、書きかけが次の操作の commit に混ざりえた（CLI の `scan` を GUI と同時に流したときに起きうる）
  - **実行中は `match` を押せない**（`scan` が顔を足し消ししている途中の手本で照合しない・`match` は長く書き込みロックを握る）
- **裏の処理は別プロセス（`spawn`）で流す**（`jobs.Job`）。同じプロセスの別スレッドにしない: 画面の接続と同じプロセスで書き込みが走り、`scan` のワーカーまで抱えることになる。別プロセスなら端末で CLI を流すのと同じ形。**daemon にしない**（daemon の子は `scan` のワーカーを作れない）
- **止めても次は続きから。** もともと `scan` は 50 件ごとに commit し、`ScanRoot` の記録と消えた行の削除は最後まで走査したときだけだった。止め方（`should_stop`）を足せば足りた。並列のときは残りの仕事を捨ててから抜ける（`with ProcessPoolExecutor` のまま抜けると、残りを全件処理し終えるまで待つ）
- **流したまま閉じない。** 閉じるときに実行中なら聞き、止めるなら止まるのを待つ（子を殺さない）。GUI が落ちたら、子は親のプロセス番号が変わったのを見て自分で止まる
- GUI に出さない `scan` の引数: `--force-rescan`（顔の行を作り直し、手動割り当てと顔認証外が消える・CLAUDE.md §8）・`--force-prune`・`--allow-missing-embeddings`。CLI で使う
- **9.2: `convert-heic` と `assess` は取り込みタブに `scan` と並べる**（上から一連の流れの順に 変換 → スキャン → 良し悪し）。別のタブにしない: 3つとも同じ root を使い、同時に流せるのは1つなので、1か所にあるほうが「いま何が流れていて、次に何を押すか」が見える
- **9.2: `convert-heic` は裏で聞き返せない。** CLI は読めない HEIC と書けない JPEG を1件ずつ `[y/N]` で聞く。GUI では**読めない HEIC は飛ばして一覧に残し**（1枚の壊れた写真で何時間もの変換を止めない）、**JPEG が書けなければ止める**（読み取り専用・空き容量の不足で、続けても書けない。CLI の既定の答え N と同じ）。利用者が別の扱いを望めば変える
- **9.2: `assess` はモデルが無ければ始める前に止める**（子で落ちるより早く、置き方を出す）。止める合図では**書きかけの塊を書いてから**抜ける

- **9.3: 設定はタブではなく、タブの左上の `設定…` から開く窓**（利用者の決定・2026-11-03）。右上は裏の処理の進み具合なので左上に置いた（こちらの判断）
- **9.3: 保存したら DB の場所以外はすぐ効かせ、DB の場所は次に起動したときから**（利用者の決定）。3枚のタブが同じ接続を持ち、裏の処理も DB のパスで子を起こすので、開いたまま差し替えると食い違う
- **9.3: 書く前に `.bak` に控え、コメントは消える**（利用者の決定・ルールの保存と同じ・依存を増やさない）。窓に出さないキーは残す。**読めない設定ファイルには書かない**
- **9.3: 出力先が root と重なるのを保存の時点で止める**（`select` のコピーの直前にも同じ検査がある。保存の時点で気づけるほうが早い）。無いフォルダは聞くだけ（NFS が外れているだけのことがある）。**DB の場所を空にしては保存させない**（PR #138 のレビュー指摘2・利用者の決定）

- **9.4: タブは顔の割り当てと写真の選定の2枚だけ。ほかはメニューから別の窓で**（利用者の決定・2026-11-04・原文は仕様書 §5.10）。これで 9.2 の「取り込みタブに3つ並べる」と 9.3 の「タブの左上の `設定…`」は置き換わった
- **9.4: `assess` は取り込みウィザードに入れず、メニューの別項目**（利用者の決定）。測るのは家族の写った写真だけで、新しい写真は顔を割り当てて `match` するまで対象にならない
- **9.4: ウィザードと別の窓は閉じても裏の処理を止めない。** 何時間もの `scan` のあいだ窓を出しておく理由が無い。閉じたあとの結果はステータスバーの1行と、開き直した窓で見る（こちらの判断）。`QWizard` の既定は閉じると最初の段へ戻すので、`reject` を上書きして隠すだけにした
- **9.4: `evaluate` も裏で流す。** 手本 16,720 件で約 46 秒（2026-11-04・実データの複製）。止めたら途中の数字は出さない（手本の前のほうだけの率になる）
- **9.4: `unassign-auto` は確認の窓で控えを既定で取る**（`match` と同じ形・利用者の決定）。CLI には控えが無い。取り消しと数え直しは1つのトランザクションで書く（`db.unassign_auto`。**CLI も同じ関数**）

## 確かめたこと（心配しなくてよいもの）

- **写真の選定タブの「選ぶ」の前の測定は、裏の `scan` をほぼ待たせない**（PR #133 のレビュー指摘2・コードを読んでの判断で、実データでの時間は測っていない）。見え方（`appearance.fill_missing`）・表情（`expression.fill_missing`）・写真の見た目（`selection` の `look_hash`）は、どれも**測る段はトランザクションの外**で、500 件ずつ書いてすぐ commit する。書き込みロックを握るのは 500 行を書くあいだだけ
- **人物の追加・編集は1つのトランザクションで書く**（PR #133 のレビュー指摘1）。以前は人物と区分・重みを別々に commit していて、2つ目が書き込みロックで落ちると人物だけが残り、「何も変えていません」の知らせが事実と違っていた。**画面の1つの操作で2回 commit する経路を足さないこと**（足すなら `commit=False` で1つにまとめる）
