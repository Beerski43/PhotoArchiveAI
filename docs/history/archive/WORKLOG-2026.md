## 2026-10-08 — 未割当の画面に撮影年月の絞り込みを足す

**#63・PR #64 に対話で追加。** 利用者から「**先に家族じゃない顔を除外したいので、
GUI 起動直後の未割当の画面に撮影年月のフィルタがほしい**」という依頼。

**家族の写っていない写真は時期でまとまっている。** 結婚式や旅行先で写った他人は
その行事の期間に固まるので、**その月だけを開いてまとめて除外できる。**

- `db.month_expression()` を足した。**読めない撮影日時を月として扱わない**
  （`substr(shooting_date, 1, 7)` と書くと「TTTT-TT」という月が並ぶ。
  判断は `SHOOTING_DATE_SORT_KEY` に1つだけ）
- `db.available_months()` / `db.count_undated_faces()`。
  **顔のある写真の月だけ**を新しい順に出す（実データで250個）
- `_face_filter` に `month` を通した。`UNDATED` で「撮影日時なし」
  （**`None`＝絞らない と同じ値で表さない**）
- GUI の未割当の画面に `いつから` 〜 `いつまで` の2つの欄を置いた。**両端を含み、
  片方だけの指定もできる。** 上下が逆転したら押し戻す（黙って0件にすると
  絞り込みが壊れて見える）。**種別や行事と併用できる**
- `撮影日時なしのみ` はチェックボックスで別に持つ。**範囲とは排他**

### 「撮影日時なし」の実体と、フォルダ名からの復元（判断待ち）

利用者から「撮影日時なしとは写真のメタデータが無いという理解でよいか。その場合
**フォルダ名に年月が入っているはずなので特定できる**のでは」と問われた。

内訳は `shooting_date IS NULL` が 11,090 件、壊れた値が 67 件
（`0000-00-00T00:00:00` と `TTTT-TT-TTTTT:TT:TT`）。**理解のとおり。**

フォルダ名からの復元は**着想として正しい**が、即席の正規表現で測ったところ
**すでに誤りが出た**（`/Photo/2010/2010.jpg` のファイル名を `YYMM` と誤読して
2020-10 にする、`20260100` のような `YYYYMMDD` を取りこぼす、など）。
**日付の読み取りはこのリポジトリが2度壊れている箇所**なので、別途きちんと
設計すべき作業として **#65 に起票した**（利用者の指示。Phase 3 手順9・
ROADMAP と phase 文書にも入れた）。**着手は指示待ち。**

調べて分かったこと。

| フォルダ名の形（顔のある3,746件） | 件数 |
|---|---|
| `YYYYMMDD…` / `YYMMDD…` / 4桁 / 2桁（いずれも4桁年の下） | **3,619（96.6%）** |
| 数字で始まらない | 169 |

**4桁フォルダ（`2012/1210/`）は `YYMM`。`MMDD` ではない。**
EXIF が読める写真400件で照合して 400/400 一致、`MMDD` は0件だった。
**規約を推測で決めず、この検算の形を実装の検証にも使うこと。**

**`Media.shooting_date` に書き戻してはいけない**（EXIF から読めた値と、
フォルダ名から推測した値を同じ列に混ぜると、どちらか分からなくなる。
`Face.age` と計算年齢を分けているのと同じ理由）。

### あわせて答えたこと: 手本が増えても、流し直すまで精度は上がらない

利用者から「**年齢ごとの確定写真が増えたので検出精度は上がらないのか。現在確定して

ただしまだ反映されていない。**

```

```

### 他人の顔をまとめて除外する戦略は成立しない（測定）

利用者から「**誰でもない写真を該当なしに登録し続けるには無理がある**」との指摘。
**そのとおりで、しかも構造的にまとめて消せない。**

| 未割当 31,275 件の在りか（2026-10-08） | フォルダ数 | 未割当 |
|---|---|---|
| **家族が1人も写っていないフォルダ** | 73 | **280 件（0.9%）** |
| **家族も写っているフォルダ** | 903 | **30,995 件（99.1%）** |

```bash
# 数え直す
sqlite3 data/photoarchive.db "
SELECT SUM(u) FROM (SELECT SUM(f.assign_source IS NULL) u,
  SUM(f.person_id IS NOT NULL) fam FROM Face f JOIN Media m ON m.id=f.media_id
  GROUP BY rtrim(m.path, replace(m.path,'/','')) ) WHERE fam = 0;"
```

**他人の顔のほぼ全部が、家族の写真に混ざっている。** 結婚式・マラソン大会・忘年会の
ような「まるごと他人」のフォルダは 73 個しかなく、一掃しても 280 件しか減らない。
**フォルダ単位でも年月単位でも、まとめて消す戦略は成立しない。**

**そして、その必要がない。** `select` は `family_score` で選び、これは
**人物が付いた顔からしか計算されない**（`recompute_family_scores` の
`WHERE person_id IS NOT NULL`）。**未割当の顔は製品の目的に一切影響しない。**
除外は「未割当のリストを短くする」ためだけの作業。

### 人物登録を増やすと精度は上がるか（利用者の問い）

**部分的に上がるが、仕組みは期待とは違う。** いまの誕生日の照合は
**「その人が生まれる前の写真には写れない」という除外だけ**で、
**顔から年齢を推定して「当時N歳だった人を優先する」ことはしていない。**

| | |
|---|---|
| 上がる | その人の顔が家族の誰かに誤って付いているなら、正しくその人へ移る |
| 上がらない | 家族同士の取り違え。これは各人の**手本の年齢カバー率**の問題 |
| 要る手間 | 新しい人物ごとに手本を人手で与える必要がある |

### #66 を起票した: 閾値は年齢ごとであるべき

## 2026-09-20 — #39 全件スキャンの実施と、並列スキャンがDBを壊す欠陥の修正

Phase 3 の手順1（全件スキャン）を実施した。`source_root`（`${SURNAME}Family`、
64,974件）は**未スキャン0件**まで到達し、顔 55,812 件を検出した。
別ソースの `photo_person2` 5,210 件は `source_root` が1つしか持てないため未着手
（Issue #24）。

**その途中で、DBが2回壊れた。** どちらも同じ壊れ方で、
`row N missing from index idx_media_hash` → `scan` が
`database disk image is malformed` で異常終了。46,184件の地点と55,788件の地点。

**原因は `scan` の並列実行。** `scanner.py` は **DB接続を開いたまま**
`ProcessPoolExecutor` を作る。Linux / Python 3.12 の既定は `fork` なので、
**全ワーカーが親の SQLite 接続と WAL の共有メモリを複製して持つ。**
ワーカー自身はDBに触らないが、子の終了時に引き継いだ接続の後始末が親の
書き込みと競合する。SQLite は接続を `fork()` をまたいで持ち越すことを禁じている。
ディスクI/Oエラーもカーネルエラーも無く、ハードウェア障害ではない。
`--workers 1`（プールを作らない経路）では最後まで通り、破損も起きなかった。

直し方は `mp_context=multiprocessing.get_context("spawn")`。子は白紙の
インタプリタとして始まるので、親のファイル記述子を引き継がない。

**この修正で、既存の並列テスト2件が `fork` に依存していたことが露見した。**
子がフェイクの mediapipe / dlib を引き継ぐ前提で書かれており、`spawn` では
実物を読みに行く。フェイクを `tests/fakes.py` へ切り出し、`scan_directory` に
`worker_initializer` を足して子へ入れられるようにした。

**壊れないことはテストで確かめられない**（数万件規模でしか再現しない）ので、
「`fork` で起こしていないこと」と「子が親のメモリ状態を引き継がないこと」を
テストで固定した。どちらも `WORKER_START_METHOD` を `fork` に戻すと落ちることを
確認している。CLAUDE.md の落とし穴「並列実行では fork 時の値が全ワーカーに
複製される」も、`spawn` では成り立たないので書き換えた。

破損したDBは保全したうえ、`REINDEX idx_media_hash` で復旧した
（テーブルの行は無傷だった）。**保全した2つはレビューでの判断を経て消した。**
原因が特定できてテストで固定できた以上、289MB×2 を持ち続ける理由が無い。
消す前に `PRAGMA integrity_check` の出力だけ残す。

```
data/photoarchive.db.bak-corrupt-20260920_001155  → row 67992 missing from index idx_media_hash
data/photoarchive.db.bak-corrupt2-003728          → row 65679 missing from index idx_media_hash
現行 data/photoarchive.db                          → ok
```

どちらも**インデックスの欠けだけ**で、テーブルの行は壊れていない。
同じ症状がまた出たら、まずこの形（`row N missing from index ...`）かどうかを見る。

回帰テスト: 200 passed / 0 failed (4.39s)。`spawn` の起動ぶん約1秒増えたが
10秒の枠内。

**修正後に実データで `--workers 4` を流して確かめた。** 対象は未スキャンだった
別ソース `photo_person2` の 5,210 件（並列経路の実地検証と、残っていたデータの
消化を兼ねた）。最後まで通り、`PRAGMA integrity_check` は `ok`。
速度も 9 件/秒で、`--workers 1` の 3 件/秒より速い。
**これで Media 70,297 件すべてが未スキャン0件になった**（顔 58,606 件）。

**レビュー（PR #37）で、この修正の副作用が1件見つかった。** `spawn` の子は
**ログの設定も引き継がない**ので、`--workers` が2以上（＝既定）のとき
ワーカーが出した警告がログファイルに1行も残らなくなっていた。書式なしの
stderr へ漏れて進捗表示に混ざるだけで、「どのファイルがなぜ読めなかったか」
という記録そのものが消える。実データ 5,210 件の検証で `errors 10` と出ていたが、

`_setup_logging` を `logging_setup.py` へ切り出し、ワーカーの入口

撮影日時は `Media` 側にあるので結合が要る。**素直に書くと、ページを送るたびに
未割当の顔を全件並べ直す。**

| 実データ（未割当 58,547 件）の1ページ | 索引なし | 式インデックス＋`CROSS JOIN` |
|---|---|---|
| 1ページ目 | 219ms | **0.7ms** |
| 100ページ目 | 361ms | **68ms** |
| 最終ページ付近 | 436ms | **197ms** |

- **`CROSS JOIN` は結合順の固定が目的**で、直積を作るわけではない。外すと
  SQLite が `Face` を外側に選び、元の遅い計画に戻る。問い合わせ計画を見る
  テストで固定した
- **`ANALYZE` を実行しないこと。** 統計があるとブルームフィルタを挟む計画に
  変わり、1ページ目が 0.7ms → 47ms に落ちた

返す式）にして、読めない値は「日時なし」と同じ最後へ送った。**式インデックス**
なので速度は変わらない。

**本筋の外だが直した**（CLAUDE.md §3.2）。`gui._format_timestamp` が
`0000` で始まるかだけを見ていたので、**この壊れ方は素通りして画面にそのまま
出ていた。** 日付として読めるかどうかで判断するようにし、並び順と表示で
「読める」の意味をそろえた。

**移行は要らない。** 列は増えず、索引はデータベースを開いたときに作られる

### 人物一覧をドラッグで並べ替えられるようにした

よく割り当てる人物を上に置けないと、人数が増えるほど毎回探すことになる。

## 2026-09-20 — 割り当て・除外に砂時計と進み具合を出し、17秒かかっていた原因を直す

「クリックできたかが分からない」という指摘から測ったところ、**1回の操作に
17秒かかる経路**が見つかった。マージ後に実データの移行が要る件は

## 2026-09-20 — 除外を取り消せるようにする（未割当に戻す）

「一度除外した顔を未割当に戻せるか」と聞かれて調べたら、**戻せなかった。**

## 2026-09-19 — #30 PRレビューの手順をスキル化

PR #31 のレビューで使った進め方を `.claude/skills/pr-review-comment/` に
スキルとして固定した。`/pr-review-comment` で呼ぶ。

**指摘を書く前に手元で再現する**ことを手順の核心に据えた。#31 のレビューでは、
実行して見つけた「集計行が端末では必ず 0 passed」は採用され、想像で書きかけた
「`EMBED_VERSION` を上げても再スキャンされない」は `DETECTOR_VERSION` の定義を
読んで取り下げた。**出してよい指摘と出してはいけない指摘を分けるのは検証だけ**
という経験を、そのまま手順にしている。

出力の形も決めた。重要度（🔴 必須 / 🟡 推奨 / 🟢 任意 / 🔵 判断）の表を先頭に置き、
詳細は後ろへ回す。指摘は新しい Issue に切り出さず、そのPRの中で片付ける前提で書く
（文脈が失われると直りが遅れるため）。判断が要るものは選択肢と推奨をセットで出す。

**レビューは白紙の文脈で始める**ことも前提に加えた。実装した本人が続けて
レビューすると、意図を覚えている分「動くはず」と思い込んで検証を省く。
#31 で最も効いた指摘も、PR 本文の実行結果を鵜呑みにせず走らせたから見つかった
もので、書いた本人なら見逃していた。実装したセッションで呼ばれたら、
`/clear` かまっさらなサブエージェント（`fork` は不可）を促して止まる。

次にやること: ROADMAP の Phase 2 残り（`face.py` の実物経路、`scoring.py` の
計算式、`gui.py` の未検証クラス）。着手時に Issue を起票する。

## 2026-09-19 — #40 取りこぼし率を測る evaluate を作る（Phase 3 着手）

Phase 3（実データでの精度確立）に着手し、親 Issue #35 を起票した。
（この作業ぶんは後から子 Issue #40 に切り出した。当時はまだ
「1 Issue - 1 ブランチ - 1 PR」の規則が無く、#35 に直接ぶら下げていた）
このフェーズは全件スキャンと手動割り当てが要で、**実データと人手が要る**。
先に片付けられるのは手順4の「取りこぼし率の実測」だけなので、
`photoarchive evaluate` を実装した。

**既定の閾値 0.4 の根拠は、片側しか測っていなかった。** #28 で測ったのは
誤一致率（同一写真に写る別人同士が閾値を下回る割合）で、**本来紐づくべき顔を
落とす率は一度も測っていない。** 閾値を下げれば誤一致は減り取りこぼしは増える
ので、片側だけでは 0.4 が妥当かも 0.45 へ緩めるべきかも判断できない。

測り方は1件抜き交差検証。手動割り当ての顔は**正解が分かっている唯一の集合**
なので、そこから1件抜き、残りを手本にして `match` と同じ判定へ通し、元の人物へ
戻るかを見る。結果を「正解 / 取りこぼし / 誤り」に分け、閾値ごとに並べる。
判定は `matcher._distances` と `_best_match` をそのまま呼ぶ。**測るものと実際に
動くものがずれたら、実測値そのものが嘘になる。**

**素直に作ると数字が甘く出る。** 抜いた顔と同じ写真に写る同一人物の手本が
残っていれば必ず当たり、取りこぼし率が0に見える。既定で外すようにし、
`--keep-same-media` で残した場合との差をテストで押さえた。手本が1件だけの
人物も、抜くと手本が0件になって**構造上かならず**取りこぼすので、率に混ぜず
件数だけ別に報告する（混ぜると取りこぼし率が実態より悪く出て、閾値を
緩めすぎる方向に判断が傾く）。

Issue のコメントでは「同一 `media_id` の顔を外す」と書いたが、実装では
**同一人物のものだけ**を外した。同じ写真に写る別人の手本は、実運用でも競合
として存在するので外すと判定が甘くなる。理由は Issue #35 にも残した。

残る限界は連写。似た手本が**別のファイル**にあると正解が甘く出るが、いまは
同じ写真かどうかでしか見ていない。撮影日時での除外が要るかは、実データの
数字を見てから判断する。

回帰テスト: 212 passed / 0 failed (3.48s)。

次にやること: 全件スキャン（未スキャン 69,347 件）→ GUI で人物ごとに20〜50枚を
割り当て → `photoarchive evaluate` で閾値を確定。**ここから先は実データの作業。**

## 2026-09-06 — #14 HEIC/HEIF の一括変換と、#10 の真因特定
