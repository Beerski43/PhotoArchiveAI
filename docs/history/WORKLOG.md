## 2026-09-20 — #53 顔一覧の並び順を、画面の目的に合わせる

| 画面 | いままで | これから |
|---|---|---|
| 未割当の顔（割り当てる画面） | 品質スコアの高い順 | **撮影日時の新しい順** |
| 割り当て済みを確認 | 品質スコアの高い順 | **年齢の若い順** |

**PR が2本同時に出ている。** マージの順序と rebase の注意は
[details/2026-09-20-two-prs-in-flight.md](details/2026-09-20-two-prs-in-flight.md)。

品質スコア順だと、同じ人の同じ日の写真がページをまたいで散らばる。撮影日時順なら
**同じ行事の写真が固まる**ので、まとめて選んで一度に割り当てられる。撮影年を
またがないので、#48 の「年齢の初期値」も1つに定まって効く。割り当て済みのほうは
**成長の順に並ぶ**ので、年齢の入れ間違いや別人の混入に気づきやすい。

`db.list_faces` に `order` を足した。**既定は変えない**（`match` と `evaluate`
も同じ関数を通る）。読めない値（撮影日時なし・年齢未設定）は**最後に置く**。
先頭に来ると、順に見ていく邪魔になる。

### 速く保つのに要ったもの

撮影日時は `Media` 側にあるので結合が要る。**素直に書くと、ページを送るたびに
未割当の顔を全件並べ直す。**

| 実データ（未割当 58,547 件）の1ページ | 索引なし | 式インデックス＋`CROSS JOIN` |
|---|---|---|
| 1ページ目 | 219ms | **0.7ms** |
| 100ページ目 | 361ms | **68ms** |
| 最終ページ付近 | 436ms | **197ms** |

- **`CROSS JOIN` は結合順の固定が目的**で、直積を作るわけではない。外すと
  SQLite が `Face` を外側に選び、元の遅い計画に戻る。問い合わせ計画を見る
  テストで固定した
- **`ANALYZE` を実行しないこと。** 統計があるとブルームフィルタを挟む計画に
  変わり、1ページ目が 0.7ms → 47ms に落ちた

### 壊れた EXIF が「いちばん新しい」になっていた

実測の途中で見つけた。カメラが **`TTTT-TT-TTTTT:TT:TT`** を書くことがあり
（実データで Media 67件・顔123件）、文字の大小で並べると `T` は数字より大きいので
**新しい順の1ページ目をまるごと占領する。**

索引と `ORDER BY` を `db.SHOOTING_DATE_SORT_KEY`（日付として読めるものだけを
返す式）にして、読めない値は「日時なし」と同じ最後へ送った。**式インデックス**
なので速度は変わらない。

**本筋の外だが直した**（CLAUDE.md §3.2）。`gui._format_timestamp` が
`0000` で始まるかだけを見ていたので、**この壊れ方は素通りして画面にそのまま
出ていた。** 日付として読めるかどうかで判断するようにし、並び順と表示で
「読める」の意味をそろえた。

**移行は要らない。** 列は増えず、索引はデータベースを開いたときに作られる
（実データで 0.07秒、増分 4KB）。`PRAGMA user_version` は上げていない。

GUI で誕生日を入れても、次に編集を開くと空欄に戻る、という報告。原因は
**`db.create_tables` が、移行していないデータベースに `PRAGMA user_version` を

**これで `migrate` が効かなくなる。** 「すでに最新です」と答えて列を足さないので、

既存の検査に引っかかっていたが、**版を刻むようになった 2 から先へ進むのは
今回が初めて**だった。

- **既にテーブルのあるDBには版を刻まない。** 版が古ければ移行を促して中断する
- **移行が要るかは、版と実際の列の両方で見る**（`db.missing_columns`）。
  すでに刻まれてしまったDBも、列を足して直せる
- **列の一覧は `SCHEMA` から作って読み取る。** 書き写すと片方だけ古くなる

**1秒・無損失**、`integrity_check` も ok。

1つの欄に `YYYY-MM-DD` と打たせると、**区切りの書き方を間違えただけで弾かれる。**

残る限界は連写。似た手本が**別のファイル**にあると正解が甘く出るが、いまは

## 2026-09-19 — #28 scan と analyze の処理順を転換し、自動紐づけを match へ分離

PR [#29](https://github.com/Beerski43/PhotoArchiveAI/pull/29)（merged）。

旧 `analyze` は **人物が1人も登録されていない段階で人物への紐づけを行っていた**。
`scan`（登録＋顔検出）→ GUI（人物登録＋手動割り当て）→ `match`（残りを自動紐づけ）
の順に組み替え、`analyze` を廃止した。あわせて、閾値判定が無く必ず誰かに紐づいて
いた欠陥（#22）、手本が2枚以上あると人物が壊れる剰余バグ、個人識別能力の無い
特徴量（FaceMesh の x 座標を128個並べただけ）を直した。特徴量は dlib ResNet の
128次元に置き換えた。DBスキーマは `user_version = 2`。移行は `photoarchive migrate`。

実データ 70,297件で移行と部分スキャンを確認済み。2回目のスキャンが 29.9秒 → 0.87秒
になり、差分スキャンの欠陥（#9）も解消した。既定の閾値は実測に基づき 0.5 → 0.4。

次にやること: GUI で人物ごとに20〜50枚を割り当てたうえで `match` の**取りこぼし率**を
測る（誤一致率しか測れていない）。全件スキャンは未実施。

詳細: [details/2026-09-19-issue28-rework.md](details/2026-09-19-issue28-rework.md)

## 2026-09-06 — #14 HEIC/HEIF の一括変換と、#10 の真因特定

PR [#21](https://github.com/Beerski43/PhotoArchiveAI/pull/21)（merged）。

`photoarchive convert-heic` を追加した。同名JPEGが同じ写真ならスキップし、違う
写真なら連番を付ける。元のHEICは変更しない。

`face_recognition_models/__init__.py` の `pkg_resources` 依存が setuptools 81 以降で
`ModuleNotFoundError` になるのが #10 の真因だった。`importlib.util.find_spec` なら
`__init__.py` を実行せずモデルのパスだけ取り出せる。`face_recognition` パッケージ
自体は不要なので依存から外した。

あわせて、解析結果がすべて0になる問題を追い込んだ。MediaPipe の矩形は
`relative_bounding_box` に入るのに空の `bounding_box` を見ていたこと、
`mp.solutions` API のために 0.10.21 への固定が必要だったことが原因。

詳細: [details/2026-09-06-heic-and-analyze.md](details/2026-09-06-heic-and-analyze.md)
