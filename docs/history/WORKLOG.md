## 2026-10-08 — 未割当の画面に撮影年月の絞り込みを足す

**#63・PR #64 に対話で追加。** 利用者から「**先に家族じゃない顔を除外したいので、
GUI 起動直後の未割当の画面に撮影年月のフィルタがほしい**」という依頼。

**家族の写っていない写真は時期でまとまっている。** 結婚式や旅行先で写った他人は
その行事の期間に固まるので、**その月だけを開いてまとめて除外できる。**

- `db.month_expression()` を足した。**読めない撮影日時を月として扱わない**
  （`substr(shooting_date, 1, 7)` と書くと「TTTT-TT」という月が並ぶ。
  判断は `SHOOTING_DATE_SORT_KEY` に1つだけ）
- `db.available_months()` / `db.count_undated_faces()`。
  **顔のある写真の月だけ**を新しい順に出す（実データで250個）
- `_face_filter` に `month` を通した。`UNDATED` で「撮影日時なし」
  （**`None`＝絞らない と同じ値で表さない**）
- GUI の未割当の画面に `いつから` 〜 `いつまで` の2つの欄を置いた。**両端を含み、
  片方だけの指定もできる。** 上下が逆転したら押し戻す（黙って0件にすると
  絞り込みが壊れて見える）。**種別や行事と併用できる**
- `撮影日時なしのみ` はチェックボックスで別に持つ。**範囲とは排他**

### 「撮影日時なし」の実体と、フォルダ名からの復元（判断待ち）

利用者から「撮影日時なしとは写真のメタデータが無いという理解でよいか。その場合
**フォルダ名に年月が入っているはずなので特定できる**のでは」と問われた。

内訳は `shooting_date IS NULL` が 11,090 件、壊れた値が 67 件
（`0000-00-00T00:00:00` と `TTTT-TT-TTTTT:TT:TT`）。**理解のとおり。**

フォルダ名からの復元は**着想として正しい**が、即席の正規表現で測ったところ
**すでに誤りが出た**（`/Photo/2010/2010.jpg` のファイル名を `YYMM` と誤読して
2020-10 にする、`20260100` のような `YYYYMMDD` を取りこぼす、など）。
**日付の読み取りはこのリポジトリが2度壊れている箇所**なので、別途きちんと
設計すべき作業として **#65 に起票した**（利用者の指示。Phase 3 手順9・
ROADMAP と phase 文書にも入れた）。**着手は指示待ち。**

調べて分かったこと。

| フォルダ名の形（顔のある3,746件） | 件数 |
|---|---|
| `YYYYMMDD…` / `YYMMDD…` / 4桁 / 2桁（いずれも4桁年の下） | **3,619（96.6%）** |
| 数字で始まらない | 169 |

**4桁フォルダ（`2012/1210/`）は `YYMM`。`MMDD` ではない。**
EXIF が読める写真400件で照合して 400/400 一致、`MMDD` は0件だった。
**規約を推測で決めず、この検算の形を実装の検証にも使うこと。**

**`Media.shooting_date` に書き戻してはいけない**（EXIF から読めた値と、
フォルダ名から推測した値を同じ列に混ぜると、どちらか分からなくなる。
`Face.age` と計算年齢を分けているのと同じ理由）。

**閾値の選び方はモデルを替えても同じ。** 「行事をまたぐ別人を1%程度しか
誤らない」点を採った。**同じ誤り率で拾える率が約30% → 63.5%。**

### 踏みかけた罠を2つ避けた

- **`DETECTOR_VERSION` の文字列を素朴に変えると、実データ 70,297 件すべてが
  再検出になる**（441GB を NFS から読み直す）。実データの値は特徴量の版まで
  連結された古い形なので、**比較の側を `face.detector_version_of` で正規化**して
  揃えた。データの書き換えも移行も要らない
- **照合に版の違う特徴量が混ざる。** `reembed` の途中は必ず混在するので、
  `load_manual_embeddings` と `iter_unassigned_embeddings` を
  `embed_version` で絞った。次元が同じモデル同士なら**黙って無意味な距離**が出る

### `reembed` を足した

サムネイルから `Face.embedding` と `Face.embed_version` **だけ**を書く。
**割り当て・除外・年齢に触らない**（`scan --force-rescan` との決定的な違い）。
**元写真を読まない。** 途中で止めても続きから再開する。

**見積りを定数で持たせなかった。** `--dry-run` が12件を実際に作って測る。
最初は 145ms/件 という測定値を定数に書いたが、**ほかの重い処理と同時に
走らせると 1,765ms/件まで落ちた**（推論が全コアを使うので取り合う）。
固定した数字は黙って古くなるし、環境でも変わる。

### `parse_date` を `gui.py` から出した

利用者が gui・`db.SHOOTING_DATE_SORT_KEY`（SQL の写し）・測定スクリプトの
**3つになった**ので、`dates.py`（新規）へ移した。`gui` は再公開するだけ。

### `scripts/fetch_models.py` を足した

ONNX（174MB）が**アプリ本体の必須ファイル**になったので、sha256 を検証して
`models/` へ置くスクリプトにした。**アプリからは呼ばない**（`scan` が黙って
外部へ通信するのは挙動が読みにくい）。`onnxruntime` を `pyproject.toml` の
実行時依存へ移した。

そのあと `evaluate` で閾値を確定し（Phase 3 手順5）、行事ごとの束ね（手順3）へ。
